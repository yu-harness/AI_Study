# 代码分析（重构版）

## 阅读指南：三个层级

| 层级 | 内容 | 面试要求 |
| --- | --- | --- |
| **必讲主干** | 链路、路由、风控、工具、记忆五条主线 + 设计取舍 | 能脱稿讲 3 分钟 |
| **需要能解释** | 每个模块的关键实现与失败分支 | 被追问时能说清“为什么这么写” |
| **知道存在即可** | 内存实现、脚本细节、Temporal 活动清单 | 问到能说出定位 |

## 一、系统全景与核心主干（面试必讲）

### 1.1 一句话链路

用户提问 → 记忆召回 → 意图路由 → 按清单逐节点执行（专业 Agent 取数）→ 候选答案合成 → Critic 合规审核 → 最终回答 + 事件流。

### 1.2 五条主线

| 主线     | 核心机制                                             | 一句话                 |
| ------ | ------------------------------------------------ | ------------------- |
| **状态** | `AgentState` 单一共享对象，所有节点只读写它                     | 一轮对话只有一份状态，谁改了都看得见  |
| **路由** | `plan()` 产出 `route_plan` 清单，`route_index` 指针逐条推进 | 先出完整计划，再按序执行，不边跑边想  |
| **风控** | Critic 是强制节点，规则硬拦截在模型判断之前                        | 合规不通过，答案出不去         |
| **工具** | 注册表 + 执行器，参数校验、超时、降级、审计统一收口                      | 工具不是一个函数，是一条带策略的调用链 |
| **记忆** | 短期滑动窗口 + 长期向量/图双路召回                              | 当前对话压缩，跨会话偏好检索      |

### 1.3 六个关键设计取舍

| 设计 | 为什么 | 代价 |
| --- | --- | --- |
| **编排确定性**，模型不自由选工具 | 同一问题两次必须走同一条路径，否则无法归因 | 灵活性差，新场景要改代码 |
| **`route_index` 不进快照** | 快照记录的是“方法执行到哪”，索引是循环变量，重放时应由入口重置 | 恢复时必须显式归零，漏了会跳步 |
| **`candidate_response` 靠条件出口触发** | 它是汇聚节点，前面可能走 1 个或 3 个 Agent，只有在所有分支汇合处触发才不会漏 | 边的关系比顺序执行复杂 |
| **查询类 / 计算类工具分开** | 查询要防不确定（超时、降级、时效标注），计算要保证可重复（纯函数） | 需要维护两套策略 |
| **工具先落 `pending_tools` 再执行，带幂等键** | 中断恢复时能判断哪些调用已执行过 | 状态里多一份队列，要清理 |
| **Critic 用规则 + 模型双层** | 规则拦得住“必涨保本”，模型兜得住隐晦表述 | 误拒率存在，需要否定语境识别 |

## 二、核心执行引擎

### 2.1 LangGraph 编排与状态恢复

#### 图结构

- **固定边**：入口两步（`memory_retrieval` → `intent_routing`）和出口一步，顺序永不变
- **条件边**：所有可执行节点共用同一个路由函数 `_next_route_node` 和同一张映射表
- **例外**：草稿节点出边固定，出错直接结束
- 编译时挂 checkpointer，才有快照与续跑

#### 一次 `run_chat` 的十步

| 步骤 | 动作 | 关键点 |
| --- | --- | --- |
| 1 | `ensure_conversation` | 幂等建会话行 |
| 2 | `add_message` | 用户这句话落库 |
| 3 | `create_task` | 生成 `task_id` + `trace_id` |
| 4 | 读最近 N 条消息 | 填 `state.messages` |
| 5 | 读上一轮 `AgentState` | 未完成则接回 `active_task` / `task_stack` |
| 6 | 构建 `ToolContext` | 租户、用户、账户范围 |
| 7 | `graph.stream(stream_mode="updates")` | 每节点吐局部更新，不是整份 state |
| 8 | 按节点类型发事件 | 记忆、路由、Agent、风控、最终各自有格式 |
| 9 | 写 `task_events` | 唯一写事件的地方，分配 `sequence` |
| 10 | 落库状态 | 供下一轮恢复 |

#### 快照只在四处存

`checkpoint=True` 只出现在：路由事件、草稿（候选答案）、风控事件、最终回答。其余事件沿用同一 `checkpoint_id`，便于按快照回放，但不会为每条日志写一份快照。

#### 恢复 vs 断线补发（两个不同问题）

| 场景 | 机制 | 做什么 |
| --- | --- | --- |
| **断线** | `resume_events` | 按 `sequence` / `event_id` 只补发漏掉的事件，流程不重跑 |
| **任务被打断** | 压栈 + `_run_resumed_task_events` | 取出原任务描述重新执行，已完成的工具不再调 |

恢复时清空 `interruption`、`task_stack`，把 `status` 改回 `running`，用**原 `task_id`** 作为 `thread_id` 续跑快照。

### 2.2 路由：`plan()` 一次判定分五段

| 段 | 做什么 |
| --- | --- |
| ① 打断判定 | 既是打断词、又确实有任务在跑，才算打断 |
| ② 意图分类 | 打断走本地规则（快、不依赖外部）；正常走可配置分类器 |
| ③ 追问处理 | 能继承就继承原意图，推不出就压低置信度 |
| ④ 压栈 | 旧任务挂起，记录 `InterruptionInfo` |
| ⑤ 落状态 | 写 `current_intent`、`intent_confidence`、`active_task`、`route_plan` |

**`route_index` 不在第 ⑤ 段**：它由调用方归零，因为它是执行指针不是任务属性。

#### 三个容易混的点

**① `TaskFrame`** 是一条「正在做的事」的记录：`task_id`、`intent`、`description`（用户原话）、`checkpoint_id`。栈里可以有多层。

**② 高风险判定**用正则先行（`HIGH_RISK_RE`），命中后进 Critic，不靠模型判断。

**③ `general_financial_question` 走 router 节点**：不需要取数的概念题，直接组织回答，不启动专业 Agent。

#### 意图分类三级递进

| 层 | 实现 | 何时生效 |
| --- | --- | --- |
| 1 | 关键词 + 正则 | 命中即返回，覆盖高频问法 |
| 2 | BERT 分类器 | 规则覆盖不到的表述，走 HTTP 网关 |
| 3 | 置信度不足 | 追问澄清 |

规则置信度 ≥ 0.9 或命中高危/偏好更新，直接采用规则结果，不调模型。

### 2.3 工具注册与执行器

#### 两类工具，两套策略

| | 查询类（9 个） | 计算类（5 个） |
| --- | --- | --- |
| 例子 | `get_realtime_stock`、`macro_indicator`、`web_search` | `calc_portfolio_metrics`、`run_scenario_analysis`、`compliance_rule_check` |
| 耗时 | 不确定 | 毫秒级 |
| 超时 | 必须 3 秒 + 重试 + 降级 | 不需要 |
| 结果 | 不可重复，必须标 `source_ts`、`freshness` | 完全可重复 |
| 失败原因 | 网络、限流、上游故障 | 参数非法、数据缺失 |

#### 一次调用的链路

构造 `ToolCall`（带 `idempotency_key`）→ 查注册表 → Pydantic 校验参数 → 线程池执行（3 秒超时）→ 失败重试 1 次 → 仅超时才降级 → 拆分 `sources` / `source_ts` / `status` → 写 `tool_call_logs`（参数只存 SHA256）→ 回填 `state.tool_results`。

**超时的真相**：`future.result(timeout=3)` 只是调用方不再等，**handler 线程仍在跑**。所以超时必须双层——外层止损，内层 HTTP 客户端自己的 timeout 才止血。

#### 工具失败只有两类

| 类型 | 表现 | 解法 |
| --- | --- | --- |
| 参数错误 | 工具对、参数错 | Schema 约束 + JSON 修复 + 结构化报错回流 |
| 工具选错 | 参数对、工具错 | 描述精确化 + `RouteStep.tools` 白名单 |

**参数错误可以重试，工具选错重试没用**——所以后者必须在路由层用白名单拦住。

### 2.4 长短期记忆

#### 两层分工

| | 短期 | 长期 |
| --- | --- | --- |
| 存什么 | 最近 10 条消息 + 旧消息摘要 | 结构化偏好条目 + 市场叙事 |
| 触发 | 每轮都压缩 | 每轮都召回，在图的第一节点 |
| 检索 | 直接拼接 | 向量 top-5 + 图 top-2 → 重排 → top-5 |

#### 召回在意图识别之前

`memory_retrieval` 是入口第一个节点。理由是**用户约束会影响路由**：用户说过「不碰 ST 股」，即使这轮问行情，也要先加载这个约束。

节点内顺序是「先写后读」：先从当前这句话抽取新偏好落库，再做召回——用户刚说的话当轮就能被召回。

#### 三个存储各管什么

| 存储 | 角色 | 存什么 |
| --- | --- | --- |
| PostgreSQL | 账本（权威） | `memory_items` 明细、`access_count`、`valid_to`、有效期 |
| Milvus | 目录（索引） | 向量 + 检索用标量字段，可从 PG 重建 |
| Neo4j | 图谱 | 市场叙事全文索引，**当前没有关系遍历** |

#### 冲突检测与权重现状

- 冲突只覆盖两类：多条不同回撤约束、ST 回避与允许并存。**靠字符串匹配**，检测结果写进最终 prompt，让模型提示用户澄清并按保守方执行，**不阻断流程**。
- 权重公式（时间指数衰减 × 访问频次对数提权）已设计，但写入时 `decay_weight` **硬编码 1.0**，`calculate_weight` 无调用点——**衰减尚未接入**。

### 2.5 四个 Agent 与 Builder / Risk

#### 各 Agent 取什么数

| Agent  | 工具                               | 输出特点                        |
| ------ | -------------------------------- | --------------------------- |
| market | 实时行情、延迟行情、历史价                    | 单一事实 + 时效                   |
| quant  | 持仓 + 历史价 + 指标 + 情景 + 影响分析        | 全数字，且从 `macro_agent` 输出推断情景 |
| macro  | `macro_indicator` + `web_search` | 指标 + 新闻交叉验证，按 theme 生成传导提示  |
| report | SEC 财报 / A 股公告                   | 只返回指定章节                     |

**量化 Agent 不重读用户问题**，直接读 `state.agent_outputs["macro_agent"]` 拼文本匹配情景关键词——避免推翻宏观已做的判断。

#### Builder 的五块上下文

1. 用户原问题
2. 长期记忆约束（`decay_weight ≥ 0.3` 且 `importance ≥ 0.3`，取前 3）
3. 冲突提示（如果有）
4. 各 Agent 的 `findings` + `sources`
5. 格式与合规要求

#### Risk 规则的判定顺序

1. 关键词命中 → 看**否定窗口**，避免「不要满仓」被当成建议满仓
2. 定级看证据来源：用户自己提的要求直接拒，模型写的走改写
3. 出现 `high` 级 → 整体降级为拒答，不再尝试改写
4. 缺来源 → 生成具体补数据清单，不给一句空话

## 三、工程配套与生产化落地

> 这一章回答“代码能跑”之外的三个问题：**数据和表从哪来、本地怎么不带依赖跑、上线前怎么确认就绪**。

### 3.1 数据库初始化与迁移

**两套入口，面向两种场景**：

| 脚本                            | 场景      | 做什么                                                     |
| ----------------------------- | ------- | ------------------------------------------------------- |
| `scripts/init_db.py`          | 开发 / 本地 | `build_store(settings)` → `store.init_schema()`，按当前后端建表 |
| `scripts/apply_migrations.py` | 生产      | 按文件名顺序执行 `infra/migrations/*.sql`，再执行 `*.cypher`        |


**为什么要两套**：`init_schema` 是代码内置的建表逻辑，跟着 Store 实现走，改表结构就要改代码；生产用迁移文件，可版本化、可审计、可回滚。**开发图快，生产图可追溯**。

`apply_migrations` 的三个工程细节：

1. **重试**：`_retry` 默认 60 次、间隔 2 秒。容器编排里数据库常常比应用晚就绪，硬等不如重试。
2. **Cypher 按分号切**：Neo4j 驱动一次只能跑一条语句，脚本先按 `;` 拆再逐条执行。
3. **缺配置直接报错**：没配 `FINAGENT_DATABASE_URL` 或 Neo4j 三件套，启动即失败，不静默跳过。

**三份迁移各自的职责**：

| 文件 | 内容 |
| --- | --- |
| `001_initial.sql` | 业务核心表：用户、会话、消息、持仓、任务、检查点、事件、工具调用日志、风控记录、记忆明细、发件箱 |
| `002_gateway_sources.sql` | 上游数据落地表：行情、历史价格、宏观指标、A 股公告、研报片段 |
| `003_graph_narratives.cypher` | Neo4j 全文索引 `market_narrative_fulltext` |

**注意表的分工**：`001` 存“系统自己产生的状态”，`002` 存“从外部抓回来的原始数据”。工具读的是 `002`，不是直接打外部 API——这样外部接口挂了，系统还能用快照降级。

### 3.2 批量导入与数据同步

四个脚本，一个共同模式：**读外部 → 落库 → 工具读表**。

| 脚本 | 数据源 | 落到哪 | 用途 |
| --- | --- | --- | --- |
| `import_portfolio.py` | 本地 JSON 快照 | `portfolios` + `portfolio_positions` | 给用户灌持仓，量化 Agent 才有数可算 |
| `sync_market_data.py` | Yahoo Finance v8 chart API | `historical_prices` + `market_quotes` | 行情、历史价 |
| `sync_sec_rag.py` | SEC EDGAR | `research_snippets` | 财报章节片段，供检索 |
| `check_production_readiness.py` | — | — | 上线前探活 + 深度检查 |

**`import_portfolio` 的设计**：命令行传租户、用户、账户、币种，JSON 里给 `positions` 数组，调 `store.upsert_portfolio_snapshot` 整份替换。**快照语义**而不是增量追加——持仓是时点状态，重复导入不该产生重复行。

**`sync_market_data` 的关键处理**：从 Yahoo 拿 `timestamp` / `quote` / `adjclose` 三组数组，按下标对齐逐日写入，同时把最新价写进 `market_quotes`。`source_url` 一并落库，供回答引用出处。

**`check_production_readiness` 的定位**：不是单元测试，是**上线门禁**。先 `validate_production_dependencies()` 检查配置齐不齐，再 `run_deep_readiness_checks()` 真实调一次工具和检索，返回非 0 就说明不该发版。

### 3.3 本地无依赖预览

**目标**：不起 Milvus、Neo4j、Ollama，也能把路由、事件、风控、SSE 全跑通。

三件内存实现：

| 实现 | 顶替什么 | 行为 |
| --- | --- | --- |
| `InMemoryMemoryVectorStore` | Milvus | 一个 list，按 `is_core` → `decay_weight` → `importance` 排序，**没有向量相似度** |
| `EmptyMarketGraphStore` | Neo4j | 永远返回空列表 |
| `InMemoryMarketDataProvider` | 行情网关 | 固定报价表 + 固定时间 `2026-06-01`，保证每次跑结果一致 |

加上 `SQLiteStore` 和一个 `LocalPreviewLLM`（返回固定文本，不调真模型），整条链路就活了。

**为什么值得单独做一套**：

- 开发时不用等外部服务，改一行代码立刻能验
- CI 里不需要起容器，跑得快
- 演示时可以控制数据，不会因为行情变了导致答案前后不一致

**取舍**：内存实现**不验证真实检索质量**。向量相似度、全文分词这些必须连真库才能测，所以它是“链路验证工具”，不是“效果验证工具”。

### 3.4 API、SSE 与健康检查

**入口**：`create_app` 组装 Settings、Store、Orchestrator、Temporal 网关（可选），用 `lifespan` 管资源释放，`dependency_overrides` 让测试能替换配置。

**流式**：`POST /v1/chat/stream` 返回 `text/event-stream`，每个事件两行（`event:` + `data:`），空行分隔。路由函数声明成 `def` 而不是 `async def`，因为内部是同步阻塞的 LangGraph——写成 `async` 会堵事件循环。

**健康检查三级**：

| 端点 | 检查什么 | 用途 |
| --- | --- | --- |
| `/health` | 进程活着 | 容器 liveness |
| `/ready` | 逐个探测 PG、Milvus、Embedding、Neo4j、RAG、行情、LLM 的连通性 | 负载均衡 readiness |
| `/ready/deep` | 真实跑一次工具和检索 | 上线前人工确认 |

**限流的现状**：`_check_rate_limit` 用**进程内内存字典**做 60 秒滑动窗口。单实例够用，多副本部署时每个实例各算各的，等于上限乘以副本数——这是已知限制，要真生效必须换 Redis。

### 3.5 Temporal 异步编排

**和 LangGraph 的关系**：LangGraph 负责“一轮对话内部怎么走”，Temporal 负责“这一轮任务怎么在故障中活下来”。两套并存，由 `orchestrator_backend` 切换。

Temporal 版把图里的每一步拆成活动（activity），好处是：

- 活动失败自动重试，重试策略可配
- 工作流状态由 Temporal 持久化，进程挂了能续
- 长任务可以跨小时，不依赖单进程存活

**代价**：多一层服务依赖，调试更麻烦。所以本地开发默认走 LangGraph，生产可以选 Temporal。

### 3.6 数据流水线与离线评测

`data_pipeline/` 不参与线上问答，服务于“把线上轨迹变成训练数据”。

| 子包 | 做什么 | 关键入口 |
| --- | --- | --- |
| `sft_generation/` | 用真实 orchestrator 跑预设场景，把工具调用和结果渲染成 SFT 样本 | `seed_trajectories.py`、`plans.py` |
| `cleaning/` | 校验 JSONL：消息结构、工具调用格式、Observation 是否被引用 | `trajectory.py` 的 `validate_jsonl`、`validate_record` |
| `training/` | 检查训练资产（配置、DeepSpeed、数据集）是否齐全，拼 LLaMA-Factory 命令 | `assets.py` 的 `build_training_plan` |
| `evaluation/` | 用固定 case + prediction 算五个指标 | `offline.py` 的 `evaluate_offline` |

**评测与线上共用一套数据结构**：`EvaluationPrediction` 里的 `tool_results`、`final_status`、`memory_items`、`risk_verdict`，正好对应 `AgentState` 和事件流里的字段。**能评测，是因为链路的每个中间结果都落了库**——这也是为什么 `tool_call_logs`、`task_events`、`risk_reviews` 这些表必须存在。

**五个离线指标**：工具成功率、目标完成率、记忆召回率、严重幻觉率、缺失预测数。

## 四、面试追问速查表

| 追问                     | 一句话回答                                                | 性质   |
| ---------------------- | ---------------------------------------------------- | ---- |
| 为什么不让模型自己选工具？          | 同一问题两次必须走同一条路径，否则出错无法归因；编排确定性换可审计                    | 设计   |
| `route_index` 为什么不进快照？ | 它是循环指针，不是任务属性；恢复时由入口归零，否则会跳步                         | 设计   |
| 为什么快照只存四处？             | 只有路由、候选、风控、最终是状态分叉点，其余是过程日志                          | 设计   |
| 断线和任务中断有什么区别？          | 断线只补事件不重跑；中断要压栈、换任务、再弹栈恢复                            | 设计   |
| 工具超时真的停了吗？             | 没有。`future.result` 只是不等了，线程还在跑，必须靠内层 HTTP timeout 兜住 | 坑点   |
| 为什么降级只对超时？             | 参数错、业务错换工具也一样错，盲目降级会把明确错误变模糊                         | 设计   |
| 查询类和计算类为什么要分？          | 一个防不确定（超时/降级/时效），一个保可重复（纯函数）                         | 设计   |
| 记忆为什么在意图识别之前召回？        | 用户约束会影响路由，比如「不碰 ST」要在路由前就加载                          | 设计   |
| 新旧偏好冲突怎么处理？            | 标记冲突、写进 prompt、按保守方执行并提示用户确认，不阻断                     | 简化版  |
| 权重衰减真的生效吗？             | 公式和字段已设计，写入固定 1.0，计算函数未被调用                           | 简化版  |
| 图数据库做了什么？              | 只用全文索引检索叙事，没有关系遍历，等于带索引的文档库                          | 简化版  |
| 意图分类是自训模型吗？            | 默认规则，可接 BERT 网关做混合，不是自训                              | 简化版  |
| 限流多副本有效吗？              | 无效，内存字典各算各的，要共享得换 Redis                              | 简化版  |
| 本地怎么不带依赖跑？             | SQLite + 三个内存实现 + 固定回复 LLM，验证链路不验证效果                 | 工程配套 |
| 为什么有两套建库方式？            | 开发用 `init_schema` 求快，生产用迁移文件求可追溯                     | 工程配套 |
| 上线前怎么确认就绪？             | `check_production_readiness` 查配置 + 真实调用，返回非 0 不发版    | 工程配套 |
| 训练数据怎么来的？              | 真实 orchestrator 跑预设场景生成轨迹，清洗后交给 LLaMA-Factory        | 数据侧  |
| 评测和线上怎么对齐？             | 评测用的字段就是 `AgentState` 和事件流的字段，因为链路中间结果全落了库           | 设计   |
