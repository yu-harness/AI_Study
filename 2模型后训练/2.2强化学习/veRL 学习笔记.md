# veRL 学习笔记

> 一句话定位：veRL 是**把「推理引擎」和「训练引擎」拼成一个 RL 闭环的编排层**——用 vLLM 负责快速采样，用 Megatron/FSDP 负责分布式反传，中间解决权重怎么同步、显存怎么复用。

---

## 一、是什么与解决什么痛点

### 1.1 RL 训练循环的主线

大模型 RL 不是「喂数据 → 更新」的单向流程，而是一个循环：

```
① Rollout：用当前策略生成一批回答
② Reward：给这批回答打分（规则 / 奖励模型 / 裁判模型）
③ Advantage：算出每条回答比平均水平好多少
④ Update：按优势更新策略参数
⑤ 回到 ①，用新参数重新采样
```

**第 ① 步是整条链路的时间瓶颈**。一次要生成几百上千条长回答，自回归解码，逐 token 出。

### 1.2 三个绕不开的痛点

| 痛点 | 具体表现 |
|---|---|
| **多角色切换** | PPO 要同时有 Actor、Critic、Reference、Reward 四个模型，权重在不同阶段反复搬运 |
| **Rollout 慢** | 普通训练框架做自回归生成，没有 KV Cache 复用、没有连续批处理，吞吐极低 |
| **显存冲突** | 四个模型同时驻留，加上长上下文的 KV Cache，单卡装不下 |

朴素做法是「训练跑完，把权重存盘，再加载到推理服务」——一次同步就要几十秒到几分钟，一个训练循环几百步，光同步就废了。

**veRL 的价值就是把这套切换做成工程化的高频操作**，而不是每次手动搬运。

## 二、核心架构与 vLLM + Megatron/FSDP 协同

### 2.1 角色分工

| 角色 | 职责 | 是否参与反传 |
|---|---|---|
| **Actor** | 当前策略，生成回答、被更新 | 是 |
| **Reference** | 初始策略的冻结副本，用于算 KL 约束 | 否 |
| **Critic** | 估计状态价值，算优势 | 是（PPO 才有） |
| **Reward Model** | 给回答打分 | 否 |
| **Rollout 引擎** | 执行 Actor 的前向生成 | 否（只推理） |

GRPO 去掉了 Critic，用**组内相对分代替价值估计**——这是它省显存的核心原因。

### 2.2 两个引擎，两种优化目标

|      | vLLM（推理）                        | Megatron / FSDP（训练） |
| ---- | ------------------------------- | ------------------- |
| 目标   | 高吞吐、低延迟                         | 大 batch 反传、参数切分     |
| 关键技术 | PagedAttention、连续批处理、CUDA Graph | 张量并行、流水并行、ZeRO 切分   |
| 显存重点 | KV Cache 要大                     | 激活值和优化器状态要小         |

**为什么不能一个框架全干**：推理要的是「同一份权重、很多条请求并行」；训练要的是「参数切到多卡、每步反传」。两套并行策略、两套显存管理，硬塞进一个框架只会两边都做不好。

### 2.3 权重同步（Weight Sync / Resharding）

这是 veRL 最核心的工程点。

**问题**：训练时参数按 TP/PP 切在 8 张卡上，推理时 vLLM 可能按另一种方式切。两份布局不一样，不能直接拷。

**做法**：把训练侧的权重**重新分片（resharding）**，转换成推理引擎能直接加载的布局，再通过 GPU 间通信（同机可用 NCCL 或共享内存）推送过去。

**同步频率**：每个训练 step 之前或之后同步一次。频率越高，模型越新，但通信开销越大。

### 2.4 显存复用：Colocate vs 分离部署

| 模式 | 做法 | 取舍 |
|---|---|---|
| **Colocate（同卡）** | 推理和训练共用一个 GPU 池，分时切换 | 省卡，但要在两者间腾挪显存 |
| **分离部署** | 推理一组卡、训练一组卡 | 简单，但卡要多一倍 |

Colocate 模式下，切换时的关键动作是**把一方的显存释放出去**：

- 训练转推理：把优化器状态、激活值卸载到 CPU 或丢弃，腾出空间给 KV Cache
- 推理转训练：释放 KV Cache，把参数和优化器状态搬回来

这一步做不好就是 OOM 的直接来源。

## 三、主流算法与训练流程

### 3.1 一次训练 step 的节奏

```
1. 同步权重到 vLLM
2. Rollout：对一批 prompt 各生成 G 条回答（G 是 group size）
3. 打分：规则 / 沙盒 / 奖励模型
4. 算 advantage
5. 把这批数据切成多个 mini-batch，做若干次梯度更新
6. 回到 1
```

**两个 batch 概念要分清**：

- **Rollout batch**：一次采样多少 prompt，决定数据多样性
- **Mini batch**：一次反传多少样本，受显存限制

### 3.2 PPO 与 GRPO 的差别

| | PPO | GRPO |
|---|---|---|
| 优势怎么算 | Critic 模型估计状态价值，再用 GAE | 同组内各条分数减去组平均 |
| 需要几个模型 | Actor + Critic + Ref + RM | Actor + Ref + RM |
| 显存 | 高，Critic 和 Actor 一样大 | 低，省掉 Critic |
| 适用 | 通用场景，信号细腻 | 有可靠打分函数时更划算 |

**GRPO 的关键前提**：必须有一个可信的**绝对打分**（比如代码能否运行、SQL 结果是否正确）。没有客观裁判，组内相对分就没有意义。

### 3.3 关键超参与稳定性

| 参数 | 作用 | 调错会怎样 |
|---|---|---|
| **KL 系数** | 约束新策略不要偏离 Reference 太远 | 太小 → 语言能力崩坏；太大 → 学不动 |
| **Clip range** | PPO 里限制单步更新幅度 | 太大 → 策略震荡 |
| **Group size（G）** | GRPO 每组生成几条 | 太小 → 优势估计噪声大；太大 → 采样成本翻倍 |
| **学习率** | 通常远小于 SFT | 太大 → 策略崩溃，输出语法都乱 |
| **最大生成长度** | 控制单条回答上限 | 不设限 → 模型学会灌水凑分 |

**三个常见失稳信号**：

1. **KL 爆炸**：输出开始重复、乱码
2. **长度膨胀**：回答越来越长，因为长回答更容易碰对
3. **奖励饱和**：所有样本同分，advantage 全为 0，梯度消失

## 四、常见坑点与调优方向

| 现象 | 原因 | 排查方向 |
|---|---|---|
| **OOM** | 推理和训练显存叠加，KV Cache 吃满 | 降 rollout batch、降最大长度、开 offload、调小 G |
| **每步很久但 GPU 利用率低** | Rollout 阶段在等生成，训练卡空转 | 提高推理并发、用连续批处理、减少同步频率 |
| **权重同步占大量时间** | 同步太频繁或走网络而非 GPU 直连 | 降同步频率、同机用共享内存、检查 resharding 是否有多余拷贝 |
| **训练发散** | 学习率过大、KL 系数不当 | 降 lr 一个数量级、加大 KL 惩罚、检查 reward 是否有异常极值 |
| **模型学会钻空子** | 奖励可被 hack（如空结果也算通过） | 加惩罚项（空集给负分）、加格式检查、人工抽检高分样本 |
| **长短样本混合导致 padding 浪费** | 变长序列填充 | 用 packing 或按长度分桶 |

**一个优先级建议**：先解决 OOM，再解决吞吐，最后调算法。显存不够时，所有调参都是在猜。

## 五、面试高频追问简答

### Q1：为什么 Rollout 用 vLLM，训练用 FSDP/Megatron？

> 两个阶段的优化目标不同。Rollout 是自回归生成，瓶颈在解码吞吐，vLLM 的 PagedAttention 和连续批处理能把 GPU 利用率拉满；训练是反传，瓶颈在显存和通信，FSDP/Megatron 的参数切分和通信重叠才是对的工具。
> 用训练框架做生成，吞吐可能差一个数量级；用推理框架做训练，根本做不了反传。

### Q2：训练和推理的显存怎么不打架？

> 两条路。一是**分时复用**（colocate）：同一批卡，训练时把 KV Cache 释放，推理时把优化器状态和激活值 offload 出去，两者不同时占显存。二是**物理分离**：推理一组卡、训练一组卡，简单但成本翻倍。
> 实际用 colocate 居多，代价是切换有开销，需要精确控制生命周期。

### Q3：权重同步为什么是个难题？

> 因为两边的**并行布局不一样**。训练侧参数按 TP/PP 切片，推理侧 vLLM 有自己的切法，不能直接拷贝，要做 resharding——把碎片化的参数重新拼成推理引擎认识的形状。
> 这会带来额外通信和内存拷贝，同步频率越高代价越大，所以要在「模型新鲜度」和「同步开销」之间取平衡。

### Q4：PPO 和 GRPO 在工程调度上有什么差异？

> 最大差异是**要不要 Critic**。PPO 要额外跑一个和 Actor 同样大的 Critic，显存和计算都翻倍，还要处理 Critic 和 Actor 的权重同步。
> GRPO 用组内相对分代替 Critic，省掉一个模型，调度简单很多。但代价是每个 prompt 要生成一组（G 条）回答，采样成本上升。
> 所以是「省显存换采样量」，适合有可靠打分的场景。

### Q5：RL 训练里最容易被忽略的瓶颈是什么？

> **不是训练，是采样**。一次 step 里，反传可能几十秒，但生成上千条长回答要几分钟。GPU 在训练阶段是满的，在采样阶段大量时间在等。
> 所以真正的优化重点在推理侧：提高并发、减少同步、控制生成长度。很多人调 RL 只盯学习率，其实吞吐才是墙。

---

> **最小认知路径**：先理解 RL 循环里「采样慢、模型多、显存挤」这三个痛点 → 再看 veRL 用两套引擎分工解决前两个 → 用权重同步和显存复用解决第三个 → 最后才是算法（PPO/GRPO）的选择。
