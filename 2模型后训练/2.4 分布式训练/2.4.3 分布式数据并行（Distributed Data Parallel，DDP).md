# 2.4.3 分布式数据并行（DDP）

> [!abstract] 一句话
> 多进程真并行：初始模型靠 Broadcast 对齐，每轮梯度靠 AllReduce 对齐，于是"相同初始 + 相同梯度 = 相同模型"。

真正的数据并行，采用**多进程**的方式进行训练。与 `nn.DataParallel` 的单进程多线程相比，区别见 [[2.4.2 数据并行（ Data Parallel，DP）]]。

- 所有显卡的初始模型都相同，**一般会将 global-rank=0 的显卡的模型广播到其他显卡**。
- 在每轮训练时，反向传播计算出梯度后，**采用 Allreduce 通信来聚合所有显卡的梯度**，确保所有显卡的梯度都一致。
- **相同的初始模型 + 相同的梯度 = 相同的训练模型**。

## 一、集合通信：六种类型

第四步的通信指不同计算节点之间**进行信息交换**、以协调训练任务，按参与方分为两类：

- **点对点通信**：将数据从一个进程传输到另一个进程；
- **集合通信**：一个分组中所有进程参与的通信模式。

常见的六种集合通信：

| 类型 | 一句话 | 结果留在哪 |
| --- | --- | --- |
| **Scatter** | 把一份数据切块，分别发给各进程 | 分散到所有进程 |
| **Gather** | 把各进程的数据收集起来 | 集中到 1 个进程 |
| **Reduce** | 在 Gather 基础上**添加计算**（求和、求平均） | 集中到 1 个进程 |
| **All Reduce** | 在每一个进程都存储 Reduce 的结果 | 每个进程都有 |
| **Broadcast** | 将一个进程的信息**广播**给其他节点 | 每个进程都有 |
| **All Gather** | 在每一个进程都存储 Gather 的结果 | 每个进程都有 |

## 二、AllReduce 拆成两半

All-reduce 可以拆解成两个步骤：**Reduce-scatter** 和 **All-gather**。假设有 4 张显卡（1 2 3 4），将一个模型分为 4 层（a b c d），即将梯度分为 4 部分。Reduce-scatter 实际上是在每个显卡**先聚合出 1 个层梯度之和**，再通过 **all-gather** 分配到所有显卡。

> [!note] 显存账要算清
> DDP 只做了数据并行，每张显卡其实保存的是**完整的参数 + 梯度 + 优化器状态**。

### 2.1 Ring-AllReduce 的通信量

All-reduce 最常用的实现方式是 **Ring-AllReduce**，NVIDIA 的 NCCL 通信库采用了这种算法。计算通信量时只统计发送的参数量：假设有 $N$ 个设备，模型参数总量为 $\Psi$，每个梯度块的大小为 $\frac{\Psi}{N}$，每个设备只与其相邻的设备通信。

Reduce-scatter 阶段：

- 步骤 1：显卡 a 将 a0 **发送**给显卡 b，同时**接收**显卡 d 发送的 d3
- 步骤 2：显卡 a 将 a3+d3 发送给显卡 b，同时接收显卡 d 发送的 c2+d2
- 步骤 3：显卡 a 将 a2+c2+d2 发送给显卡 b，同时接收显卡 d 发送的 b1+c1+d1

AllGather 阶段：

- 步骤 1：显卡 a 将 a1+b1+c1+d1 发送给显卡 b，显卡 b 直接做替换，同时接收显卡 d 发送的 a0+b0+c0+d0，直接做替换
- 步骤 2：显卡 a 将 a0+b0+c0+d0 发送给显卡 b，显卡 b 直接做替换，同时接收显卡 d 发送的 a3+b3+c3+d3，直接做替换
- 步骤 3：显卡 a 将 a3+b3+c3+d3 发送给显卡 b，显卡 b 直接做替换，同时接收显卡 d 发送的 a2+b2+c2+d2，直接做替换

![[Pasted image 20261111150827.png]]

*图 5：Ring-AllReduce 的两阶段——先 Reduce-scatter 聚合，再 All-gather 分发*

**结论**：单个设备的通信量与 GPU 数量 $N$ 无关，每个阶段的通信量为 $(N-1)\cdot\frac{\Psi}{N}\approx\Psi$，两阶段合计 **$2\Psi$**。

### 2.2 与 DP 的 parameter-server 通信对比

DP 采用主进程集中式通信：**主显卡 GPU0** 负责收集其他 GPU 的梯度（All Gather），执行参数更新，再将更新后的参数广播给其他 GPU（Broadcast）。GPU 0 负责接收来自其他 GPU 的梯度和发送参数，再将更新后的参数广播给 $N-1$ 个 GPU，总通信量为 $(N-1)\Psi$；其他 GPU 只发送 $\Psi$ 的梯度和接收 $\Psi$ 的参数，总通信量为 $\Psi$。

虽然所有显卡的**总通讯量相同**，但搬运相同数据量的时间却不一定相同。DDP 把通讯量均衡负载到了每一时刻的每个 Worker 上，而 DP 仅让 Server 做勤劳的搬运工。当越来越多的 GPU 分布在距离较远的机器上时，DP 的通讯时间是会增加的。

| 维度 | parameter-server（DP） | Ring-AllReduce（DDP） |
| --- | --- | --- |
| **带宽利用率** | 所有 GPU 同时与主 GPU 通信，**主 GPU 的网络带宽成为瓶颈** | 每个 GPU 只与两个相邻 GPU 通信，带宽分配更均匀 |
| **并行度** | **星型拓扑**，通信必须经过中心节点 | **环形拓扑**，通信可以并行进行 |
| **负载均衡** | 主 GPU 承担了大量计算和通信负担 | 所有 GPU **负载基本均衡** |
| **可扩展性** | GPU 数量增加时，主 GPU 的瓶颈效应更明显 | 实践中表现出更好的可扩展性 |

**为什么 DDP 选 Ring**：总通信量一样，但 Ring 把流量摊到每个 Worker、每时每刻，PS 则把流量堆在中心节点——机器越分散，这个差距越大。

## 三、分桶策略

简而言之就是在反向传播时，把需要的梯度按照一定策略分到若干个"桶"，从而**减少通信开销**、**在最大限度上做到通信和计算重叠**。

没有分桶机制的 DDP 中，每计算完一层的梯度就要进行一次梯度同步。但是**每次 All-reduce 通信的参数量越多，通信效率越高**。**梯度分桶就是将模型参数逆序插入每个桶中，每次一个桶中的所有参数的梯度都更新后，再进行 allreduce 通信。**

![[Pasted image 20261111151809.png]]

**分桶的 DDP 的迭代流程**：

1. **初始化**：初始化桶，**按照逆序把 parameters 分配到桶之中**，可以通过设置 DDP 构造函数中的参数 `bucket_cap_mb` 来**配置桶**的大小。还在构造期间注册 autograd 钩子，每个参数一个钩子。当梯度准备好时，将在向后传递期间触发这些钩子。
2. **前向传播**：每张卡分别计算其所负责数据的**前向结果**。
3. **后向传播**：从最后一层开始进行反向计算，每层得到相应的梯度。由于 DDP 做了梯度 hook，每次计算完对应的梯度后，会将梯度放到对应的"桶"里。如果桶中所有梯度都更新过，会对这个"桶"中包含的梯度做一次 All-Reduce。
4. **同步与更新**：当所有的梯度都已完成通信并合并之后，**各个进程得到了全局一致的梯度**，就可以各自进行参数更新（例如优化器 `optimizer.step()`）。

### 3.1 默认策略与优化点

PyTorch 默认的**分桶策略**会按照参数层的逆序分桶：在计算图中越"靠后"（例如网络的后几层）的梯度会先被计算出来并开始通信，从而在后向剩余部分计算梯度时，之前触发的通信能够并行进行，做到更好的 overlap。

三个可调优化点：

1. **桶大小调整**：根据模型大小、网络环境调整，避免浪费带宽或并行效率。
2. **梯度压缩和量化**：在分桶之后、All-Reduce 之前做梯度压缩和量化，降低通信量。
3. **梯度累加**：梯度**累积一定轮数后**再执行 All-Reduce，减少通信频率。

大规模训练里 DDP 与 TP、PP 如何叠加，见 [[2.4.6 Megatron-LM#5.4 PTD-P]]。
