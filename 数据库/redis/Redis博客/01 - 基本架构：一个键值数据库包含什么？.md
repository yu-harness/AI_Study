# 01 基本架构：一个键值数据库包含什么？

一个键值数据库 = **数据模型 + 操作接口 + 四个内部模块**。下面以 Redis 为主线，最简实现（SimpleKV）只作对照。

## 一、数据模型：key 差不多，value 差很多

- key 一般是 String，各家差别不大；**value 类型差别很大，选型主要看它**。
- Memcached 只有 String；Redis 有 String、哈希表、列表、集合等。**Redis 应用广，靠的就是 value 类型多。**
- value 类型同时决定两件事：能支撑什么业务，以及不同数据结构在性能和空间上的差异。

## 二、操作接口：五个动作

| 操作 | 作用 |
| --- | --- |
| `PUT` | 新写或更新一个键值对 |
| `GET` | 按 key 读 value |
| `DELETE` | 按 key 删掉整个键值对 |
| `SCAN` | 按一段 key 范围返回 value |
| `EXISTS` | 判断 key 是否存在 |

新写和更新常共用一个接口（有的库叫 `SET`），执行时按 key 是否存在走不同分支。

**接口简单是优点也是限制**：键值库做不了聚合计算，比如求多个用户年龄的均值，这类需求要交给关系型数据库。

## 三、放内存还是磁盘

| 位置 | 速度 | 风险 |
| --- | --- | --- |
| 内存 | 百 ns 级 | 断电即丢 |
| 磁盘 | ms 级 | 不丢，但整体性能被拉低 |

按场景选：缓存要快、允许丢，就放内存。Redis 和 Memcached 都是内存键值数据库。

## 四、四个内部模块

| 模块 | 负责什么 | 典型选择 |
| --- | --- | --- |
| 访问框架 | 对外提供访问入口 | 动态链接库（RocksDB）或网络框架（Redis、Memcached） |
| 索引模块 | 按 key 找到 value 的位置 | 哈希表（Redis、Memcached）、B+ 树、跳表、字典树 |
| 操作模块 | 不同操作的具体逻辑 | `GET`/`SCAN` 直接返回；`PUT` 分配内存；`DELETE` 释放内存 |
| 存储模块 | 内存分配与持久化 | 分配器影响碎片；持久化在性能与可靠性间取舍 |

### 访问框架与 I/O 模型

- **动态链接库**：链接进自己的程序直接调用，没有网络开销。
- **网络框架**：Socket Server 加协议解析，能对外提供广泛服务。

一旦走网络，就要决定连接处理、请求解析、数据存取用一个线程、多个线程还是多个进程——这就是 I/O 模型。**单线程一旦某步阻塞，整个线程都停住；多线程能互相兜住，但共享资源会产生竞争。** Redis 单线程却高性能，靠的是后续的专门设计。

### 索引

索引负责按 key 定位 value。内存键值库多用哈希表：数据本来就在内存，内存的随机访问特性正好匹配哈希表的 O(1)。

Redis 的特殊之处在于 **value 有多种类型**：通过索引找到 value 之后，还要在列表、集合这类结构内部继续找目标数据，这一步的效率取决于 value 的底层实现结构。

### 存储与持久化

- **分配器**：键值对大小不一，规模一大容易产生内存碎片，所以分配器是键值库的关键因素。
- **持久化两条路**：每个键值对都写盘（可靠但慢）；周期性把内存刷成文件（避免频繁写盘，但可能丢数据）。

## 五、Redis 相对最简实现的四处演进

| 方向 | 变化 |
| --- | --- |
| 访问 | 动态库 → 网络框架，从库变成可对外访问的基础服务 |
| 数据模型 | value 从基本类型 → 多种类型，接口随之增多（`LPUSH`/`LPOP`、`SADD`/`SREM`） |
| 持久化 | 从无 → AOF 与 RDB，各有优劣 |
| 部署 | 单机 → 高可靠集群与可扩展集群 |

## 六、还缺什么（复习清单）

- **数据结构**：跳表、Stream，缺范围查询能力
- **高可用**：主从复制、哨兵
- **横向扩展**：分片、Cluster
- **内存管理**：过期机制、淘汰策略、压缩型数据结构
- **事务**：多操作的原子性
- **辅助能力**：统计、通知、调试、元数据查询、多语言客户端
