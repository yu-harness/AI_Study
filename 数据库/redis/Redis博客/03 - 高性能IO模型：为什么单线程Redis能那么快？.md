# 03 高性能 IO 模型：单线程为什么能这么快

## 一、"单线程"到底指什么

**指的是：网络 IO 和键值对读写由一个线程完成**，这是 Redis 对外提供键值服务的主流程。

持久化、异步删除、集群数据同步这些功能，另起线程执行。所以严格说 Redis 不是单线程，"单线程高性能"是习惯叫法。

## 二、为什么选单线程

关键在**多线程的并发控制开销**。

- 线程数刚开始增加时吞吐上升，继续加就增长迟缓，甚至下降。
- 瓶颈是共享资源：多个线程改同一个结构，必须加锁保证正确。
- 粗粒度互斥锁的后果更糟——大部分线程在等锁，**并行变串行**，加了线程吞吐不涨。
- 同步原语还降低代码的可调试性和可维护性。

Redis 的选择是：**与其花钱做并发控制，不如直接省掉**。

## 三、单线程为什么快：三个因素共同作用

| 因素 | 作用 |
| --- | --- |
| **内存操作** | 大部分操作在内存完成，本身比磁盘快几个数量级 |
| **高效数据结构** | 哈希表 O(1)、跳表 O(logN)（见第 02 篇） |
| **IO 多路复用** | 一个线程并发处理大量客户端请求，这是本节重点 |

单线程能达到每秒数十万级处理能力，是三者叠加的结果，不是单靠某一条。

## 四、多路复用怎么解决阻塞

### 基本 IO 模型的六步

一次 Get 请求要走：`bind/listen` → `accept` → `recv` → `parse` → `get` → `send`。

前四步和后一步是网络 IO，`get` 是数据操作。单线程就是依次执行这六步。

### 两个阻塞点

| 阻塞点 | 什么时候卡住 |
| --- | --- |
| `accept()` | 有连接请求但一直建立不起来 |
| `recv()` | 从客户端读数据，数据一直不到 |

一旦卡住，整个线程停摆，其他客户端全部排队。

### 非阻塞模式解决"卡住"，但引出新问题

把监听套接字和已连接套接字设成非阻塞后，`accept()` 和 `recv()` 会立即返回，不再等待。

但"立即返回"意味着没人盯着这些套接字了——**总得有机制继续监听，并在有数据时通知 Redis 线程**。这就是多路复用的位置。

### select/epoll：内核替你盯着

- 内核中同时存在多个监听套接字和已连接套接字，由内核监听它们的连接和数据请求。
- 一旦有请求到达，事件被放进**事件队列**，Redis 单线程不断处理这个队列。
- 处理时调用对应的事件回调：Accept 事件走 `accept` 回调，Read 事件走 `get` 回调。

两个直接好处：

1. **不用轮询**，避免空转浪费 CPU；
2. **一个线程处理多个 IO 流**，不用为每个客户端开线程。

**医院分诊台的比喻**：分诊、测体温、登记这些准备工作如果全由医生做，医生效率极低。设了分诊台（内核监听），医生（Redis 线程）只负责诊断，效率就上来了。

不同系统有不同实现：Linux 用 `select`/`epoll`，FreeBSD 用 `kqueue`，Solaris 用 `evport`。

## 五、单线程真正的阻塞点

多路复用解决的是"等待时别浪费"，但**只要某个请求本身耗时长，后面的请求仍然要排队**。这才是生产环境要防的。

| 阻塞类型 | 为什么慢 |
| --- | --- |
| **操作 bigkey** | 写入要分配大块内存，删除要释放大块内存，都耗时 |
| **高复杂度命令** | `SORT`、`SUNION`、`ZUNIONSTORE`，或 `LRANGE key 0 -1` 这种一次取全量 |
| **大量 key 集中过期** | 过期删除在主线程执行，同一时刻集中过期会连着删很久 |
| **淘汰策略触发** | 内存到上限后，每次写入都要淘汰 key，也在主线程 |
| **AOF 刷盘 always** | 每次写都要落盘，磁盘比内存慢得多 |
| **fork 生成 RDB** | 虽然用子进程做快照，但 **fork 那一瞬间会阻塞主线程**，实例越大阻塞越久 |

**对应的缓解手段**：

- 业务侧规避：不用 bigkey、不用 O(N) 大范围命令、错开过期时间。
- 服务侧优化：Redis 4.0 的 **lazy-free** 把 bigkey 的释放放到异步线程，减少主线程耗时。

## 六、6.0 的多线程改了什么

**只改了网络读写，没改命令执行。**

- 多线程负责读 socket、解析命令、写回结果；**每条命令的执行仍然是单线程顺序执行**。
- 目的有两个：利用多核；分摊同步 IO 读写的开销（`read`/`write` 系统调用本身耗时）。
- IO 线程要么同时读、要么同时写，不会同时读写，主线程要等 IO 线程结束。
- 默认不开启，需要手动配置。

**为什么需要它**：并发量很大时，单线程同步读写客户端数据成为瓶颈——10 个连接的吞吐和 1000 个连接的吞吐差别明显。这时候瓶颈不在命令执行，在网络 IO。

## 七、一句话总结

**单线程避免了锁竞争，多路复用避免了 IO 等待，两者配合让一个线程能扛住大量连接；但代价是任何一个慢请求都会拖住所有人，所以真正的性能优化是消灭慢命令，不是加线程。**
