**主从库模式下的故障影响**
- 从库故障：客户端可以继续向主库或其他从库发送请求。
- **主库故障**：从库没有主库可以复制数据；纯读业务还能由从库继续提供服务，但**写操作**按读写分离要求必须由主库执行，此时没有实例能处理写请求。
![[Pasted image 20261016230012.png|500]]

**主库故障后要做的事**
- 做法：运行一个新主库，把一个从库切换为主库。
- 涉及的三个问题：
  1. 主库真的挂了吗？
  2. 该选择哪个从库作为主库？
  3. 怎么把新主库的相关信息通知给从库和客户端？

**哨兵机制**
- Redis 主从集群中实现主从库自动切换的关键机制，负责解决上述三个问题。

## 哨兵机制的基本流程
**哨兵是什么**
- 一个运行在特殊模式下的 Redis 进程，与主从库实例同时运行。
- 负责三个任务：监控、选主、通知。

**监控**
- 周期性给所有主从库发送 PING 命令，检测是否在线。
- 从库未在规定时间内响应 → 标记为"下线状态"。
- 主库未在规定时间内响应 → 判定主库下线，启动自动切换主库的流程。
**选主**
- 从多个从库中按一定规则选出新主库，集群里随即有了新主库。

**通知**
- 把新主库的连接信息发给其他从库，让它们执行 `replicaof` 与新主库建立连接并复制数据。
- 把新主库的连接信息通知客户端，让请求发到新主库上。

![[Pasted image 20261016230124.png||500]]

**需要做决策的任务**
- 监控：判断主库是否处于下线状态。
- 选主：决定选择哪个从库实例作为主库。
- 通知：不涉及决策逻辑，把新主库信息发给从库和客户端即可。
**主库的下线判断**
- 分两种：主观下线、客观下线。

## 主观下线和客观下线

**主观下线**
- 哨兵用 PING 命令检测自己与主、从库的网络连接：响应超时，就把实例标记为"主观下线"。
- 检测对象是从库：直接标记即可，从库下线影响不大，集群对外服务不会间断。
- 检测对象是**主库**：**不能直接标记并开启主从切换**，因为可能误判；切换（选主、通知、从库重新同步）本身有计算和通信开销。

**误判与减少办法**
- 误判：主库实际没有下线，哨兵误以为它下线。多发生在集群网络压力大、网络拥塞或主库本身压力大时。
- 办法：哨兵以多实例组成集群方式部署（**哨兵集群**）。**多个哨兵**一起判断，单个哨兵自身网络状况不好也不至于误判；多个哨兵同时不稳定的概率较小，误判率降低。

**客观下线**
- 判定原则是少数服从多数：大多数哨兵都判断主库"主观下线"后，主库才被标记为"客观下线"，进而触发主从切换流程。
- 示例（1 主库、3 从库、3 哨兵）：只有 1 个哨兵判主观下线时，主库仍算上线；2 个哨兵判主观下线时，即使第 3 个判上线，主库也被标记为客观下线。

![[Pasted image 20261016230252.png|500]]

**客观下线的判定标准**
- N 个哨兵实例时，要有 N/2 + 1 个实例判断主库"主观下线"，才能最终判定为**"客观下线**"，以减少误判和无谓的主从切换。
- 判定所需的实例数量可以由 Redis 管理员自行设定。

主库确认下线后，进入下一个决策过程：从多个从库中选出一个作为新主库。

## 如何选定新主库？

![[Pasted image 20261016230412.png||500]]

**选主过程：筛选 + 打分**
- 步骤：先按**筛选条件**去掉不符合条件的从库，再按规则给剩下的从库逐个打分，得分最高的选为新主库。

**筛选条件**
- 从库仍然在线运行。
- 还要判断从库之前的网络连接状态：在线只代表现状良好，网络状况不好、很快又会故障的从库不适合做新主库。
- 判断方式：`down-after-milliseconds × 10`。`down-after-milliseconds` 是认定主从库断连的最大连接超时时间，在该时长内主从节点没通过网络联系上就算一次断连；断连次数超过 10 次，说明该从库网络状况不好，筛掉。



**打分：依次进行三轮**
- 规则：某一轮中出现了得分最高的从库，它就是新主库，选主结束；没有就进入下一轮。
- 第一轮（优先级）：用 `slave-priority` 给从库设置不同优先级，例如给内存配置较高的从库设置高优先级；优先级最高的从库当选。
- 第二轮（复制进度）：`slave_repl_offset` 最接近旧主库 `master_repl_offset` 的从库得分最高，因为它的数据最新。示例：旧主库 offset 为 1000，三个从库分别为 950、990、900，选 990 的从库。
- 第三轮（ID 号）：优先级和复制进度都相同时，ID 号最小的从库得分最高。

**汇总流程**

- 先按**在线状态、网络状态筛选过滤掉不符合要求的从**库；再依次按优先级、复制进度、ID 号打分；出现得分最高的从库即选为新主库。

## 小结
**本讲小结**
- 哨兵机制自动完成三大功能，实现**主从库自动切换**，降低运维开销：
  1. 监控主库运行状态，判断是否客观下线；
  2. 主库客观下线后选取新主库；
  3. 选出新主库后通知从库和客户端。
- 数据同步是数据可靠的基础，主库故障时的自动主从切换是服务不间断的关键支撑。
- 部署建议：通常采用多实例部署，按"少数服从多数"判断客观下线。常规部署三个哨兵，其中两个认定主观下线就可以开始切换；想进一步提升判断准确率可以增加到五个。

**留言中的疑问**

- 主库已经挂了，`master_repl_offset` 从哪里获取？哨兵如何比较各从库的复制进度？
- 比较复制进度时，是从库之间互相比较，还是与旧主库的 `master_repl_offset` 比较？
- 选出新主库后，其他从库与新主库同步时是否需要先做一次全量同步？
- Redis 实例 ID 是根据什么生成的？
- 哨兵实例之间如何互相感知，启动时需要指定其他哨兵的 IP 吗？
- 优先级高的从库若复制进度不是最接近，会不会选出并非最优的主库？
- ID 号最小的从库得分最高，依据是什么？

**作者回复（Kaito）**

- 切换期间：读请求可以在从库正常执行；主库挂了、新主库还没选出期间，写请求会失败，失败时长 = 哨兵切换主从的时间 + 客户端感知新主库的时间。
- 避免业务感知异常：客户端把写失败的请求先缓存起来或写入消息队列，切换完成后发给新主库；只适合对写入返回值不敏感的业务，需要业务层适配；切换时间过长会让缓存的请求过多、重放时间变长。
- `down-after-milliseconds`：配置越短，哨兵越敏感，可能因网络拥塞而在主库正常时发起切换；配置越长越保守，可以减少误判，但主库真正故障时写失败的时间更久。
- 客户端感知主库变更：① 哨兵把新主库地址写入 pubsub 的 switch-master，客户端订阅这个通道即可感知；② 客户端也要支持主动获取最新地址（`sentinel get-master-addr-by-name`），不要固定主从库地址；一般 Redis SDK 已经封装好这些逻辑，分片集群模式下可以放在 proxy 层实现（例如 Codis）。
- 哨兵集群中有实例挂掉：只要集群中大多数节点状态正常，集群依旧可以对外提供服务。
- 由谁执行主从切换：先选出一个"哨兵领导者"，由它完成主从切换。选举方式类似 Raft：每个哨兵设置随机超时时间，超时后请求其他哨兵为自己投票，其他节点对收到的第一个请求投票；首先达到多数选票的哨兵当选，没有达到多数就重新选举。
