**场景与第一个方案**
- 需求：保存 5000 万个键值对，每个约 512B，共约 25GB；用云主机部署 Redis。
- 方案：选一台 32GB 内存的云主机（25GB 数据加 7GB 余量），并用 RDB 做持久化。
**方案暴露的问题**
- 现象：Redis 响应有时非常慢；用 INFO 查看 `latest_fork_usec`（最近一次 fork 的耗时），值快到秒级。
- 原因：RDB 持久化时 Redis 要 fork 子进程，fork 的用时与数据量正相关，且 fork 执行时会阻塞主线程；数据量越大，阻塞时间越长。25GB 数据做持久化时，fork 阻塞主线程，导致响应变慢。
**切片集群**
- 做法：启动多个 Redis 实例组成一个集群，按一定规则把数据划分成多份，每一份用一个实例保存。
- 示例：把 25GB 数据平均分成 5 份，用 5 个实例保存，每个实例只保存 5GB。
- 优点：可以保存大量数据，对主线程的阻塞影响较小。

![[Pasted image 20261016232619.png|500]]

**切片集群为什么能避免响应变慢**
- 每个实例只负责约 5GB 数据，生成 RDB 时 fork 子进程对主线程的阻塞时间短了很多。
- 结果：既能保存 25GB 数据，又避免了单实例数据量大时 fork 阻塞主线程导致的响应突然变慢。
- 随着业务规模扩展，保存大量数据无法避免，切片集群是合适的解决方案。

## 如何保存更多数据？
**应对数据量增多的两种方案**
- **纵向扩展**（scale up）：升级单个实例的资源配置，包括增加内存容量、增加磁盘容量、使用更高配置的 CPU。示例：内存从 8GB 增加到 24GB，磁盘从 50GB 增加到 150GB。
- **横向扩展**（scale out）：横向增加实例个数。示例：原来用 1 个 8GB 内存、50GB 磁盘的实例，改成三个相同配置的实例。

![[Pasted image 20261016232746.png|500]]

**纵向扩展**
- 好处：**实施简单、直接**。
- 问题一：用 RDB 持久化时，数据量增加，需要的内存也增加，主线程 fork 子进程时**可能阻塞**（就是前面 25GB 例子的情况）。如果不要求持久化保存数据，纵向扩展会是不错的选择。
- 问题二：**受硬件和成本的限制**——内存从 32GB 扩到 64GB 还算容易，要扩到 1TB 就会面临硬件容量和成本上的限制。

**横向扩展**

- 扩展性更好：想保存更多数据只需要**增加实例个数**，不用担心单个实例的硬件和成本限制。
- 面向**百万、千万级别的用户规模**时，横向扩展的切片集群是很好的选择。

**切片集群要解决的两大问题**
- 数据切片后，在多个实例之间**如何分布**？
- 客户端怎么确定想访问的数据在**哪个实例**上？

## 数据切片和实例的对应分布关系

**切片集群与 Redis Cluster**
- 切片集群是**保存大量数据的通用机制**，可以有不同实现方案。
- Redis 3.0 之前官方没有提供具体方案；从 3.0 开始官方提供 **Redis Cluster** 方案，其中规定了数据与实例的对应规则。
**哈希槽（Slot）**
- Redis Cluster 采用**哈希槽**来处理数据与实例之间的映射关系：一个切片集群共有 **16384 个哈希槽**，类似数据分区，每个键值对都会根据 key 映射到其中一个槽。
- 映射分两大步：① 按 key 用 **CRC16 算法**计算一个 16 bit 的值；② 该值对 **16384 取模**，得到 0～16383 范围内的模数，每个模数代表一个编号的哈希槽。
**哈希槽如何分配到实例**
- `cluster create` 创建集群：Redis 自动把槽**平均分布**在集群实例上，N 个实例时每个实例 16384/N 个槽。
- 手动方式：用 `cluster meet` 建立实例间的连接形成集群，再用 `cluster addslots` 指定每个实例上的哈希槽个数。
- 适用场景：实例内存配置不一样时，槽均分会让内存小的实例承担更大的容量压力，可以用 `cluster addslots` 按各实例的资源配置手动分配。

![[Pasted image 20261016232911.png|500]]

**哈希槽分配示例（3 个实例、假设 5 个槽）**
- 实例1 保存槽 0 和 1，实例2 保存槽 2 和 3，实例3 保存槽 4：
```
redis-cli -h 172.16.19.3 -p 6379 cluster addslots 0,1
redis-cli -h 172.16.19.4 -p 6379 cluster addslots 2,3
redis-cli -h 172.16.19.5 -p 6379 cluster addslots 4
```

- 运行过程中：key1、key2 计算完 CRC16 值后，对哈希槽总个数 5 取模，再根据各自的模数结果映射到对应的实例（实例1 和实例3）。
- 提醒：手动分配哈希槽时，**需要把 16384 个槽都分配完，否则 Redis 集群无法正常工作**。

至此，切片集群完成了数据到哈希槽、哈希槽再到实例的分配。接下来的问题是：客户端怎么知道要访问的数据在哪个实例上？

## 客户端如何定位数据？

**客户端如何定位数据所在的实例**

- 哈希槽可以通过计算得到（客户端发请求时即可计算），但要进一步定位到实例，还需要知道哈希槽分布在哪个实例上。
- 客户端和集群实例建立连接后，实例就会把**哈希槽的分配信息**发给客户端。
- 实例之间会把自己的哈希槽信息发给和它相连的其他实例，完成**哈希槽分配信息的扩散**；相互连接之后，每个实例都掌握了所有哈希槽的映射关系，所以客户端访问任何一个实例都能拿到完整信息。
- 客户端把哈希槽信息**缓存在本地**，请求键值对时先计算键对应的哈希槽，再给相应的实例发送请求。

**对应关系会变化**

- 常见变化有两种：① 实例新增或删除，Redis 需要重新分配哈希槽；② 为了负载均衡，把哈希槽在所有实例上重新分布一遍。
- 实例之间可以互相传递消息获取最新分配信息，但**客户端无法主动感知**这些变化，本地缓存的分配信息就会与最新分配不一致。

**重定向机制（MOVED）**

- 重定向：客户端给一个实例发送数据读写操作，这个实例上并没有相应的数据，客户端要再给一个新实例发送操作命令。
- 实例上没有该键值对映射的哈希槽时，会返回 `MOVED` 命令响应，其中包含新实例的访问地址：

```
GET hello:key
(error) MOVED 13320 172.16.19.5:6379
```

- 上面的响应表示：键值对所在的哈希槽 13320 实际在 172.16.19.5 这个实例上，客户端可以直接连过去发送请求。
- 图示流程：负载均衡使 Slot 2 的数据从实例2 迁移到实例3，客户端缓存仍记录"Slot 2 在实例2"，于是把命令发给实例2；实例2 返回 MOVED 告知 Slot 2 的最新位置；客户端改向实例3 发送请求，同时**更新本地缓存**里的对应关系。

![[Pasted image 20261016233103.png|500]]

**数据部分迁移时的 ASK 报错**
- 迁移可能只完成一部分：Slot 2 的数据比较多时，客户端向实例2 发送请求，但此时只有一部分数据迁到了实例3，还有部分留在实例2。
- 这种部分完成的情况下，客户端会收到 ASK 报错：

```
GET hello:key
(error) ASK 13320 172.16.19.5:6379
```

- 处理步骤：先给 172.16.19.5 发送 `ASKING` 命令（让这个实例允许执行客户端接下来发送的命令），再向它发送 GET 命令读取数据。

**ASK 的两层含义**

- 第一，表明 Slot 数据**还在迁移中**。
- 第二，把客户端所请求数据的**最新实例地址**返回给客户端。
- 示例：Slot 2 正在从实例2 迁往实例3，key1、key2 已经迁过去，key3、key4 还在实例2；客户端向实例2 请求 key2，就会收到实例2 返回的 ASK，随后需要先给实例3 发送 `ASKING`，再发送操作命令。

![[Pasted image 20261016233231.png|500]]

**ASK 与 MOVED 的区别**
- **ASK 命令不会更新客户端缓存的哈希槽分配信息**：客户端再次请求 Slot 2 中的数据时，仍然会把请求发给实例2。
- ASK 的作用只是让客户端能给新实例发送**一次**请求；MOVED 则会更改本地缓存，让**后续所有命令**都发往新实例。
## 小结

**本讲小结**
- 纵向扩展（增加内存）简单直接，但会造成数据库内存过大、性能变慢。
- **切片集群**提供横向扩展：使用多个实例，每个实例配置一定数量的哈希槽；数据经过键的哈希值映射到哈希槽，再分散保存到不同实例上。好处是**扩展性好**，数据量再大也能应对。
- 实例增减、或为负载均衡进行数据重新分布时，哈希槽与实例的映射会变化，客户端请求时会收到报错；掌握 **MOVED** 和 **ASK** 两个响应命令，就能应对这类报错。

**后续**
- Redis 3.0 之前官方没有切片集群方案，业界已有基于客户端分区的 **ShardedJedis**、基于代理的 **Codis**、**Twemproxy** 等方案；它们在支撑的集群实例规模、集群稳定性、客户端友好性方面各有优势，后面的课程会专门讲。

**每课一问**

- Redis Cluster 用哈希槽分配数据（key 做 CRC 计算再映射到槽），好处是什么？为什么不直接用一张表记录键值对与实例的对应关系？

**作者回复（Kaito）：为什么不直接用映射表**
- key 数量无法预估：直接记录每个 key 与实例的映射关系，映射表会非常庞大，无论存在服务端还是客户端都占用非常大的内存空间。
- Redis Cluster 采用**无中心化模式**（客户端与服务端直连）：客户端访问的 key 不在当前节点时，节点要有纠正路由的能力（MOVED 响应），这要求节点之间互相交换路由表、每个节点保存完整的路由关系。如果存的是 key 与实例的对应关系，节点之间交换的信息也会非常庞大，且每个节点都要额外存储其他节点的路由表，内存占用过大。
- 集群扩容、缩容、数据均衡时会发生数据迁移，迁移时需要修改每个 key 的映射关系，**维护成本高**。
- 中间加一层哈希槽，把数据与节点**解耦**：key 经过 Hash 计算只需关心映射到哪个槽，再通过槽与节点的映射表找节点；映射表很小，便于客户端和服务端保存、节点之间交换信息也轻量；数据分布更均匀；扩缩容与均衡以哈希槽为基本单位操作，简化维护管理。

**补充：集群管理的两个核心问题**

- **请求路由**：Redis Cluster 在每个节点记录完整映射关系，并发给客户端缓存，客户端与服务端配合完成路由（业务需要升级为集群版 SDK）；Twemproxy、Codis 等中心化方案在 Proxy 层做路由，客户端不用更换 SDK，但 Proxy 会带来性能损耗。
- **数据迁移**：Twemproxy 不支持在线扩容（扩容需要停机重新分配数据）；Redis Cluster 和 Codis 支持在线扩容。Redis Cluster 的数据迁移是同步的，迁移一个 key 会同时阻塞源节点和目标节点；Codis 提供异步迁移，速度更快、对性能影响更小。
