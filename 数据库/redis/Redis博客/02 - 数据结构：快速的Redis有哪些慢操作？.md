# 02 数据结构：Redis 快在哪，慢在哪

Redis 快，一半靠内存（访问本身快），一半靠数据结构（键值对按结构组织，操作即增删改查）。

## 一、两层结构：数据类型 ≠ 底层实现

- **String、List、Hash、Set、Sorted Set 只是「值的保存形式」**，不是底层结构。
- 底层共 6 种：简单动态字符串（SDS）、双向链表、压缩列表、哈希表、跳表、整数数组。
- String 只有一种实现（SDS）；List、Hash、Set、ZSet 各有两种，统称**集合类型**——一个键对应一整个集合。

所以看 Redis 性能要看两层：键值之间怎么组织，值内部怎么组织。

## 二、键和值之间：全局哈希表

Redis 用一个哈希表保存所有键值对，称为**全局哈希表**。

- 哈希表是数组，每个元素叫哈希桶，桶里放 entry。
- **entry 存的是 `*key` 和 `*value` 两个指针，不是值本身**。所以值即使是集合，也能通过指针找到。
- 查找只需要算一次哈希 → 定位桶 → 取 entry，**复杂度 O(1)，与数据量无关**：10 万键和 100 万键都是一次计算。

## 三、哈希冲突与渐进式 rehash

**冲突从哪来**：桶的数量少于 key 数量，不同 key 可能落到同一个桶。

**Redis 的解法是链式哈希**：同一个桶里的多个 entry 用 `*next` 指针串成链表。

**问题**：冲突链越长，链上查找越慢，对追求"快"的 Redis 不可接受。

**因此要 rehash**：增加桶数量，把 entry 分散到更多桶。Redis 维护两张全局哈希表：

1. 给表 1 分配更大空间（通常是两倍）
2. 把表 1 的数据重新映射到表 2
3. 释放表 1

**第 2 步如果一次性迁移，会阻塞主线程**，这期间无法服务其他请求。

**所以用渐进式 rehash**：迁移期间照常处理请求，每处理一个请求，就顺带把表 1 中下一个索引位置的所有 entry 搬过去。把一次大拷贝摊到多次请求里，避免卡顿。

## 四、集合的底层结构与复杂度

集合操作分两步：先通过全局哈希表找到桶，再在集合内部增删改查。

| 结构 | 特点 | 复杂度 |
| --- | --- | --- |
| 整数数组 | 顺序读写，按下标访问 | O(N) |
| 双向链表 | 顺序读写，按指针逐个走 | O(N) |
| 哈希表 | 按 key 定位 | O(1) |
| 压缩列表 | 类似数组，连续存储；表头三字段记录总长、尾偏移、entry 数，表尾 `zlend` 标记结束 | 首尾 O(1)，其他 O(N) |
| 跳表 | 链表加多级索引，靠跳转定位 | O(logN) |

**跳表为什么快**：有序链表只能逐个走。加一级索引（每两个元素抽一个），查找次数减半；再加二级索引，继续减半。查找过程就是在多级索引上跳，所以叫"跳表"。

## 五、复杂度口诀：四句话

| 口诀 | 含义 | 例子 |
| --- | --- | --- |
| 单元素操作是基础 | 单个元素的增删改查，复杂度由底层结构决定 | `HGET`/`HSET`/`HDEL` 在哈希表上是 O(1) |
| 范围操作非常耗时 | 遍历整个集合或一段范围，一般 O(N) | `HGETALL`、`SMEMBERS`、`LRANGE`、`ZRANGE` |
| 统计操作通常高效 | 结构里专门记了元素个数 | `LLEN`、`SCARD` 都是 O(1) |
| 例外情况只有几个 | 能靠偏移量直接定位的头尾操作 | `LPOP`/`RPOP`/`LPUSH`/`RPUSH` 是 O(1) |

**两个补充**：

- 批量操作复杂度随元素个数走：`HMSET` 写 M 个元素，复杂度是 O(M)，不是 O(1)。
- 范围操作用 **SCAN 系列**（`HSCAN`/`SSCAN`/`ZSCAN`）替代，渐进式遍历、每次只返回一部分，避免一次性返回全部导致阻塞。

## 六、为什么还要用紧凑结构（课后问的核心答案）

整数数组和压缩列表在查找复杂度上并不占优，Redis 仍然用它们，原因有三：

1. **省内存**：两者都是紧凑结构，比链表占用内存少。Redis 是内存数据库，内存利用率是硬约束。
2. **对 CPU 缓存友好**：元素连续排列，能利用 CPU 高速缓存，实际执行速度比复杂度看起来更快。
3. **减少碎片**：一次分配一块连续内存，避免链表节点分散带来的碎片。

**策略是分档**：元素少时用紧凑结构（省内存、访问还快）；元素超过阈值后，为避免查询复杂度太高，转成哈希表或跳表。**空间和时间的权衡，按数据量切换。**

## 七、小结：快在哪，慢在哪

**快**：

- `String`、`Hash`、`Set` 的操作基本由 O(1) 的哈希表决定
- `ZSet` 用 O(logN) 的跳表

**慢**：

- 范围操作要遍历底层结构，一般 O(N)
- `List` 的两种实现（双向链表、压缩列表）复杂度都是 O(N)

**两条实践建议**：

- 用 `SCAN` 替代 `HGETALL` 这类全量遍历，避免在 Redis 内部做费时操作。
- `List` 的 POP/PUSH 是 O(1)，适合做 FIFO 队列，不要当成可随机读写的集合用。

**方法论**：操作太多记不住，掌握数据结构原理就能反推复杂度，不用死记。
