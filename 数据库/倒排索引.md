# 倒排索引

倒排索引是 **「词 → 文档编号」的目录表**，把「哪些文档含这个词」从扫全表变成查一次表。写入慢、占空间，换来查询毫秒级。

- **正排**：文档 → 内容，找词只能全表扫描。
- **倒排**：词 → 文档编号，像书末索引页。

---

## 一、本质（三行说清）

```text
doc1: 苹果 手机      建索引：分词 → 拆成 (词, 文档) 对 → 按词归并
doc2: 苹果 价格
doc3: 香蕉 价格
```

归并结果：

| 词 | 出现在 |
| --- | --- |
| 苹果 | doc1, doc2 |
| 手机 | doc1 |
| 价格 | doc2, doc3 |
| 香蕉 | doc3 |

右边一列就是 **posting list**。查询「苹果 价格」= 分词 → 查词典 → 取两个列表 → 求交集 `{doc2}` → 打分排序。快的原因只有一个：**只对整数列表做集合运算，不碰原文**。

---

## 二、ES 里的两个部件

### 2.1 词典：FST（负责「词在哪」）

词典存所有出现过的词，按字典序排列。几千万个词直接存字符串要几十 GB，所以 Lucene 用 **FST（有限状态转换器）** 按**公共前缀**压缩：

```text
cat / car / cart   →   c→a→( t / r→t )
```

三个词共享 `ca` 一条路径，不存三份字符串。三个收益：内存省一个量级、查找只需走一遍字符（$O(\text{词长})$）、天然支持前缀查询（走到 `ca` 就能拎出所有 `ca*`）。

### 2.2 倒排列表：docID + tf + pos（负责「文档里什么情况」）

```text
订单 → [(doc1, tf=1, pos=[0]), (doc5, tf=3, pos=[2,7,11])]
```

| 字段 | 含义 | 谁在用 |
| --- | --- | --- |
| `docID` | 哪篇文档 | 集合运算（交/并）、增量编码压缩 |
| `tf` | 该词在文档出现几次 | **BM25 打分**，出现越多越相关（收益递减） |
| `pos` | 出现在第几个位置 | **短语查询**（「订单 金额」要求相邻）、高亮 |

---

## 三、分词与 mapping：不是自动切，而是按字段配

ES 不会「拿到文档自己猜怎么切」，严格按 **mapping** 执行。同一个索引里三个字段可以三种切法：

| 配置 | 行为 | 适合 |
| --- | --- | --- |
| `text` + `standard` | 按规则切词，中文切成**单字** | 英文正文 |
| `text` + `ik_max_word` | 中文细粒度分词 | 中文描述、同义词 |
| `keyword` | **完全不切**，整串当一个词 | 编码 `'021'`、ID、枚举 code |
| `keyword` + `normalizer` | 不切但统一小写/去符号 | 大小写不敏感的唯一值 |

一个字段可以同时有两种形态：

```json
"name": {
  "type": "text",
  "analyzer": "ik_max_word",
  "fields": { "raw": { "type": "keyword" } }
}
```

`name` 分词做全文检索，`name.raw` 不分词做精确过滤与聚合。

**写入与查询可以用不同分词器**：

| 参数 | 作用 | 常见组合 |
| --- | --- | --- |
| `analyzer` | 建索引时怎么切 | `ik_max_word`（切细，召回高） |
| `search_analyzer` | 查询时怎么切 | `ik_smart`（切粗，精度高） |

**不写 mapping 的坑**：ES 会做 dynamic mapping，字符串自动变成 `text` + `keyword` 两个子字段，`text` 用 `standard` 分词器。中文因此被切成单字——「上海市」变成 上/海/市，召回质量很差。中文场景必须显式配 IK，或把枚举值字段设为 `keyword`。

## 四、打分：BM25

ES 5.x 起默认相似度就是 **BM25**，取代了老的 TF-IDF：

$$
\text{score}(D,Q)=\sum_{t\in Q}\text{IDF}(t)\cdot\frac{f(t,D)\cdot(k_1+1)}{f(t,D)+k_1\left(1-b+b\cdot\frac{|D|}{\text{avgdl}}\right)}
$$

| 因子 | 含义 | 直觉 |
| --- | --- | --- |
| $\text{IDF}(t)$ | 词的稀有度 | 「退货率」只在一张表出现，权重大；「金额」出现在五张表，权重小 |
| $f(t,D)$ | 词频 | 出现越多越相关，但被 $k_1$ 压住上限 |
| $\frac{\vert D\vert }{\text{avgdl}}$ | 长度归一化 | 字段多的大表天然容易命中，要打折 |

**两个可调参数**（比 TF-IDF 多出来的控制点）：

| 参数 | 含义 | 调大的效果 |
| --- | --- | --- |
| $k_1$（默认 1.2） | 词频饱和点 | 越大越晚饱和，长文档里重复词更能加分 |
| $b$（默认 0.75） | 长度归一化强度 | $b=0$ 不归一化，$b=1$ 完全归一化 |

```json
"similarity": { "my_bm25": { "type": "BM25", "k1": 1.5, "b": 0.6 } }
```

字段级还能换成 `boolean`（只看有没有出现）或 `classic`（老 TF-IDF）。

**BM25 相比 TF-IDF 改了两件事**：词频**饱和**（出现 10 次不该是 1 次的 10 倍分）与**长度归一化**（避免长文档霸榜）。

## 五、代价在写入侧

| 操作 | 代价 |
| --- | --- |
| 读 | 毫秒级，只碰倒排列表 |
| 写 | 新增一条要往几十个词的 posting list 插入，顺序维护成本高 |
| 删 | 不能摘节点，否则列表断裂；用「标记删除 + 后台合并」 |
| 空间 | 索引体积可能接近原始数据 |

ES 用**分段（segment）**缓解写入：新文档先进内存 buffer 和 translog，每秒 refresh 出一个**不可变小段**（自带倒排索引），查询时并行查所有段再归并，段多了后台 merge。代价是删除只打标记（`.liv`），空间要等 merge 才释放。

由此得到三个常考结论：

1. 写完 **1 秒内搜不到**（near real-time），不是没落盘，是还没 refresh
2. **更新 = 标记旧文档删除 + 插入新文档**，比 insert 贵
3. **段越多查询越慢**，因为要归并的结果集变大

## 六、选型：什么时候用什么

| 类别 | 代表 | 适合 |
| --- | --- | --- |
| 搜索引擎 | **Elasticsearch**、OpenSearch、Solr | 中文分词、模糊匹配、高亮、聚合、横向扩展 |
| 底层库 | **Apache Lucene**、Tantivy（Rust）、Bleve（Go） | 嵌进服务，不想维护集群 |
| 关系库内置 | MySQL `FULLTEXT`、**PostgreSQL `tsvector` + GIN** | 数据已在库里，只做简单过滤 |
| 嵌入式 | **SQLite FTS5** | 桌面端、单机应用，零运维 |
| 内存实现 | **`rank_bm25`**、`bm25s` | 几百到几万条，启动时建索引 |
| 图数据库 | **Neo4j fulltext index**（底层同为 Lucene） | 图里做属性全文检索 |

三个判断点：**数据量**（几千条以内别上 ES）、**要不要中文分词与模糊匹配**、**要不要高亮/聚合/多副本**。

## 七、与 Text2SQL 项目的关系

| 用途 | 实现 | 为什么这么选 |
| --- | --- | --- |
| 表级召回 | `rank_bm25.BM25Okapi` | 表只有几十上百张，内存建索引几毫秒 |
| 值映射（上海 → `'021'`） | Elasticsearch | 枚举值几十万，需要精确 + 前缀 + 同义词 |

表级召回是 BM25 与 BGE-M3 各取 Top-$2k$，用 RRF 按名次融合取 Top-10。值映射之所以不用向量：向量会把「上海」和「上饶」算到 0.85 相似，WHERE 条件就写错了；倒排是精确匹配，同义词还能显式配置。

## 八、面试问法

1. **倒排与正排的区别**：正排文档到内容，倒排词到文档列表；前者适合按主键取整条记录，后者适合按关键词找文档。
2. **为什么查询快**：只对整数列表做集合运算，不扫原文。
3. **词典怎么存的**：FST 按公共前缀压缩，省内存、$O(\text{词长})$ 查找、支持前缀查询。
4. **posting list 里有什么**：docID（集合运算）、tf（BM25 打分）、pos（短语查询与高亮）。
5. **BM25 比 TF-IDF 强在哪**：词频饱和 $k_1$ + 长度归一化 $b$，避免长文档与高频词无限加分。
6. **ES 分词是自动的吗**：不是，按字段 mapping 配。`text` 分词、`keyword` 不分词，中文必须显式配 IK，否则 `standard` 会切成单字。
7. **为什么写入慢**：倒排列表需顺序维护，ES 用不可变 segment 缓解，代价是删除只打标记、空间延迟释放。
8. **BM25 与向量怎么选**：关键词、代号、枚举值用 BM25/倒排；同义改写、口语表达用向量；两者互补，用 RRF 融合。

---

## 九、一句话总结

倒排索引是「词 → 文档编号」的目录表，词典用 FST 压缩、列表带 tf 与位置；分词由 mapping 决定而非自动；BM25 在列表上按稀有度、词频饱和、长度归一化打分；规模小用内存库，规模大用 Elasticsearch。
