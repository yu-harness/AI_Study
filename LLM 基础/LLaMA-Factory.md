# LLaMA-Factory 学习笔记

> 一句话定位：把「数据 → 训练 → 评测 → 导出 → 部署」串成一条流水线的一站式微调框架，用配置文件代替手写训练脚本。

---

## 一、是什么与核心定位

LLaMA-Factory 是一个开源微调框架，核心价值是**把训练流程标准化**：同一套配置能换模型、换阶段、换微调方式，不需要为每个模型重写训练代码。

**支持的训练阶段**

| 阶段               | 用途               | 数据形态        |
| ---------------- | ---------------- | ----------- |
| SFT              | 指令微调，教模型「怎么回答」   | 问题 + 标准回答   |
| DPO / ORPO / KTO | 偏好对齐，教模型「哪个回答更好」 | 好回答 + 差回答成对 |
| RM               | 训练奖励模型           | 打分数据        |
| PPO              | 强化学习             | 奖励模型 + 提示词  |

**支持的模型**：主流开源底座基本都覆盖——Qwen、Llama、Baichuan、ChatGLM、Mistral、DeepSeek 等。支持的方式是每个模型家族配一个「对话模板」，而不是为每个模型改代码。

**它不做什么**：不做数据标注、不做推理优化、不做业务逻辑。它只管训练这一段。

---

## 二、核心工作流与关键配置

整体链路：**准备数据 → 选模板 → 选微调方式 → 调超参 → 训练 → 评测 → 导出**

### 2.1 数据准备与 `dataset_info.json`

数据文件本身只是一个 JSONL，每行一条样本。**但框架不知道你的字段叫什么**，所以要用 `dataset_info.json` 做映射。

| 要解决的问题        | 对应配置                                               |
| ------------- | -------------------------------------------------- |
| 数据文件叫什么       | `file_name`                                        |
| 用哪种格式解析       | `formatting`：`alpaca` 或 `sharegpt`                 |
| 哪个字段是消息列表     | `columns` → `messages`                             |
| 哪个字段是角色、哪个是内容 | `tags` → `role_tag`、`content_tag`                  |
| 角色值怎么对应       | `user_tag`、`assistant_tag`、`system_tag`、`tool_tag` |

**为什么必须配这一层**：不同来源的数据字段命名五花八门（`conversations` / `messages` / `instruction+output`），框架不可能内置所有方言。多这一层映射，换来的是「任何格式都能接入」。

**两种主流格式的区别**：

- `alpaca`：单轮，`instruction` + `input` + `output` 三个字段，简单但不支持多轮
- `sharegpt`：`messages` 数组，支持多轮、支持 system 和 tool 角色，**做 Agent 或工具调用必须用它**

### 2.2 Chat Template

`template` 决定样本怎么拼成模型认识的字符串——BOS/EOS 放哪、角色标记长什么样、特殊 token 怎么加。

**为什么模板错了训练就废**：模型在预训练时见过固定的对话格式，微调时必须用同一种。模板不匹配，等于用错格式教它，模型会学到一堆错位的 token 边界，表现为**loss 能降但回答混乱**。

常见取值（用模型家族名，如 `qwen`、`llama3`），选之前先确认底座训练时用的格式。

### 2.3 微调方式

| 方式         | 训练什么             | 显存          | 适用          |
| ---------- | ---------------- | ----------- | ----------- |
| **全参**     | 全部参数             | 最高，14B 需要多卡 | 数据量大、要改模型能力 |
| **LoRA**   | 低秩适配器            | 低，单卡可跑      | **绝大多数场景**  |
| **QLoRA**  | 4bit 量化基座 + LoRA | 最低          | 显存紧张、单卡跑大模型 |
| **Freeze** | 只训部分层            | 较低          | 简单场景，效果有限   |

**为什么默认选 LoRA**：基座能力已经够用，缺的是领域适配。LoRA 只训 1% 左右的参数，基座冻结不会训坏，适配器还能按任务热插拔。

**LoRA 的三个关键参数**：

| 参数 | 作用 | 怎么选 |
|---|---|---|
| `lora_rank` | 适配器容量 | 小任务 8~16，改行为模式 32~64 |
| `lora_alpha` | 缩放系数 | 常见是 rank 的 2 倍，**比例比绝对值重要** |
| `lora_target` | 加在哪些层 | `all` 覆盖注意力 + MLP；只调风格可以只加 q/v |

**QLoRA 的额外代价**：基座量化成 4bit 后，前向精度下降，训练更慢，部分任务效果略差。显存够就别用。

### 2.4 关键超参与性能优化

| 参数                            | 作用       | 经验值                            |
| ----------------------------- | -------- | ------------------------------ |
| `cutoff_len`                  | 单条样本最大长度 | 覆盖 95% 样本即可，不必追最大              |
| `learning_rate`               | 学习率      | LoRA 常用 1e-4 ~ 5e-5；全参 1e-5 量级 |
| `num_train_epochs`            | 训练轮数     | 1~3 轮，SFT 数据少时别超过 3            |
| `lr_scheduler_type`           | 学习率调度    | `cosine` 最常用                   |
| `warmup_ratio`                | 预热比例     | 0.1 左右                         |
| `gradient_accumulation_steps` | 梯度累积     | 显存不够时用它模拟大 batch               |
| `bf16`                        | 混合精度     | A100/30 系以上开，比 fp16 稳          |

**全局 batch 的算法**：

```
全局 batch = per_device_train_batch_size × GPU 数 × gradient_accumulation_steps
```

**Packing（样本拼接）**

- **作用**：把多条短样本拼成一条定长序列，减少 padding 浪费。短样本多时吞吐能提升一倍以上。
- **风险**：拼接后，后一条样本能"看到"前一条，产生跨样本注意力泄漏，loss 会算错。
- **解法**：必须同时开 `neat_packing`，在序列内部做块对角掩码，让每条样本只看自己那段。

**DeepSpeed**

| Stage | 切什么 | 什么时候用 |
|---|---|---|
| ZeRO-2 | 优化器状态 + 梯度 | LoRA 微调够用，通信开销小 |
| ZeRO-3 | 再加参数本身 | 全参微调大模型时必须用 |

**FlashAttention**：降低注意力显存占用并加速，模型和硬件支持就开。

## 三、常用操作方式

三种入口，底层是同一套配置：

| 方式 | 命令形态 | 适用 |
|---|---|---|
| **WebUI** | `llamafactory-cli webui` | 试用、调参、看数据集 |
| **CLI + YAML** | `llamafactory-cli train xxx.yaml` | 正式训练，可版本化、可复现 |
| **命令行参数** | `llamafactory-cli train --model_name_or_path ...` | 单次实验，参数少时方便 |

**推荐 YAML**：配置能进 Git，改了什么一目了然；命令行参数一长就没法 review。

**四个典型任务**：

| 任务 | 做什么 |
|---|---|
| 训练 | `train` 加配置文件，`stage` 指定 `sft` / `dpo` / `ppo` |
| 评测 | 配置里开 `do_eval` + `val_size`，或单独跑评测脚本 |
| 导出 | `export` 命令，指定 `export_dir`；LoRA 可选合并成完整权重 |
| 推理 / API | `chat` 起交互界面，`api` 起 OpenAI 兼容服务 |

**导出时的一个选择**：

- **只导出适配器**：体积小，但推理时必须加载基座 + 适配器
- **合并成完整模型**：体积大，但可以直接当普通模型部署

生产环境常选合并，省掉运行时拼装。

## 四、常见坑点与排查方向

| 现象 | 可能原因 | 排查方向 |
|---|---|---|
| loss 在降，但回答乱码 / 格式错 | `template` 和底座不匹配 | 换成模型对应的模板名，先小样本试跑 |
| 报错读不到数据 / 字段为空 | `dataset_info.json` 字段映射错 | 检查 `columns`、`tags`、`formatting` 三者是否和文件一致 |
| 多轮对话只学了最后一轮 | 用了 `alpaca` 格式 | 多轮必须转 `sharegpt` |
| 训练 loss 正常但模型不会调工具 | 角色标签没配 `tool_tag` | 检查 tool 角色的字段映射 |
| OOM 显存爆掉 | batch 太大 / `cutoff_len` 太大 / 没开梯度检查点 | 依次降 batch、降长度、开 `gradient_checkpointing`、上 QLoRA |
| 吞吐很低，GPU 利用率上不去 | 短样本多、padding 浪费 | 开 `packing` + `neat_packing` |
| loss 震荡或突然爆炸 | 学习率过大 | 降一个数量级重跑，同时开梯度裁剪 |
| 训练集 loss 降、验证集不降 | 过拟合 | 减 epoch、加数据、降 rank |

**一个容易被忽略的坑**：换模型时，`template`、`cutoff_len`、`lora_target` 三个都要重新确认。只改 `model_name_or_path` 是最常见的错误来源。

## 五、面试高频追问简答

### Q1：LoRA 的原理是什么，为什么能省显存？

> 冻结原权重，在旁路加两个低秩矩阵 A 和 B（形状是 d×r 和 r×d，r 远小于 d），前向时把 BA 加到原权重上。
> 省显存是因为**只需要存适配器的梯度和优化器状态**，不用存全参的。全参训练时优化器状态是参数量的数倍，LoRA 把这部分砍掉了。
> rank 决定容量，alpha 是缩放，实际生效比例是 alpha/rank，两个要一起调。

### Q2：QLoRA 和 LoRA 有什么区别，什么场景选 QLoRA？

> QLoRA 多一步：把基座量化成 4bit 再挂 LoRA。显存能降到三分之一左右，代价是前向精度下降、训练变慢。
> 选它的唯一理由是**显存不够**——单卡跑 14B 以上、或者本地只有消费级显卡。显存够就别用，没必要为省显存牺牲效果。

### Q3：`template` 和 `dataset_info.json` 为什么都要配？

> 两者解决不同层的问题。`dataset_info` 解决**字段映射**：你的文件里字段叫什么、哪种格式、角色怎么标。`template` 解决**拼装格式**：样本最终要变成模型认识的那种字符串。
> 前者是「读得进来」，后者是「喂得对」。少任何一个，训练都会跑偏，而且往往表现为 loss 正常、效果很差，很难排查。

### Q4：Packing 为什么能提效，又有什么风险？

> 提效是因为短样本会填充大量 padding，GPU 在算空气。拼满定长序列后，每个位置都是有效 token。
> 风险是跨样本注意力泄漏——后一条样本能看到前一条。所以必须开 `neat_packing` 做块对角掩码。
> 另外开了 packing 后，一个 batch 里的真实样本数变多，调学习率和 warmup 要按 token 数换算。

### Q5：训练 loss 降得很好，但模型效果不行，怎么排查？

> 按这个顺序查：
> 1. **模板**——最可能的原因，格式错了 loss 照样降，因为模型在学错位的模式；
> 2. **数据格式**——多轮用了单轮格式、角色标签配错，会导致只学了部分内容；
> 3. **过拟合**——训练集 loss 降、验证集不降，减 epoch 或加数据；
> 4. **学习率**——太大导致训崩基座能力，表现为通用问答变差；
> 5. **评测方式**——用训练集同分布的数据测，本来就看不出泛化问题。

---

> **最小可跑路径**：准备 JSONL → 写 `dataset_info.json` → 确认 `template` → 选 LoRA + 合理 rank → 设 `cutoff_len` 和 batch → 开 `bf16` + 梯度检查点 → 跑 1 epoch 看 loss → 验证集抽样人工看 → 调整后再全量训。
