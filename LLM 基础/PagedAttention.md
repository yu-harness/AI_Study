# PagedAttention 重点（重写版）

## 一句话主线

KV cache 很吃显存，而且长度事先不知道，**传统"连续预留"浪费严重**。PagedAttention 借用操作系统的分页：把 KV cache 切成**定长块**，用块表映射。这样既不浪费，又能共享，同样显存能同时跑更多请求，吞吐就上去了。

## 1. 背景：KV cache

- 作用：自回归生成时，旧 token 的 K、V 算过就存下来，每步只算新 token 的，用显存换算力。
- 有多大：每个 token 约占 $2\times\text{层数}\times\text{hidden}\times\text{字节数}$。OPT-13B 是 $2\times40\times5120\times2\text{B}\approx800\text{KB}$，一个 2048 token 的请求就是约 1.6 GB。
- 难点：**生成多长事先不知道，缓存是动态增长的**。

## 2. 问题：显存被浪费了 60%～80%

传统做法是给每个请求按"最大长度"预留一整段连续显存。浪费分三类：

|类型|含义|
|---|---|
|预留|现在没用、将来才会用上的位置，期间别人不能用|
|内部碎片|按 2048 预留，实际生成 100 个就结束，剩下 1948 个位置白占|
|外部碎片|请求长短不一，空闲空间被切成零散小段，凑不出一整段给新请求|

论文测得，现有系统里**真正存放有效 token 的只有约 20%～38%**。真正的后果是：显存省不出来，同时能处理的请求（batch）就小，吞吐上不去。

## 3. 做法：分块加块表

- KV cache 切成**固定大小的块**（vLLM 默认 16 个 token），按需申请，当前块写满才申请下一块。
- 块表记录"逻辑块号 → 物理块号"。序列在逻辑上仍是连续的，物理上可以散在显存各处。计算 attention 时，kernel 按块表一块一块取数，不需要先拼成连续内存。
- 例：总长 100 个 token，$\lceil100/16\rceil=7$ 块（112 个位置），浪费 12 个。一般来说，每个序列最多浪费不到 1 块（至多 15 个位置）。
- 外部碎片消失：块大小一致，任何空闲块都能给任何请求用。

## 4. 共享与写时复制

- 并行采样、beam search 时，同一个 prompt 派生的多个输出，**前缀的 KV 完全相同**。它们的块表指向同一批物理块，只存一份，prompt 部分也只算一次。
- **每个物理块有引用计数**。某个序列要往被共享的块里写新 token 时，先复制一份再写（copy-on-write），互不影响，**没被改的块继续共享**。
- 省多少：$k$ 个输出共享长度 $L_p$ 的前缀、各自再生成 $L_o$ 个 token，占用从 $k(L_p+L_o)$ 降到 $L_p+kL_o$，省的是 $(k-1)L_p$。共享的那一段省了 $\frac{k-1}{k}$，整体省多少取决于共享前缀占总长的比例，prompt 越长、输出越短，省得越多。

## 5. 为什么叫"分页"

| 操作系统      | PagedAttention                        |
| --------- | ------------------------------------- |
| 页         | KV 块                                  |
| 字节        | token                                 |
| 进程        | 请求（序列）                                |
| 页表        | 块表                                    |
| 换入换出、写时复制 | 显存满时把块换到 CPU 内存（或丢弃后重算）、copy-on-write |

## 6. 代价与限定

- **非连续访问有开销**：attention kernel 本身比连续存储的版本慢一些（论文测过，大约一两成），但被更大的 batch 抵消后还有净收益。
- 吞吐提升的根源是"省内存，batch 变大"，不是"块可以并行算"。
- "**24 倍**"是最高值，对比的是没有这类优化的 HuggingFace Transformers，并且来自 vLLM 整套调度（包括连续批处理），不全是 PagedAttention 一个点的功劳。论文里对比 FasterTransformer、Orca 等已优化系统，提升约 2～4 倍。

## 一句话记忆

逻辑连续、物理不连续，靠块表对上；按需分配消灭碎片，块级共享省掉重复。

# KV cache 之所以必须连续，是因为 attention kernel 依靠“基址 + 步长”寻址

> **你的问题（整理后）**：KV cache 存的是什么？为什么它必须占用一段连续的内存？这个“连续”要求是怎么来的？

## 一、先明确存的是什么

自回归生成时，第 $t$ 步要计算 `Attention(q_t, K_{1..t}, V_{1..t})`。前 $t-1$ 个 token 的 K、V 在第 $t-1$ 步已经算过；**如果不保存下来，每一步都得重算整段前缀**，计算量会退化为 $O(n^2)$ 次前向。

因此，缓存每一层、每个 token 的 K 和 V：

$$
\text{单 token 占用}=2\times L_{\text{layers}}\times d_{\text{model}}\times \text{字节数}
$$

OPT-13B 一个 token ≈ 800 KB，2048 token 的请求 ≈ 1.6 GB（见 `[[PagedAttention#1 背景：KV cache]]`）。

**它的特点是只追加、不修改**：每生成一个 token 就在末尾写一条，长度事先无法知道。

## 二、“连续”指什么

它指的是：**某个请求的全部 KV，在物理显存中占据一段首尾相接的区间。**

```
请求 A:  [k0 v0][k1 v1][k2 v2][k3 v3][ ...预留 ... ]
          └──────── 一段连续显存 ────────┘
```

“连续”不是指 K 和 V 挨着存，而是指**同一序列的不同 token 位置之间连续**，因为寻址依赖这个性质。

## 三、为什么必须连续：三个层面的原因

**① kernel 用线性偏移定位第 $i$ 个 token**

attention 计算需要取“第 $i$ 个位置的 K”。最省事的寻址方式是：

$$
\text{addr}(i)=\text{base}+i\times \text{stride}
$$

**只用一个基址和固定步长就能算出任意位置**。如果内存分散成若干段，每个位置都要单独记录地址，kernel 里就得做间接寻址，开销和复杂度都会上升。

**② 张量的 stride 必须是规则的**

PyTorch 里的 `stride` 描述的正是“沿某个维度走一步，指针跳多少字节”：

```python
K.shape  = (batch, heads, seq, head_dim)
K.stride = (H*S*D, S*D, D, 1)      # 靠这个算地址
```

**如果一个序列的 seq 维不是连续存放的，`stride` 就无法用一个常数表示**，也就无法构造出一个合法的 view 传给 kernel。

**③ GPU 的合并访存依赖连续性**

显存以 32/128 字节的 transaction 为单位读取。连续布局下，相邻线程读相邻地址，一次事务能取到多个元素；**跳着读会让事务数成倍增加，带宽利用率骤降**。

这三点叠加的结果是：**传统实现要求每个请求在分配时就占住一段连续、足够长的空间。**

## 四、连续要求导致的连锁问题

因为要求“必须连续”，分配时只能**按最大长度一次性预留**：

```
实际生成 100 token，但按 2048 预留 → 1948 个位置白占
```

于是出现三类浪费（`[[PagedAttention#2 问题：显存被浪费了 60%～80%]]`）：

| 类型 | 成因 |
|---|---|
| 预留 | 为将来预留，但此刻不能用 |
| 内部碎片 | 预留 2048，实际只用到 100 |
| 外部碎片 | 长短请求交错，空闲区域被切碎，凑不出整段 |

**本质原因就是“连续”这一约束**：它强制在时间上提前占位、在空间上整段占位。

## 五、PagedAttention 只调整“映射”，不改变访存方式

它把 KV 切成定长块（默认 16 token），块之间**物理上可以散落各处**，再用块表记录“逻辑块 → 物理块”：

```
逻辑：  [块0][块1][块2][块3][块4][块5][块6]
物理：   ↓    ↓    ↓    ↓    ↓    ↓    ↓
        17   3    42   8    25   11   60
```

**序列在逻辑上仍然连续，但物理上已经不再连续。**

attention kernel 顺着块表一块一块取数，不需要先把数据拼成一段连续内存——这正是“非连续访问”的代价来源（约慢 10%~20%，`[[PagedAttention#6 代价与限定]]`），但换来的是几乎消除碎片。

## 六、“连续”是选择而非必然

|           | 传统实现          | PagedAttention |
| --------- | ------------- | -------------- |
| 物理布局      | 连续            | 离散             |
| 寻址方式      | base + stride | 查块表            |
| 分配单位      | 整段预留          | 16 token 一块，按需 |
| 碎片        | 60%~80% 浪费    | < 1 块/序列       |
| kernel 效率 | 高             | 略低（多一次查表与跳转）   |

**“必须连续”从来不是硬性要求，而是“用最简单寻址换最高访存效率”的工程取舍。** 分页把这笔账重新算了一遍：牺牲一点 kernel 效率，换回大量显存，再用更大的 batch 把损失赚回来。

## 一句话

**KV cache 连续，是因为 attention kernel 只用一个基址加固定步长就能定位每个 token，而 GPU 的合并访存也要求地址相邻；这个要求逼着系统按最大长度整段预留，于是产生大量碎片——PagedAttention 恰恰是放弃“物理连续”，改用块表映射，只保留“逻辑连续”。**

# 共享块的前提是前缀 KV 完全相同，而且 KV 写入后只读

> **你的问题（整理后）**：PagedAttention 为什么要做块级别的共享？共享能带来什么收益，又依赖什么条件？

## 一、先看什么场景会重复

三种典型情况，会产生**逐字节相同**的 KV：

```
① 并行采样（n>1）      同一 prompt → 采 8 条不同回复
② beam search          同一 prompt → 保留 k 条候选路径
③ 多轮对话 / RAG       同一 system prompt + 少量变化的历史
```

这 8 条回复在前 1000 个 token 上的 K、V **完全一样**，因为输入一样，模型计算也一样。

```
不共享：[p0..p999][out A]      ← 8 份前缀，8 倍显存
        [p0..p999][out B]
        ... 8 份

共享：  [p0..p999] ←── 8 个块表都指向这里
        [out A] [out B] ... 8 份
```

**重复的那 1000 个 token，存 1 份就够了。**

## 二、为什么能共享：两个前提

**① 因果性保证前缀 KV 与后续无关**

第 $i$ 个 token 的 K、V 只由前 $i$ 个 token 决定：

$$
K_i=f(x_{\le i}),\qquad V_i=f(x_{\le i})
$$

**它不会被后面的 token 影响**。所以“同一前缀 → 同一 KV”是严格成立的，不是近似。

**② KV 写入后只读**

KV cache 的整个生命周期里，写入只发生在“追加新 token”时，已有内容**永不修改**。

**只读数据天然可以共享**——多份指针指向同一块内存，不存在一致性问题。

这两条合起来，共享就是安全的。

## 三、为什么共享的粒度是“块”，而不是“整段”或“token”

**整段共享太粗**：并行采样的几条回复长度不同，整段共享会要求前缀长度完全一致。

**token 级太细**：块表要记录每个 token 的地址，映射表膨胀，寻址也变慢。

**块级刚好**：

```
前缀 1000 token，块大小 16
→ 共享 ⌊1000/16⌋ = 62 个完整块
→ 剩下的 8 个 token 在块 62 里，各自复制一份
```

**共享指针的代价是 O(1)**：8 个序列的块表里，前 62 项填同一个物理块号即可，不复制任何数据。

## 四、写时复制针对的正是“最后一个半块”

共享的块都是满的、只读的。**唯一会出问题的是最后一个未写满的块**：

```
共享块 62：[p992 ... p999][空][空]...
序列 A 要写第 1000 个 token → 会覆盖共享块里的空格
```

一旦写入，就会污染其他序列。所以：

```
序列 A 要写 → 先把块 62 复制一份 → 在副本上写
其他序列仍指向原块 → 互不影响
```

**没被写的块继续共享，只有被写的那一块被复制。** 这就是 copy-on-write，和操作系统的 fork 是同一套逻辑。

## 五、省多少：算一笔具体账

$k$ 个输出共享长度 $L_p$ 的前缀，各自再生成 $L_o$：

$$
\text{节省}=(k-1)\times L_p
$$

**例子**：4 条回复，前缀 1000 token，各生成 200 token

- 不共享：$4\times(1000+200)=4800$ 个 token 的 KV
- 共享后：$1000+4\times200=1800$ 个 token
- **省 3000 个 token，占 62.5%**

按 OPT-13B 每 token 约 800 KB：

$$
3000\times800\ \text{KB}\approx 2.4\ \text{GB}
$$

**一个请求就省下 2.4 GB**，这些空间可以多跑好几个并发请求。

## 六、省的不只是显存，还有计算

**前缀的 prefill 只算一遍。**

```
不共享：8 条回复各自 prefill 1000 token → 8 次前向
共享：  1 次 prefill，KV 复用       → 1 次前向
```

prefill 是计算密集阶段（$O(L^2)$），**省掉 7 次能显著降低首 token 延迟（TTFT）**。这一点经常被忽略，但在 beam search 里收益很大。

## 七、什么时候共享不了

| 场景 | 能否共享 | 原因 |
|---|---|---|
| 并行采样、beam search | ✅ 强共享 | 前缀完全相同 |
| 多轮对话（system prompt 固定） | ✅ 共享 system 段 | 前缀相同 |
| RAG（同一文档多次提问） | ✅ 共享文档段 | 文档块相同 |
| 不同用户、不同 prompt | ❌ | 前缀不同，第一个块就分叉 |
| 前缀只有部分相同 | ⚠️ 部分共享 | 只共享到分叉点前最后一个完整块 |

**共享收益与“公共前缀占总长度的比例”成正比**：prompt 越长、输出越短、并发分支越多，省得越多。

## 八、一句话

**共享块的前提是：因果性保证同一前缀算出同一份 KV，KV 又只读不写，因此多份指针指向同一块内存没有任何风险；块级粒度既能让映射代价保持 O(1)，又能在前缀分叉处自然断开，唯一需要特殊处理的是“最后一个未写满的块”，用 copy-on-write 解决。**

# 修改共享块时复制整块，引用计数决定何时复制、何时回收

> **你的问题（整理后）**：如果要往一个已被共享的块里写入 token，是直接分配一个新块，还是把旧块搬过去？块上的引用计数具体起什么作用？

## 一、四种写入情形，处理方式不同

| 情形                    | 处理                | 是否复制数据         |
| --------------------- | ----------------- | -------------- |
| 块没满，且**独占**（ref=1）    | 原地追加写入            | 否              |
| 块没满，但**共享**（ref>1）    | **复制整块** → 写入副本   | 是（整块 16 token） |
| 块**已满**               | 分配一个**新空块**，追加到块表 | 否              |
| 修改**历史** token（回滚/重算） | 同样走 CoW，复制成私有块再改  | 是              |

**关键区分**：

- **满了** → 开新块（空块）
- **共享** → 复制旧块（不是开空块）

## 二、CoW 的具体流程

```
写入前：
  序列A 块表: [0, 1, 2]        →  物理块 5, 9, 12
  序列B 块表: [0, 1, 2]        →  物理块 5, 9, 12    ← 完全共享
  块 12: [p992..p999][空][空]   ref_count = 2

序列 A 要写新 token：
  ① 检查最后一个块 12：ref=2 > 1，写了会污染 B
  ② 分配新块 37（空）
  ③ 把块 12 的内容整体复制到 37
  ④ 在 37 的空白位置写新 token
  ⑤ 块 12 的 ref_count → 1
  ⑥ 序列 A 的块表最后一项改成 37

写入后：
  序列A: [0, 1, 2, 37]  →  5, 9, 12, 37
  序列B: [0, 1, 2]      →  5, 9, 12        ← 前三个块仍然共享
  块 12 ref=1，块 37 ref=1
```

**只复制最后那个要写的块，前面的共享块完全不动。**

## 三、复制整块而不是单个 token 的原因

**块是分配与映射的最小单位**，没有“半块”的概念：

```
块表记录的是 "逻辑块 k → 物理块 p"，粒度是块
若要只复制一个 token，就得再维护一套 token 级偏移，映射表膨胀 16 倍
```

复制 16 个 token 的 KV 大约 12.8 KB（OPT-13B：800 KB/token ÷ … 实际每 token 800KB 是整模型全部层，块 16 token 约 12.8 MB）。这是**一次性的小代价**，换来映射结构简单。

**真正昂贵的是“整段复制”，块级 CoW 把复制量从 O(序列长度) 降到 O(16)**——这才是它比传统 fork 更划算的地方。

## 四、引用计数的三个作用

**① 判断是否需要 CoW（写入前）**

$$
\text{ref}>1\ \Rightarrow\ \text{有别人在用，必须先复制}
$$

没有这个计数，就无法区分“独占块”（可原地写）和“共享块”（必须复制）。

**② 判断何时可以回收（释放时）**

```
序列结束 / beam 被剪枝 / 请求被抢占
  → 它占的每个块 ref -= 1
  → ref 归 0 才真正还给空闲池
```

**注意：ref 减到 0 才回收，不是“有人释放就回收”。** 否则会把别人还在用的块清空，造成数据损坏。

**③ 支持分支式解码**

beam search 是最典型的例子：

```
初始：前缀块 ref = 3（3 条 beam 共享）
       ↓
beam 0 生成结束 → 释放 → 前缀块 ref = 2
beam 1 被剪枝     → 释放 → ref = 1
beam 2 继续生成   → 要写共享块 → 发现 ref=1，直接原地写（省一次复制）
beam 2 结束       → ref = 0 → 块回收
```

**ref 从 3 降到 1 的过程中，前两个释放完全没触发复制**——只有最后一个真正要写的时候才判断。

## 五、顺带：ref 也用于换出与抢占

当显存不足需要 swap 到 CPU 或直接丢弃时，调度器会看 ref：

```
ref = 1  → 独占，可安全换出/丢弃
ref > 1  → 有人在共享，换出会影响别人（通常等所有引用都结束，或只标记不释放）
```

**引用计数本质是一个“有多少人正在用这块内存”的全局账本**，写入、释放、换出三个决策都靠它。

## 六、一句话

**块满了就开新空块；块没满但被共享，就复制整块再写（copy-on-write），只复制要动的那一块；引用计数负责三件事——写入前判断要不要复制，释放时判断能不能回收（归 0 才算），以及 beam 分支这类多引用场景下的生命周期管理。**
