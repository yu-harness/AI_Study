## 一、总论与综合选型

### 1. Role of Databases in GenAI Applications（arXiv 2503.04847）

链接：[Role of Databases in GenAI Applications](https://arxiv.org/abs/2503.04847)（[HTML 全文](https://ar5iv.arxiv.org/html/2503.04847)）

作者是资深解决方案架构师 Santosh Bhupathi。论文把 GenAI 应用里的数据按上下文分成三类，并逐类给出适配的存储：会话上下文（聊天历史、用户交互，动态、非结构化、读写频繁）推荐 Redis 键值与 MongoDB 文档，需要强一致时用 PostgreSQL 关系型；情境上下文（用户画像、运营指标、领域信息，结构化、要求一致性）推荐 MySQL 与 PostgreSQL，以及 Delta Lakehouse 方向的 Apache Hudi；语义上下文（高维嵌入、向量化数据）推荐 Milvus、FAISS、Vespa 与 pgvector 扩展。文中还按用户提问到响应交付的八个步骤逐一说明数据库在每一步的位置，并用一个跑鞋推荐的例子演示欧氏距离检索与价格元数据过滤结合的做法，同时指出只用向量数据库会带来的性能瓶颈与视图不完整问题。

对应问题：①②③④。这是把「哪类数据放哪种数据库」讲清楚的总论。

### 2. Database Architecture for AI Applications: SQL, NoSQL, Vectors and Caches

链接：[Database Architecture for AI Applications](https://www.aimadetools.com/blog/sql-vs-nosql)

主张先确定每一类状态由哪个系统负责。关系型数据库承担用户与租户身份、计费与权益、Agent 运行与任务状态、工具审批与审计日志、会话元数据、文档归属与访问策略、需要长期对比的评测结果；灵活的 JSON 列可以在保留事务与约束的前提下存厂商特定的元数据。文档数据库适用记录差异较大且通常整体读写的场景（导入的源对象、不断变化的集成载荷、工具执行轨迹），文中同时提醒不能因为模型输出是 JSON 就把数据放进文档库，JSON 语法并不免除身份、归属、校验与关联的需要。向量记录需要带上嵌入与模型版本、源文档与分段标识、租户范围、内容版本或校验值、时间戳与删除状态，源文档与访问策略要留在向量索引之外以便索引可以重建。状态被分成持久（用户消息、审批、工具结果、最终状态）、临时（未完成的 token、锁、短期计划）、派生（摘要、嵌入、缓存）三类。末尾给出一个起步架构：PostgreSQL 负责用户、任务、权限、会话、审计，对象存储放原始文档，PostgreSQL 向量检索或向量服务索引已批准分段，Redis 承担缓存与计数，队列把推理与摄取移出请求路径。

对应问题：①③④。

### 3. 做大模型业务系统的数据库建模与缓存设计

链接：[做大模型业务系统，如何做好数据库建模、缓存设计与系统拆分](https://aicoding.csdn.net/6a687a6d662f9a54cb953d0c.html)

针对大模型业务给出建模原则：冷热数据分离、大字段独立存储、事务型数据与日志统计型数据分开、预留扩展字段、适度冗余减少多表关联。接着用六张 MySQL 表把这套原则展开：租户表、会话主表、对话消息表、消息内容附表、知识库文档表、模型调用用量日统计表，并说明大文本单独存附表、列表查询只读短预览字段、账单做预聚合、超过六个月的历史对话定时归档。往后是本地内存缓存到 Redis 到模型结果缓存的三级缓存设计，附带缓存键的构造方式与缓存一致性、缓存雪崩、缓存穿透的处理，以及按业务领域划分服务、把文档解析与向量化交给消息队列的处理方式。

对应问题：①②。

## 二、MySQL：用户信息、对话日志等结构化数据

### 4. MySQL 8.4 官方文档：The JSON Data Type

链接：[MySQL 8.4 Reference Manual · The JSON Data Type](https://dev.mysql.com/doc/refman/8.4/en/json.html)

讲 MySQL 的 JSON 列如何以内部二进制格式存储，服务器可以直接按 key 或数组下标取子对象而不必重新解析；存储空间与 LONGBLOB、LONGTEXT 大致相当，单文档大小受 max_allowed_packet 限制。8.4 增加了原地部分更新，条件是更新语句使用 JSON_SET、JSON_REPLACE 或 JSON_REMOVE，并且替换后的值不大于旧值。函数按创建、合并、搜索、修改、属性几类列出，JSON Path 语法用 `$` 起头，支持 `.key`、`[N]`、`[M to N]`、`last`、`.*`、`[*]` 与 `**`。JSON 的 null、true、false 必须小写，字符串比较区分大小写。JSON 列不能直接建索引，要借助生成列或 InnoDB 多值索引来实现对内部字段的检索。

对应问题：①。

### 5. 大模型开发 - SpringAI 之 MySQL 存储 ChatMemory

链接：[大模型开发 - SpringAI 之 MySQL 存储 ChatMemory](https://blog.csdn.net/yangshangwei/article/details/158183970)

把 Spring AI 默认的内存对话记忆换成 MySQL 持久化。给出单表 message_store 的结构：自增 BIGINT 主键、conversation_id、message_type、LONGTEXT 类型的 content、毫秒级 BIGINT 时间戳，并在 conversation_id 与 timestamp 上建索引，content 不建索引。逐项解释字段类型的选择理由（BIGINT 的空间余量、utf8mb4 对表情符号的支持、content 建索引收益小于成本）与两个索引用途。组件层面区分负责存取的 JdbcChatMemoryRepository 与负责按滑动窗口裁剪消息的 MessageWindowChatMemory，以及拦截调用的 MessageChatMemoryAdvisor。写入流程上，只有模型回复成功后才把用户消息与模型回复写入数据库，避免失败的调用污染后续上下文。

对应问题：①②。

## 三、PostgreSQL：JSONB 存储 Agent 非结构化中间状态

### 6. PostgreSQL 官方文档：JSON Types

链接：[PostgreSQL 18 Documentation · 8.14. JSON Types](https://www.postgresql.org/docs/current/datatype-json.html)

json 与 jsonb 的区别在这里讲得最清楚：json 按输入文本原样存储，每次处理都要重新解析，会保留空白与键的顺序；jsonb 按分解后的二进制格式存储，处理更快并且支持索引，代价是输入时略慢且不保留空白、键顺序与重复键。包含与存在性判定部分给出 `@>`、`?`、`?|`、`?&` 的语义与若干容易判断出错的例子（数组元素顺序无关、嵌套一层的数组才算被包含）。索引部分给出两种 GIN 运算符类：默认 jsonb_ops 支持键存在、包含与 jsonpath 匹配，jsonb_path_ops 只支持包含与 jsonpath 匹配，索引更小、检索针对性更强，代价是无法判断某个键是否存在，并且对 `{"a": {}}` 这类不含值的结构不产生索引项，会退化为全索引扫描。另附表达式索引（例如 `GIN ((jdoc -> 'tags'))`）与 btree、hash 索引的适用情形。

对应问题：②。

### 7. LangGraph 官方文档：Checkpointers

链接：[LangGraph · Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

Checkpointer 在图每个 super-step 边界保存状态快照，按 thread 归集，带来人工介入、记忆、时间旅行与容错四类能力。核心概念包括 thread、checkpoint、super-step、命名空间（根图为空字符串，子图为 `node_name:uuid`，嵌套子图用 `|` 连接）。实现列表：InMemorySaver（实验用）、SqliteSaver 与 AsyncSqliteSaver（本地）、PostgresSaver 与 AsyncPostgresSaver（生产）、langgraph-checkpoint-mongodb 的 MongoDBSaver 与 AsyncMongoDBSaver、langchain-azure-cosmosdb。序列化默认用 JsonPlusSerializer，覆盖 LangChain 与 LangGraph 类型、datetime、enum，可用 pickle_fallback 处理 msgpack 不支持的类，可用 EncryptedSerializer 做加密。持久化模式分 exit、async、sync 三档，对应性能与落库频率的取舍。文中还提到 DeltaChannel 只存增量以压缩高频追加通道的检查点体积，以及自定义 saver 需要实现的五个方法。

对应问题：②。

### 8. LangGraph 官方文档：Persistence

链接：[LangGraph · Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

checkpointer 与 store 的分工：checkpointer 保存单个 thread 的图状态，用于会话连续、人工介入、时间旅行、容错；store 保存应用自定义的键值数据，用于跨 thread 的长期记忆（用户偏好、事实、共享知识）。常见问题部分给出四类现象与处理方式：PostgresSaver 的 thread_id 超过 255 字符会报数据库错误，需要用 UUID 或哈希；MemorySaver 与 InMemorySaver 把检查点放在内存，进程重启即丢失；长会话下检查点不断累积会抬高延迟与存储开销，需要定期清理或设置保留策略；子图更新状态时父图不会立即看到，因为两者各管自己的检查点命名空间。

对应问题：②。

### 9. Understanding Checkpointers, Databases, API Memory, and TTL（LangChain 官方支持文章）

链接：[Understanding Checkpointers, Databases, API Memory, and TTL](https://support.langchain.com/articles/6253531756-understanding-checkpointers-databases-api-memory-and-ttl)

把检查点、数据库、运行时内存与 TTL 放在一起解释，用于排查内存溢出、数据库膨胀、pod 重启。给出五组问题与对应做法。直接使用 PostgresSaver 时默认在一次运行全程持有数据库连接，长任务会出现连接超时，应改用 ConnectionPool。检查点里直接存图片、PDF 等大对象会造成数据库膨胀，应改为存外部存储的引用键，或放进 LangGraph Store。TTL 只对启用之后新建的检查点生效，更早的检查点需要单独清理。文中一条对比很关键：MongoDB 的检查点文档有 16MB 上限，PostgreSQL 单个字段可达 1GB，遇到 DocumentTooLarge 时可以考虑改存 PostgreSQL 或压缩状态体积。

对应问题：②。

### 10. Adaptive Agentic RAG：构建可反思、可调式的知识智能体（第 4.2 节）

链接：[Adaptive Agentic RAG：构建可反思、可调式的知识智能体](https://blog.csdn.net/weixin_29053383/article/details/165669648)

这个页面的第 4.2 节讲作者把 LangGraph 的 Checkpoint 从 Redis 改存 PostgreSQL JSONB 的理由与做法。列出的两个问题是：节点并发读写时可能读到不完整的 JSON 导致解析失败；序列化后的内容难以人工排查状态里缺了哪个字段。给出的表结构是 thread_id 主键加 checkpoint JSONB 字段加创建与更新时间，并用 `ON CONFLICT (thread_id) DO UPDATE` 保证写入原子性。收益是可以直接用 `checkpoint->'values'->'evidence'` 取任意字段、结合 created_at 退回上一个检查点、用 jsonb_path_exists 找出卡在某个节点的会话，代价是写入延迟增加约 12ms。

对应问题：②。

### 11. AI 智能客服数据库设计实战：从架构选型到高并发优化

链接：[AI智能客服数据库设计实战：从架构选型到高并发优化](https://blog.csdn.net/2600_94959967/article/details/158286105)

先说明 AI 客服的数据特点（写入洪峰、会话上下文的树状存储、混合检索需求），再做选型对比：MySQL 与 PostgreSQL 在事务、JSON 支持、分库分表生态上的差别；MongoDB 的灵活模式与缺少强事务、跨会话关联查询吃力；Redis 存活跃会话状态。选型结论是 PostgreSQL 承担主业务存储，用 JSONB 存对话树并用 pgvector 做语义检索，Redis 存活跃上下文。实现部分给出用 JSONB 存整棵对话树的建表语句与 GIN 索引、用 jsonb_set 做局部更新、用 asyncpg 连接池做批量异步插入、用 pgvector 建 IVFFlat 或 HNSW 索引并写余弦距离检索的完整代码，以及冷热数据分离、读写分离、敏感信息加密存储的做法。末尾三个常见问题分别是 N+1 查询、数据库连接池耗尽、JSONB 使用过度导致索引失效。

对应问题：①②③④。

## 四、pgvector：在 PostgreSQL 上做向量检索

### 12. pgvector 官方仓库

链接：[pgvector/pgvector](https://github.com/pgvector/pgvector)

官方 README。支持精确与近似最近邻检索，数据类型包括 vector（最多 2000 维）、halfvec（最多 4000 维）、bit（最多 64000 维）、sparsevec（最多 1000 个非零元素）。距离函数有 L2、内积、余弦、L1、汉明、Jaccard，对应运算符 `<->`、`<#>`、`<=>`、`<+>`、`<~>`、`<%>`。索引类型为 HNSW 与 IVFFlat，并说明两者的构建时间、内存占用、查询性能差异与各自参数（HNSW 的 m 与 ef_construction；IVFFlat 的 lists 与 probes，以及建索引要在表里有数据之后、召回率与查询时间如何平衡）。还给了向量、半精度向量、二进制向量、稀疏向量的建表与查询示例，量化用于压缩索引的说明，以及各语言客户端列表。

对应问题：③。

### 13. pgvector in Production: A 2026 Reality Check

链接：[pgvector in Production: A 2026 Reality Check](https://selfhost.dev/blog/pgvector-in-production-2026-critiques-failures)

按向量规模分三档给出判断：一千万以内原生 pgvector 配 HNSW 能承担多数生产负载，延迟约 5–20ms；一千万到五千万需要 halfvec 量化、内存预算与 pgvectorscale 的 Streaming DiskANN 后端；五千万以上需要重新评估专用向量数据库的成本。随后列出六类常见故障：HNSW 构建时 maintenance_work_mem 默认 64MB 导致构建速度下降 10–50 倍甚至失败；索引运算符类与查询运算符不匹配造成静默顺序扫描；隐式类型转换使索引失效；先做向量检索后做过滤造成结果数量不足并错过更靠前的匹配；持续写入与索引维护争用；部署后冷缓存使 p99 延迟放大。每条都给出处理方式，并用一个三万行数据集上 226ms 到 0.982ms 的对比说明运算符类匹配的重要性。末尾给出 maintenance_work_mem、ef_construction、ef_search、m、shared_buffers 五个参数的默认值与生产目标。

对应问题：③。

### 14. Vector Search with pgvector — Similarity Search, HNSW Indexing, and Production Patterns

链接：[Vector Search with pgvector](https://www.datasops.com/blog/pgvector-semantic-search)

覆盖面完整的一篇。对比 pgvector 与专用向量数据库在向量数量、查询延迟、运维开销、元数据过滤、与应用数据一致性、多租户、规模化成本上的差别，并给出迁移的判断条件（查询 p99 超出服务目标、需要独立于业务数据做多区域复制、向量数超过两亿且内存放不下 HNSW 索引）。HNSW 与 IVFFlat 的构建时间、内存、召回率、增量插入表现逐项对比，结论是新的生产部署从 HNSW 开始。列出十项生产检查清单，包括构建索引前把 maintenance_work_mem 提到 4GB 以上、在 PgBouncer 事务模式下用 SET LOCAL 设置 hnsw.ef_search、批量插入嵌入、为内容列建 GIN 全文索引以支持 RRF 混合检索、把嵌入存成 vector(N) 而不是 JSONB。文中还提醒 Agent 长期记忆这类负载会比预期更早触到容量上限，以及按租户过滤查询占主导时应使用部分索引。

对应问题：③④。

### 18. AI Agent MongoDB Integration 2026
