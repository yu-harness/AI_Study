## 06 数据同步：主从库如何实现数据一致？

> AOF 和 RDB 解决了「数据少丢失」，但单个实例宕机意味着**服务中断**。Redis 的高可靠第二层：**增加副本冗余**——多实例部署，一台挂了其他的顶上。主从模式 + 读写分离是基础，全量复制（首次）+ 长连接命令传播（常态）+ 增量复制（断连恢复）是三种同步方式。

> 💡 **从哪里来？** 第 01~03 节解决了「单机快」，第 04~05 节解决了「数据不丢」。但宕机恢复期间——不管 AOF 重放还是 RDB 加载——服务是中断的。Redis 不能接受这一点。于是出现了「多副本」思路：一台挂了，另一台立刻顶上。但多个副本之间数据怎么保持一致？这就是本节要解决的核心问题——主从同步。

### 为什么必须读写分离？

```mermaid
graph TD
```

| 操作 | 主库 | 从库 |

## 二、第一次同步：全量复制的三个阶段

```mermaid
graph TD
    subgraph "阶段一：握手协商"
        S1["🟢 从库 → 主库<br/>psync ? -1<br/>——<br/>? = 不知道主库 runID<br/>-1 = 第一次复制"] --> S1R["🔴 主库 → 从库<br/>FULLRESYNC<br/>runID + offset<br/>——<br/>FULLRESYNC = 全量复制"]
    end

    subgraph "阶段二：全量数据传输"
        S1R --> S2["🔴 主库<br/>① bgsave 生成 RDB<br/>② 发送 RDB 给从库<br/>③ 新写命令暂存<br/>replication buffer"]
        S2 --> S2R["🟢 从库<br/>① 清空自身旧数据<br/>② 加载 RDB 文件"]
    end

    subgraph "阶段三：补齐增量"
        S2R --> S3["🔴 主库<br/>把 replication buffer 中<br/>RDB 生成后收到的写命令<br/>发给从库"]
        S3 --> S3R["🟢 从库<br/>执行这些写命令<br/>→ 数据追平"]
        S3R --> Done["✅ 主从数据一致"]
    end

    style S2 fill:#fff3cd,stroke:#ffc107
    style Done fill:#d4edda,stroke:#155724
```

| 阶段         | 主库做什么                                        | 从库做什么           |
| ---------- | -------------------------------------------- | --------------- |
| **① 握手协商** | 响应 `FULLRESYNC runID offset`                 | 发送 `psync ? -1` |
| **② 全量传输** | bgsave 生成 RDB → 发送；新写命令暂存 replication buffer | 清空旧数据 → 加载 RDB  |
| **③ 补齐增量** | 把 replication buffer 中的命令发送                  | 执行补齐命令 → 追平     |

### psync 命令的两个参数

| 参数 | 含义 | 首次同步的值 |
|---|---|---|
| **runID** | 每个 Redis 实例的唯一随机 ID | `?`——还不知道主库是谁 |
| **offset** | 复制进度偏移量 | `-1`——表示第一次复制 |

### 为什么用 RDB 而不是 AOF 做首次同步？

| 维度 | RDB | AOF |
|---|---|---|
| **文件大小** | 紧凑·二进制压缩 | 累积所有命令·更大 |
| **传输效率** | ✅ 更高 | ❌ 低 |
| **加载速度** | ✅ 直接读入内存 | ❌ 需逐条重放 |
| **首次同步的核心诉求** | 把主库当前的**全量状态**快速传给从库 | — |

> 首次同步要的是「主库当前状态的一份完整副本」，RDB 天生适合。AOF 记录的是历史操作序列，恢复时还要逐条重放——主从同步如果也逐条重放，太慢了。

## 三、主从级联模式 —— 分担主库压力

### 全量复制的两个开销（都落在主库）

```mermaid
graph TD
    Cost["🔴 主库两重压力"] --> C1["① fork 子进程生成 RDB<br/>→ 阻塞主线程"]
    Cost --> C2["② 传输 RDB 文件<br/>→ 占用主库网络带宽"]

    C1 --> Problem2["如果 N 个从库同时<br/>发起全量复制<br/>→ 主库扛不住"]
    C2 --> Problem2

    style Problem2 fill:#f8d7da,stroke:#721c24
```

### 解法：「主-从-从」级联

```mermaid
graph TD
    Master2["🔴 主库"] -->|"全量复制 + 命令传播"| Relay["🟡 级联从库<br/>（内存配置高）"]
    Relay -->|"同步"| Slave_A["🟢 从库 A"]
    Relay -->|"同步"| Slave_B["🟢 从库 B"]
    Relay -->|"同步"| Slave_C["🟢 从库 C"]

    Master2 -.->|"不再直接连接"| Slave_A
    Master2 -.->|"不再直接连接"| Slave_B
    Master2 -.->|"不再直接连接"| Slave_C

    style Relay fill:#fff3cd,stroke:#ffc107
```

| 模式 | 主库压力 | 适用 |
|---|---|---|
| **直连模式**（所有从库连主库） | 🔴 重——每个从库都要主库 fork + 传 RDB | 从库少 |
| **级联模式**（主-从-从） | 🟢 轻——主库只同步给一个级联从库 | 从库多 |

## 四、正常运行：基于长连接的命令传播

首次全量复制完成后，主从之间维持一个**长连接**，主库每收到一条写命令，就实时同步给从库——避免频繁建立连接的开销。

## 五、网络断了怎么办？—— 增量复制 + repl_backlog_buffer

> Redis 2.8 之前：断连 → 只能重新全量复制 → 开销巨大。
> Redis 2.8+：断连 → **增量复制**——只补发断连期间主库新收到的命令。

### 核心机制：环形缓冲区 + 双偏移量

```mermaid
graph TD
    subgraph "repl_backlog_buffer（环形缓冲区）"
        direction LR
        Pos1["位置 0"] --> Pos2["位置 1"] --> Pos3["..."] --> PosN["位置 N"] --> Pos1
    end

    subgraph "两个偏移量"
        MasterOffset["🔴 master_repl_offset<br/>主库写到哪里了<br/>——<br/>主库每收到一个写命令<br/>offset +1"]
        SlaveOffset["🟢 slave_repl_offset<br/>从库读到哪里了<br/>——<br/>从库每复制一个命令<br/>offset +1"]
    end

    MasterOffset --> Gap["📏 两个 offset 的差值<br/>= 需要补发的命令"]
    SlaveOffset --> Gap

    style MasterOffset fill:#f8d7da,stroke:#721c24
    style SlaveOffset fill:#d4edda,stroke:#155724
```

### 增量复制流程

```mermaid
graph LR
    Disconnect["💥 网络断连"] --> MasterWrite["🔴 主库继续收写命令<br/>→ master_repl_offset ↑<br/>→ 命令写入 repl_backlog_buffer"]
    MasterWrite --> Reconnect["🔗 连接恢复"]
    Reconnect --> SlaveSend["🟢 从库发送<br/>psync runID slave_repl_offset"]
    SlaveSend --> MasterCheck["🔴 主库判断<br/>master - slave 的差值"]
    MasterCheck --> Sync["📤 只发送差值区间<br/>内的命令给从库"]
    Sync --> Done2["✅ 从库补执行·追平"]

    style Reconnect fill:#d1ecf1,stroke:#0c5460
    style Sync fill:#d4edda,stroke:#155724
```

### ⚠️ 环形缓冲区的风险：覆盖

```mermaid
graph TD
    Risk["⚠️ 环形缓冲区写满后<br/>新写入覆盖旧数据"] --> RiskDetail["如果从库读得太慢<br/>→ 还没读的命令被覆盖<br/>→ master 无法找到差值区间<br/>→ 只能重新全量复制！"]
    RiskDetail --> Fix["🔧 调大 repl_backlog_size<br/>=（主库写入速度 - 网络传输速度）× 操作大小 × 2<br/>—— × 2 是安全冗余<br/>应对突发流量"]

    style Risk fill:#f8d7da,stroke:#721c24
    style Fix fill:#d4edda,stroke:#155724
```

### repl_backlog_size 计算示例

| 参数 | 值 |
|---|---|
| 主库每秒写入 | 2000 个操作 |
| 每个操作大小 | 2 KB |
| 网络每秒传输 | 1000 个操作 |
| 积压操作 = 2000 - 1000 | 1000 个 |
| 最小缓冲 = 1000 × 2KB | **2 MB** |
| 最终设置（×2 冗余） | **4 MB** |

## 六、三种同步模式全景对比

```mermaid
graph TD
    Sync3["📡 三种同步模式"] --> Full["📦 全量复制<br/>首次连接·完整 RDB<br/>耗时·不可避免"]
    Sync3 --> Live["📡 命令传播<br/>长连接·实时同步<br/>常态运行·低延迟"]
    Sync3 --> Partial["📝 增量复制<br/>断连恢复·只补缺失<br/>基于 repl_backlog_buffer"]

    Full --> Cascade["优化：主-从-从级联<br/>分散主库 fork + 传输压力"]
    Live --> Risk2["风险：网络断连<br/>→ 切到增量复制"]
    Partial --> Risk3["风险：环形缓冲区覆盖<br/>→ 被迫退回到全量复制<br/>→ 调大 repl_backlog_size"]

    style Full fill:#fff3cd,stroke:#ffc107
    style Live fill:#d4edda,stroke:#155724
    style Partial fill:#d1ecf1,stroke:#0c5460
```

| 同步方式 | 触发时机 | 传输内容 | 开销 |
|---|---|---|---|
| **全量复制** | 首次连接 / 增量复制失败 | 完整 RDB 文件 | 🔴 大——主库 fork + 网络传输 |
| **命令传播** | 正常运行 | 每条写命令 | 🟢 小——长连接实时推送 |
| **增量复制** | 网络断连恢复 | 断连期间的写命令 | 🟡 中——取决于断连时长 |

> **🧭 接下来看什么？** 主从模式解决了多副本数据一致的问题。但还有一个尴尬的空白——主库挂了以后，谁来「顶上」？从库可以继续提供读服务，但写操作必须由主库执行。主库挂了，写操作全部失败。这时需要一套**自动故障转移机制**——自动检测主库下线、自动选一个新主库、自动通知所有从库和客户端。这就是哨兵（Sentinel），下一节讲。

---

## 一句话总结

> 主从同步 = 全量复制（首次 RDB）+ 命令传播（常态长连接）+ 增量复制（断连后基于 repl_backlog_buffer 环形缓冲区补缺失命令）。读写分离避免了多主写冲突；主-从-从级联把全量复制的压力从主库分散到中间节点；repl_backlog_size 决定增量复制能不能成功——太小会触发回退全量复制。核心记住：全量靠 RDB（快照传输），增量靠环形缓冲区 + 双偏移量（master_repl_offset - slave_repl_offset = 要补的命令）。
