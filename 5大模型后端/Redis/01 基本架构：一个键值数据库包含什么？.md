## 一、数据模型与操作接口 —— 存什么、怎么操作
数据模型和操作接口是 Redis 常被用于**缓存、秒杀、分布式锁**等场景的重要基础。
### 数据模型：可以存哪些数据？
键值数据库的**基本数据模型**是 **key-value 模型**。
```
Key-Value 模型
 ├── 🔹 SimpleKV
 │    └── Value 类型：基本类型（String · 整型）
 ├── 🔹 Memcached
 │    └── Value 类型：仅 String
 └── 🌟 Redis（重点）
      └── Value 类型：String · 哈希表 · 列表 · 集合 · 有序集合
```

> **Redis 能在业务中广泛使用，核心就是支持多样化的 value 类型。**

**举例**：用户信息可以用关系型数据库存，但「一个用户 ID → 一个用户信息集合」也天然适合用 Redis 的哈希表存储。
### 操作接口
基本操作无外乎**增删改查**：

| 操作              | 说明                                        |
| --------------- | ----------------------------------------- |
| **PUT**（也叫 SET） | **新写入或更新**。实际执行时根据 key 是否存在走不同流程          |
| **GET**         | 根据 key **读**取 value                       |
| **DELETE**      | 根据 key **删**除整个 KV 对                      |
| **SCAN**        | 根据**一段 key 范围返回 va**lue。如「查询用户一段时间内的访问记录」 |
| **EXISTS**      | 判断某个 **key 是否存**在（如黑白名单场景）                |
String（字符串）
```Bash
# 设置与获取
SET key value                  # 设置 key-value
SET key value EX 60            # 设置 key-value，并在 60 秒后过期
SETNX key value                # 仅在 key 不存在时才设置（Set if Not eXists，常用于分布式锁）
GET key                        # 获取 key 的值
MSET k1 v1 k2 v2               # 批量设置多个值
MGET k1 k2                     # 批量获取多个值

# 计数器操作
INCR key                       # 值自增 1（如果 key 不存在，从 0 开始加）
DECR key                       # 值自减 1
INCRBY key increment           # 增加指定数值（如 INCRBY pv 10）
```
 Hash（哈希 / 字典）
```Bash
HSET user:1001 name "Alice" age 25   # 设置 key 中的一个或多个字段
HGET user:1001 name                  # 获取指定字段的值
HMGET user:1001 name age             # 批量获取多个字段的值
HGETALL user:1001                    # 获取该 Hash 内的所有 field 和 value
HDEL user:1001 age                   # 删除指定字段
HEXISTS user:1001 name               # 判断字段是否存在
HINCRBY user:1001 age 1              # 给指定字段增加数值
```
List（列表）
```Bash
# 压入与弹出
LPUSH mylist a b c             # 从左侧（头部）依次压入元素
RPUSH mylist d e               # 从右侧（尾部）依次压入元素
LPOP mylist                    # 从左侧弹出并返回一个元素
RPOP mylist                    # 从右侧弹出并返回一个元素

# 查询与范围
LRANGE mylist 0 -1             # 获取指定范围内的元素（0 到 -1 表示获取全部）
LLEN mylist                    # 获取列表元素总数
LINDEX mylist 0                # 获取指定索引位置的元素

# 阻塞式弹出（常用于消息队列监听）
BLPOP mylist 10                # 从左侧弹出元素，若列表为空则阻塞等待最多 10 秒
```
Set（无序集合）
```Bash
SADD tags java python c++      # 向集合添加一个或多个元素
SREM tags c++                  # 移除集合中的元素
SMEMBERS tags                  # 获取集合中的所有元素（注意：数据量过大时谨慎使用）
SISMEMBER tags java            # 判断元素是否存在于集合中（返回 1 或 0）
SCARD tags                     # 获取集合中的元素数量
SRANDMEMBER tags 2             # 随机获取 2 个元素（不删除）
SPOP tags 1                    # 随机弹出并删除 1 个元素（常用于抽奖）

# 集合间运算
SINTER set1 set2               # 计算交集（共同好友）
SUNION set1 set2               # 计算并集
SDIFF set1 set2                # 计算差集（set1 有但 set2 没有的）
```
Sorted Set / ZSet（有序集合）
```Bash
ZADD leaderboard 100 "UserA" 200 "UserB" 150 "UserC"  # 添加带 score 的元素
ZINCRBY leaderboard 50 "UserA"                         # 给指定元素的 score 加 50
ZSCORE leaderboard "UserA"                            # 查看指定元素的 score
ZRANK leaderboard "UserA"                             # 获取元素的从小到大排名（从 0 开始）
ZREVRANK leaderboard "UserA"                          # 获取元素的从大到小排名

# 范围查询
ZRANGE leaderboard 0 -1 WITHSCORES                     # 按 score 从小到大返回所有元素及分数
ZREVRANGE leaderboard 0 2 WITHSCORES                  # 按 score 从大到小返回前 3 名及分数
ZRANGEBYSCORE leaderboard 100 200                     # 获取 score 在 100 到 200 之间的元素
ZREM leaderboard "UserC"                              # 移除指定元素
```

常用拓展数据类型

| **数据类型**              | **核心操作指令**                              | **典型应用场景**                               |
| --------------------- | --------------------------------------- | ---------------------------------------- |
| **Bitmap（位图）**        | `SETBIT`, `GETBIT`, `BITCOUNT`, `BITOP` | 极省空间**的布尔打卡、用户签到状态、在线状态**统计              |
| **HyperLogLog（基数统计）** | `PFADD`, `PFCOUNT`, `PFMERGE`           | 海量数据的 UV（独立访客）计数，内存固定约 12KB，允许 ~0.81% 误差 |
| **GEO（地理位置）**         | `GEOADD`, `GEODIST`, `GEORADIUS`        | 存储经纬度，计算两地距离、查找“附近的人/店铺”                 |
| **Stream（消息流）**       | `XADD`, `XREAD`, `XGROUP`, `XACK`       | Redis 5.0+ 提供的完整消息队列，支持持久化、主备复制、消费组与 ACK |

### Redis 的局限性

| 能做           | 不能做                      |
| ------------ | ------------------------ |
| ✅ 单 key 增删改查 | ❌ 复杂的聚合计算（如「计算多个用户年龄均值」） |

## 二、内存还是外存？—— 存储介质的选择

```
⚡ 数据存哪里？
├── 💾 内存
│   ├── ✅ 百 ns 级访问
│   ├── ❌ 掉电数据全丢
│   └── 🎯 选型取决于应用场景
│       ├── 缓存场景（要快 · 允许丢 → 内存）
│       │   └── 代表：Memcached · Redis
│       └── 持久化场景（不能丢 → 外存）
│           └── 代表：RocksDB
└── 💿 外存
    ├── ✅ 数据不丢
    └── ❌ ms 级访问 · 性能拉低
```

> Redis 是**内存键值数据库**。缓存是其最重要的应用场景——后面会讲 Redis 作为缓存的机制、优势和优化方法。

## 三、访问框架 —— 怎么和外部交互？

```Plaintext
🚪 两种访问模式
├── 📚 函数库调用
│   ├── 动态链接库 .so
│   ├── 嵌入应用程序内
│   └── 代表：RocksDB
│
└── 🌐 网络框架
    ├── Socket 通信
    ├── 独立网络服务
    ├── 代表：Memcached · Redis
    └── ⚙️ I/O 模型设计（单线程？多线程？多进程？）
        └── Redis：单线程
            └── 怎么做到高性能？（后续详解）
```

| 方式 | 优点 | 缺点 | 代表 |
|---|---|---|---|
| **函数库** | 简单·低延迟 | 使用面窄 | RocksDB |
| **网络框架** | 使用面广·独立服务 | 引入 I/O 模型复杂度 | Redis、Memcached |

> 网络框架扩大了 Redis 的使用面，但也带来了 **I/O 模型设计的选择**——单线程还是多线程？如何平衡阻塞与线程竞争？

## 四、索引模块 —— 怎么快速定位数据？

**索引的作用**：让键值数据库根据 **key** 找到相应 **value** 的存储位置。

| 索引类型     | 复杂度      | 代表              |
| -------- | -------- | --------------- |
| **哈希表**  | O(1)     | Memcached、Redis |
| **B+ 树** | O(log n) | 关系型数据库          |
| **跳表**   | O(log n) | RocksDB（内存索引）   |
| **字典树**  | O(k)     | 前缀匹配场景          |
> 内存键值数据库（如 Redis）采用**哈希表**作为索引——因为**内存的高性能随机访问**可以很好地与哈希表 O(1) 相匹配。
### Redis 的特殊之处
不同于普通 KV “找到 Key 即结束”，Redis 的 Value 是复杂结构，需要“二次定位”，其**高性能**依赖于**内部高效的数据结构实现**。

## 五、操作模块 —— 不同操作的具体逻辑

找到存储位置后，不同操作需要不同的后续处理：

| 操作 | 具体逻辑 |
|---|---|
| **GET / SCAN** | 根据存储位置直接返回 value |
| **PUT**（新写） | 分配内存空间 → 写入键值对 |
| **DELETE** | 删除键值对 → 释放内存空间（由分配器完成） |

```plaintext
🔧 SimpleKV -->>redis(基础键值数据库)
├── ① 访问框架
│   ├── 函数库 → 网络服务
│   └── 扩大了应用范围
├── ② 数据模型
│   ├── value 仅基本类型 → String · Hash · List · Set · ZSet
├── ③ 持久化
│   ├── 简单文件落盘 →AOF 日志 + RDB 快照
```

| 维度           | SimpleKV                  | Redis                     |
| ------------ | ------------------------- | ------------------------- |
| **访问方式**     | 动态链接库 .so                 | 网络框架（Socket 通信）           |

> **🧭 接下来看什么？** 这一节从宏观上搭好了 Redis 的骨架（访问→索引→操作→存储）。但有一个关键问题还没回答：Redis 为什么这么快？宏观架构只是第一步，真正决定性能的是**底层数据结构**——哈希表 O(1)、跳表 O(logN)、压缩列表、SDS……下一节就钻进这些细节。

## 一句话总结

> 一个键值数据库 = 访问框架（怎么接进来）+ 索引（怎么定位）+ 操作（怎么执行）+ 存储（怎么存、怎么持久化）。
>
> SimpleKV 是麻雀版，Redis 是五脏俱全的加强版——value 类型更丰富、持久化双模式、支持集群。
> 理解这四块，就理解了 Redis 单机版的骨架。

## 面试问答稿（直接背这些回答）

> 面试稿和演讲稿不一样：**结论先行，3~5 句讲完就停，留白等追问**。下面是这篇知识点的高频题，每道后面就是可以直接照着说出口的回答。

---

**Q1（开放题）："Redis 为什么被归类为键值数据库？它和其他数据库区别在哪？"**

> 因为它的核心是 key-value 模型，拿 key 直接定位 value。和关系型数据库最大的区别是：关系型用 B+ 树做索引，支持复杂的 SQL 查询和关联；Redis 主要用哈希表，O(1) 定位，追求极致的读写性能。另外 Redis 的 value 类型很丰富，有 String、Hash、List、Set、ZSet，这让它能在缓存、秒杀、分布式锁、排行榜这些场景广泛使用。

**Q2（核心必背）："Redis 的 value 支持哪几种数据类型？各有什么典型应用？"**

> 五种基本类型：String 字符串，可以做缓存、计数器（INCR）、分布式锁（SETNX）；Hash 哈希表，适合存一个对象，比如用户信息；List 列表，可以做消息队列，比如 BLPOP 阻塞弹出；Set 无序集合，可以做共同好友、去重、抽奖（SPOP）；ZSet 有序集合，按 score 排序，最适合做排行榜。另外还有 Bitmap、HyperLogLog、GEO、Stream 这些扩展类型，分别用于签到统计、UV 去重计数、地理位置、消息队列。

**Q3（对比题）："Redis 为什么用内存存储？内存和外存怎么选？"**

> 内存访问是百纳秒级，外存是毫秒级，差了上万倍。Redis 主打的就是这个速度，所以数据放内存。但内存掉电全丢、而且贵，所以纯内存只能用于缓存场景——允许丢、要极快。如果是不能丢数据的持久化场景，就得用外存，比如 RocksDB。所以选型看场景：要速度、能容忍丢，就内存；必须持久化，就外存。

**Q4（架构题）："键值数据库有哪几个核心模块？分别干什么？"**

> 四个：访问框架、索引、操作、存储。访问框架管怎么和外部交互，是函数库调用还是网络 Socket 服务。索引管根据 key 定位 value 的存储位置。操作管具体指令的执行逻辑，PUT、GET、DELETE、SCAN。存储管内存分配和持久化。SimpleKV 是这四个模块的最小实现，Redis 是加强版。

**Q5（追问）："Redis 用哈希表做索引，为什么 O(1)？相比 B+ 树呢？"**

> 哈希表是根据 key 算出一个哈希值，直接定位到桶的位置，不需要比较，所以平均 O(1)。但它是无序的，而且会有哈希冲突、需要扩容。B+ 树是 O(log n)，有序，所以适合范围查询，关系型数据库都用它。Redis 用哈希表，是因为内存的高性能随机访问正好能发挥 O(1) 的优势，而它主要就是按 key 精确读写，不需要复杂的范围查询。

**Q6（陷阱题）："Redis 的 GET 和 PUT 是不是都只是'找到位置返回'？"**

> 不是。GET 和 SCAN 确实只是根据存储位置直接返回 value。但 PUT 如果是新写，需要先分配内存空间，再写入键值对。DELETE 除了删掉键值对，还要释放内存空间，这个由内存分配器完成。所以操作模块不是简单地读写，不同类型操作有不同逻辑，尤其是涉及内存分配和释放的。

**Q7（演进题）："从 SimpleKV 到 Redis，核心演进在哪几个方面？"**

> 四个方面。访问框架：从函数库调用变成网络 Socket 服务，扩大了应用范围。数据模型：value 从基本类型扩展成 String、Hash、List、Set、ZSet 五种。持久化：从简单落盘变成 AOF 日志加 RDB 快照双模式。集群：从单机变成支持主从、哨兵、集群分片，做到高可靠和高扩展。

**Q8（开放性追问）："Redis 有哪些做不了的事？"**

> 最大的限制是复杂的聚合计算，比如算多个用户的年龄均值这种跨 key 的操作，Redis 做不了，那是关系型数据库或者专门计算引擎的事。Redis 擅长的是单 key 的增删改查和高并发读写，不适合做复杂查询和数据分析。
