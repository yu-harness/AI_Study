## 零、一句话理解 RAG

**RAG(Retrieval-Augmented Generation,检索增强生成)** = 先「检索」相关文档片段,再「生成」回答。

核心动机:大模型的知识有截止日期、且不含私有资料。RAG 把**你自己的文档**(如藜麦种植手册)变成可检索的索引,回答时先把相关片段捞出来塞进上下文,让模型"翻着书"回答。

对比记忆:

| | 普通问答 | RAG 问答 |
|---|---|---|
| 依据 | 模型记忆 | 模型记忆 + **实时检索到的文档** |
| 私有资料 | ❌ 不知道 | ✅ 来自你的文档 |
| 时效性 | 截止训练日 | ✅ 随时更新文档即可 |
| 可追溯 | ❌ 无法解释来源 | ✅ 可展示引用片段 |

> **类比**:普通问答像让 ChatGPT 凭记忆写作文;RAG 像给一个学生**开卷考试**,还允许他翻你指定的参考书。

```
│  (8140字)      TextSplitter            Embedding 模型               │
│                                                                     │
│                    ┌──────────────┐                                 │
│                    │  向量数据库    │  ──────────────┐               │
│                    │   (Chroma)    │                │               │
│                    └──────────────┘                │               │
│                          ▲                         ▼               │

```

对应代码六步:

| 步骤 | 代码位置 | 核心对象 | 一句话作用 |
|------|---------|---------|-----------|
| 1 加载 | `TextLoader` | Document | 把文件读成文档对象 |

| 6 生成 | `ConversationalRetrievalChain` | Chain | 片段+问题 → LLM → 答案 |

## 二、第 1 步:加载文档(Document Loaders)

```python
import os
from langchain_community.document_loaders import TextLoader

BASE_DIR = os.path.dirname(os.path.abspath(__file__))
loader = TextLoader(os.path.join(BASE_DIR, "藜麦.txt"), encoding="utf-8")
documents = loader.load()
print(len(documents))            # 1
print(documents[0].page_content) # 文档正文(字符串)
print(documents[0].metadata)     # 元信息字典(如来源路径)
```

### 知识点

**1. Document 对象是什么?**
LangChain 里的文档统一封装成 `Document`,只有两个字段:
- `page_content`:正文文本(大字符串)
- `metadata`:元数据字典(来源、标题、页码等),检索时可携带、可过滤

这是全流程传递的"最小数据单元"。

**2. 为什么需要 Loader 而不用 `open()`?**
Loader 是**统一接口**:不管来源是 txt / pdf / word / 网页 / 数据库,都产出同样的 `Document` 列表,下游代码不用改。不同来源换 Loader 即可:

```python
from langchain_community.document_loaders import PyPDFLoader, CSVLoader, WebBaseLoader
# PyPDFLoader("./手册.pdf").load()   # PDF
# CSVLoader("./数据.csv").load()     # CSV
# WebBaseLoader("https://...").load()# 网页
```

**3. 两个实战教训(本项目踩过的坑)**
- **相对路径失效**:`"./藜麦.txt"` 是相对"当前运行目录"的,换目录运行就找不到 → 用 `os.path.join(BASE_DIR, ...)` 基于脚本自身定位。
- **编码坑**:Windows 中文系统 Python 默认用 GBK 解码文件,UTF-8 中文文件会报 `UnicodeDecodeError` → 必须显式 `encoding="utf-8"`。

## 三、第 2 步:文本切分(Text Splitters)—— RAG 的灵魂

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=128,    # 每个片段最多 128 字符
    chunk_overlap=50,  # 相邻片段重叠 50 字符
    separators=["\n\n", "\n", "。", "！", "？", "，", "//"]
)
texts = text_splitter.create_documents(
    [documents[0].page_content],
    metadatas=[documents[0].metadata]
)
print(len(texts))  # 35 个片段
```

### 知识点

**1. 为什么要切分?三个理由**

| 理由 | 说明 |
|------|------|
| ① 检索粒度 | 向量检索找的是"最相似的一小段",整篇 8000 字作为整体,问什么都返回同一整篇,检索失效 |
| ② 模型输入上限 | 嵌入模型和 LLM 都有 token 上限,超长必须切 |
| ③ 定位引用 | 切了才能指出"依据第几段" |

> ⚠️ 本项目最初的大 Bug:切好 `texts` 却**没用**,存库时存的是未切分的 `documents`。结果检索返回整篇文档——切分等于白做。

**2. 三个关键参数**
- `chunk_size=128`:片段目标长度。对中文按**字符**计(英文按 token)。太小则片段语义破碎,太大量级大检索噪声多。经验:小文档 100~500,大文档按需。
- `chunk_overlap=50`:相邻片段**重叠**,防止一句话/一个概念正好被切成两半,谁都不完整。经验:约 chunk_size 的 10%~20%。
- `separators=["\n\n", "\n", "。", ...]`:**优先按语义边界切**。它会从列表第一个分隔符开始尝试,切不出再往下。中文场景把标点(`。！？，`)加进去,长句才能被均匀切开。

**3. 递归切分的本质**
`RecursiveCharacterTextSplitter` 是"**从大到小递归**":先按段落 `\n\n` 切,段太长再按 `\n` 切,再长按 `。` 切……直到每块 ≤ chunk_size。**优先保留完整语义单元**,是通用场景的默认选择。

**4. 其他切分器(了解)**
- `CharacterTextSplitter`:纯按字符数硬切,简单但会切断语义
- `TokenTextSplitter`:按 token 数切(和模型计数一致)
- 语义切分(`SemanticChunker`):按 embedding 相似度切,质量高但慢、贵

## 四、第 3 步:向量化(Embedding)—— 文本 → 向量

```python
from langchain_community.embeddings import HuggingFaceBgeEmbeddings

model_kwargs = {'device': 'cpu'}                   # 用 CPU 推理
encode_kwargs = {'normalize_embeddings': True}     # 向量归一化

embedding = HuggingFaceBgeEmbeddings(
    model_name="moka-ai/m3e-small",                # 开源中文嵌入模型
    model_kwargs=model_kwargs,
    encode_kwargs=encode_kwargs,
    query_instruction="为文本生成向量表示用于文本检索"
)
```

### 知识点

**1. Embedding 是什么?**
把文本变成一长串数字(向量),使得**语义相近的文本向量距离近**。

- "藜麦播种方式" 和 "藜麦栽培方法" → 向量近 ✅
- "藜麦播种方式" 和 "今天天气不错" → 向量远 ✅

这解决了**关键词匹配做不到的语义检索**(拼写不同、同义改写也能命中)。

**2. 为什么用 m3e-small?**
- 中文效果好、模型小(~几十 MB)、本机 CPU 可跑,适合学习
- `m3e`(Moka Embedding)是中文嵌入模型系列,还有 `m3e-large`(更好更贵)
- 备选:`text-embedding-ada-002`(OpenAI 闭源)、`bge-*`(BAAI 开源)、`qwen-embedding`(DashScope 也有嵌入接口)

> 学习建议:本地开源模型(如 m3e)免费但首次要从 HuggingFace 下载、还要装 torch,环境重;线上嵌入 API(如 qwen-embedding)开箱即用。

**3. 两个配置参数的含义**
- `model_kwargs={'device':'cpu'}`:传给底层 transformer 模型的参数,`cpu` 指不用 GPU。
- `encode_kwargs={'normalize_embeddings': True}`:向量归一化(单位长度),余弦相似度计算更稳定。
- `query_instruction`:查询指令。**BGE 系列**用「为检索任务生成向量」类提示可提升检索;m3e 官方说不需要,留着无害。

**4. 嵌入模型 vs 对话模型(易混)**
- 嵌入模型(embedding):文本 → 向量,用于**检索**,如 m3e
- 对话模型(LLM):问题 → 回答文本,用于**生成**,如 qwen-plus
- 两者角色不同、互相独立,本项目里各用一个。

## 五、第 4 步:存入向量库(VectorStore)

```python
from langchain_community.vectorstores import Chroma

db = Chroma.from_documents(texts, embedding)   # 关键:存的是切分后的 texts
```

### 知识点

**1. 向量库干什么?**
把每个片段的向量存起来,并建**索引**(如 HNSW),以便快速找"和查询向量最近的 K 个"。

> 没有索引的话,全库逐条算距离也行但太慢;向量库用近似最近邻(ANN)加速。

**2. Chroma 是什么?**
轻量级开源向量库,**pip 安装即可用、无需单独部署**,适合学习与小项目。生产常用的还有:
- `FAISS`:Meta 开源,纯内存,轻快
- `Milvus` / `Weaviate` / `Qdrant`:需服务端部署,支持分布式、海量数据

**3. 修改它的用法就一行**
```python
db = Chroma.from_documents(texts, embedding)          # 本次:内存版
db = Chroma.from_documents(texts, embedding, persist_directory="./chroma_db")  # 持久化
```
持久化后向量库存到磁盘,下次直接加载,不用重新跑前 3 步:
```python
db = Chroma(persist_directory="./chroma_db", embedding=embedding)
```

**4. 从 documents 与 从 texts 的区别(本项目核心 Bug)**
- `Chroma.from_documents(documents, ...)`:整篇 8000 字 → **1 个向量**
- `Chroma.from_documents(texts, ...)`:35 个片段 → **35 个向量**

检索命中粒度 = 入库粒度。**切分结果必须喂给向量库**,否则切分毫无意义。

## 六、第 5 步:相似度检索(Retrieval)

```python
search_result = db.similarity_search("藜一般在几月播种？")
for i, doc in enumerate(search_result):
    print(f"[{i+1}] {doc.page_content[:200]}...")
```

### 知识点

**1. 检索过程(默认 topK=4)**
1. 你的提问 → embedding 模型 → 查询向量
2. 在向量库里找距离最近的 **4 个**片段(默认 `k=4`)
3. 返回 `Document` 列表,每个都带 `page_content`(片段)+ `metadata`

**2. 常用变体**
```python
db.similarity_search(query, k=6)                    # 返回 6 个
db.similarity_search_with_score(query)              # 附带相似度分数
db.similarity_search_by_vector(query_vector, k=4)   # 直接用向量检索
```

**3. Retriever 抽象**
```python
retriever = db.as_retriever()   # 把向量库包装成统一检索接口
# retriever.invoke("藜一般在几月播种？")  # 效果等同 similarity_search
```
`Retriever` 是 LangChain 的统一"检索口",后面问答链传的就是它。好处:换检索方式(向量/关键词/混合/重排序)不改变下游代码。

**4. 你运行时的真实输出对照**
```
[1] 。藜麦种植行距为20～50cm、株/穴距15～30cm效果较好。...
[2] 藜麦播种方式有撒播、条播、穴播或育苗移栽等。通常，中国藜麦栽培多采用条播和穴播的方式...
[3] 。不同地区应依据当地种植的实际情况，选择适宜的播种方式。贵州、河北、新疆等地宜进行条播...
[4] 藜麦生育期内灌水次数和灌水量应依据藜麦长势、种植环境和气候等具体情况而定...
```
问"几月播种",命中的全是"播种"相关段落——**语义检索生效了**。

## 七、第 6 步:检索增强问答(Chain + LLM)

```python
from langchain_openai import ChatOpenAI

api_key = os.getenv("DASHSCOPE_API_KEY")   # 从环境变量读,不写死

llm = ChatOpenAI(
    model="qwen-plus",           # 通义千问
    temperature=0,               # 0 = 最确定性回答
    api_key=api_key,
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1/",
)

retriever = db.as_retriever()
memory = ConversationBufferMemory(memory_key="chat_history", return_messages=True)
qa = ConversationalRetrievalChain.from_llm(llm, retriever, memory=memory)

result = qa.invoke({"question": "藜怎么防治虫害？"})
print(result.get("answer"))
```

### 知识点

**1. 用 OpenAI 兼容协议对接任何大模型**
`ChatOpenAI` 是 OpenAI 的客户端,但**任何厂商只要提供 OpenAI 兼容接口**,换 `base_url` 就能用。本项目用 **通义千问(DashScope)**:
- `base_url`:DashScope 的 OpenAI 兼容端点
- `model="qwen-plus"`:模型名(另有 qwen-max / qwen-turbo / qwen-embedding)
- `api_key`:你的 DashScope API Key(**从环境变量读取**,不写死在代码里)

**2. 问答链内部做了什么?**
```
用户问题 "藜怎么防治虫害？"
        │
        ▼
  [1] 历史记忆(多轮对话时) ──▶ 重新组织成独立问题
        │
        ▼
  [2] retriever 检索 4 个相关片段
        │
        ▼
  [3] 拼成 Prompt:
      system: 仅根据以下资料回答问题...
      context: [片段1][片段2]...
      question: 藜怎么防治虫害？
        │
        ▼
  [4] qwen-plus 生成答案
```

**3. `ConversationBufferMemory` 的作用**
- `memory_key="chat_history"`:链内部用这个 key 存放历史
- 效果:多轮对话时,链会先结合历史重写问题,再检索 → 支持"那病害呢?"这样的追问

**4. `invoke` 的返回结构**
```python
result.keys()   # dict_keys(['question', 'chat_history', 'answer', 'source_documents'])
result["answer"]             # 最终答案文本
result["source_documents"]   # 本次检索到的证据片段(可展示引用)
```

**5. Legacy vs LCEL(1.x 时代的重点)**
你环境是 **langchain 1.2.17**,`ConversationalRetrievalChain` 这类"预包装链"被官方标记为 legacy 并迁移到 `langchain_classic` 包,所以导入是:
```python
from langchain_classic.chains import ConversationalRetrievalChain
from langchain_classic.memory import ConversationBufferMemory
```
**官方推荐的新写法是 LCEL**(LangChain Expression Language),组件用 `|` 拼接,透明可控。见下文第九节。

## 九、进阶:LangChain 1.x 的 LCEL 新写法(推荐掌握)

> 1.x 里 legacy 链被迁移/移除,**推荐用 LCEL 组合式写法**,逻辑更透明、易定制。同样实现"记忆 + 检索 + 问答":

```python
# 1) 先让 LLM 结合历史重写问题(处理追问)
from langchain_classic.chains import create_history_aware_retriever  # 或从 langchain_core 引入
# ⚠️ 1.x 实际导入路径需按环境确认,见下方版本说明

from langchain.chains.history_aware_retriever import ...  # 旧版(0.3)
```

**LCEL 三段式核心代码(概念示意):**
```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

# ① 历史感知检索:把"那病害呢?"重写成带上下文的独立问题
contextualize_prompt = ChatPromptTemplate.from_messages([
    ("system", "把最新问题结合历史改写成独立问题。"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}"),
])
history_aware_retriever = create_history_aware_retriever(
    llm, retriever, contextualize_prompt
)

# ② 生成链:把检索到的片段"塞"进 prompt
qa_prompt = ChatPromptTemplate.from_messages([
    ("system", "仅根据以下资料回答:\n\n{context}"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}"),
])
question_answer_chain = create_stuff_documents_chain(llm, qa_prompt)

# ③ 用 | 组装完整流水线
rag_chain = create_retrieval_chain(history_aware_retriever, question_answer_chain)
answer = rag_chain.invoke({"input": "那病害呢？", "chat_history": [...]})
```

### LCEL 相比 legacy 的优势
1. **`|` 管道式组装**:每一步输入输出显式可见,像 Unix 管道
2. **易插拔**:想加"重排序"或"压缩",在中间插一个组件即可
3. **可流式、可追踪**:支持 `stream()` 流式输出、`get_graph()` 可视化
4. **官方主推**:新功能只加在 LCEL,legacy 链不再维护

### 版本导入差异(易踩坑)
| 写法 | langchain 0.3 | langchain 1.x |
|------|--------------|---------------|
| 预包装问答链 | `from langchain.chains import ConversationalRetrievalChain` | `from langchain_classic.chains import ...` |
| 对话记忆 | `from langchain.memory import ConversationBufferMemory` | `from langchain_classic.memory import ...` |
| LCEL 工厂函数 | `from langchain.chains... import create_history_aware_retriever` | 需按环境确认具体包(可能在 langchain_classic 或独立包) |

> 本项目完整跑通的都是 legacy 写法(仅换包名),因为**逻辑最接近原始代码、改动最小**。想学 1.x 正宗姿势再上手 LCEL。

## 十、常见问题自查表(FAQ)

| 症状 | 原因 | 解决 |
|------|------|------|
| `FileNotFoundError: './藜麦.txt'` | 运行目录不是脚本目录 | `os.path.join(BASE_DIR, "藜麦.txt")` |
| `UnicodeDecodeError: gbk` | Windows 默认 GBK 解码 UTF-8 文件 | `TextLoader(..., encoding="utf-8")` |
| `UnicodeEncodeError: gbk`(print 中文崩) | 终端编码 | 脚本顶部 `sys.stdout.reconfigure(encoding="utf-8")` |
| `ModuleNotFoundError: langchain.chains` | 环境是 langchain 1.x,legacy 链已迁移 | 改从 `langchain_classic` 导入 |
| 检索结果整篇返回、不像片段 | 向量库存了未切分的 documents | `Chroma.from_documents(texts, ...)` |
| 检索结果质量差 | chunk 太大/重叠太小 | 调小 chunk_size、加大 overlap |
| `ModuleNotFoundError: langchain_huggingface` | 新版 embedding 类在独立包 | `pip install langchain-huggingface` |
| 模型下载慢/失败 | 首次从 HuggingFace 拉权重 | 离线下载/换镜像/用线上嵌入 API |
