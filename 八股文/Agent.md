### 4.1 ⭐ 什么是 Agent？和普通的"调一次大模型"有什么区别？

Agent 是以大模型为"大脑"，能**自主规划、调用工具、根据结果决定下一步、循环执行直到完成任务**的系统。
普通调用是"一问一答"一次性；
Agent 是"**感知→思考→行动→观察→再思考**"的循环，能处理需要多步、需要外部能力（查数据库、算数、画图）的复杂任务。

核心四要素：**大模型（规划）+ 工具（Tools）+ 记忆（Memory）+ 循环控制**。


"Agent 一定比直接问强吗？" → "不一定——简单任务上 Agent 是杀鸡用牛刀，更慢更贵更不可控，复杂多步任务才值得上 Agent。"

| **维度** | **普通调用（一问一答）** | **Agent**             |
| ------ | -------------- | --------------------- |
| 交互     | 你发一句它回一句，一次结束  | 感知→思考→行动→观察→再思考，循环到完成 |
| 能力     | 只靠模型脑子里的知识     | 能调外部工具：查数据库、算数、画图     |
| 配置     | 就一个模型          | 大脑(模型)+工具+记忆+循环控制     |
| 啥时候用   | 简单任务           | 复杂多步任务                |
### 4.2 ⭐ Function Calling（工具调用）的原理是什么？

**模型负责"决定调什么、传什么参"，代码负责"执行"，结果再回灌**——模型不会自己执行函数。

 ① 我把可用工具的**名称、功能描述、参数 schema（格式说明书，JSON）** 告诉模型；
 ② 模型理解用户意图后**不直接回答，而是输出一个结构化的调用请求**（调哪个函数、参数是什么）
 ③ **真正执行函数的是我的代码**；
 ④ 把执行结果再喂回模型，它据此生成最终回答或决定下一步。

"工具描述写不好会怎样？" → "模型会**选错工具、传错参**——工具的 description 和参数说明本质是给模型看的 Prompt，得当接口文档一样写清楚。"

关键词串【**报清单·模型决定·代码执行·结果回灌**】
    - 四步：报工具清单（名称+描述+参数 schema）→ 模型输出结构化调用请求 → 我代码执行 → 结果回灌。
    - 模型永远不执行函数，只输出"调用意图"（JSON）；执行和安全校验都在代码侧。
    - 工具的 description 和参数说明 = 给模型看的 Prompt。

### 4.3 ⭐ ReAct 范式是什么？

ReAct = **Reasoning + Acting**，是 Agent 最经典的工作模式：让模型按 **Thought（思考）→ Action（行动/调工具）→ Observation（观察结果）** 循环往复，直到得出 Final Answer（最终答案）。
它的价值是把推理和行动交织——**边想边做、根据真实结果调整**，而不是一次性瞎规划。

- "和 CoT（思维链）什么区别？" → "CoT 只在'脑子里'推理，ReAct 多了**真去调工具拿外部结果**，能接触真实世界。"
- "ReAct 会不会死循环？" → "会——所以必须**设最大步数/超时兜底**"

关键词串【**想·做·看·循环到出答案**】
    - ReAct = Reasoning（思考）+ Acting（行动）。
    - 循环：Thought 想 → Action 调工具 → Observation 看结果 → 再想，直到 Final Answer。
    - 价值：边想边做、拿真实结果调整，不一次性瞎规划。
    - 隐患：可能死循环 → 设最大步数/超时。

### 4.4 ⭐ 工具（Tool）应该怎么设计？

工具设计的好坏直接决定 Agent 成败，我按五条原则来：
	① **单一职责、粒度合适**——一个工具只干一件事，别又取数又画图；
	② **描述清晰**——name 和 description 要让模型一看就懂何时用、参数 schema 要精确，这就是给模型的 Prompt；
	③ **输入输出结构化**——参数和返回都用规整 JSON；
	④ **健壮容错**——参数非法、查无结果要**返回明确错误信息**而不是抛异常崩掉，让模型能据此重试；
	⑤ **安全可控**——涉及写操作/SQL 要做**权限和注入校验**。

- "工具太多模型选不对怎么办？" → "**控制工具数量、拉高描述区分度，必要时分层路由**——先选大类再选具体工具。"
- "返回错误怎么写？" → "**结构化错误信息**——写明错在哪、怎么改，模型能读懂并自我纠正。"

关键词串【**单一职责·描述清晰·结构化·容错·安全**】
    - **单一职责**：一个工具只干一件事（别又取数又画图）。
    - **描述清晰**：name/description/参数 schema = 给模型的 Prompt。
    - **结构化** + 容错：出入都规整 JSON；
    - 出错**返回明确错误**信息别崩，让模型能重试。
    - **安全**：写操作/SQL 做权限与注入校验。

### 4.5 ⭐ 多工具怎么编排？复杂任务怎么拆解？

两种思路。
	**模型自主编排（ReAct）**：让模型每一步自己决定调哪个工具、按观察结果推进——灵活，但不完全可控；
	**预定义流程编排（workflow/图）**：把已知步骤用代码或LangGraph，节点是工具或模型调用——可控、可观测。

实战选法：**流程固定的复杂任务用 workflow，开放探索性任务用 ReAct**，更多是**混用**——大框架固定、局部让模型自主；
	任务太复杂就先让模型做 plan（先列计划）拆解再逐步执行。

|**维度**|**模型自主（ReAct）**|**固定流程（workflow/图）**|
|---|---|---|
|谁定下一步|模型每步现场决定|代码/LangGraph 预先固定|
|优点|灵活、能应变|可控、可观测|
|缺点|不可控、难调试、易跑飞|应付不了开放问题|
|**怎么选**|**开放探索任务**|**流程固定的复杂任务；实战多混用（大框架固定+局部自主），太复杂先 plan 拆解**|

"为什么不全交给模型自主？" → "自主 = 不可控 + 难调试 + 易跑飞
生产更偏好'**可控编排 + 局部自主**'"


### 4.6 ⭐ LangGraph 是什么？解决了什么问题？

LangGraph 是用**图（状态机）来编排 Agent 流程**的框架，解决的是纯 ReAct（边想边干）**黑盒不可控、难调试、易跑飞**的问题。

它把 Agent 流程建模成**节点（Node）+ 边（Edge）+ 共享状态（State）**，支持**条件分支、循环、人工介入节点**；

用图组织后**流程显式、状态可见、每一步走向能精确控制**，还支持回滚和断点续跑，适合做复杂、可控、生产级的 Agent。

对比 LangChain（LLM 开发框架）自带的 Agent，LangGraph 更底层、更可控。

"为什么不用普通 if-else 自己写？" → "简单流程确实能，但状态管理、循环、条件路由、可观测、人工介入这些自己写很繁琐，框架都封装好了——

关键词串【**图编排 · 节点+边+状态 · 可控可观测 · 告别黑盒**】
    - LangGraph = 用图（状态机）编排 Agent 流程的框架。
    - 三件套：节点 Node + 边 Edge + 共享状态 State；支持条件分支、循环、人工介入。
    - 解决：纯 ReAct 黑盒不可控、难调试、易跑飞。
    - 效果：流程显式、状态可见、可精确控制，支持回滚和断点续跑；比 LangChain 自带 Agent 更底层更可控。

### 4.7 Agent 的"记忆（Memory）"怎么做？

Agent 记忆分**短期、长期**，再加一个**工作记忆**，三种各归各管。
	短期记忆是当前对话的最近几轮上下文，太长就**滑动窗口（只留最近 N 轮）或摘要压缩**；
	长期记忆是跨会话的持久知识，常用**向量库存历史**、要用时检索召回，本质又是 RAG；
	工作记忆是执行过程**中的中间结果**（取到的数、上一步输出），要放在 state 里传递。

设计要点：**别把所有历史一股脑塞进上下文**，按需检索 + 摘要压缩控成本。

|**记忆**|**存什么**|**怎么管**|**前端对照**|
|---|---|---|---|
|短期|当前对话最近几轮|滑动窗口（留最近 N 轮）/ 摘要压缩|sessionStorage|
|长期|跨会话持久知识|存向量库、用时检索召回（本质是 RAG）|localStorage / 后端库|
|工作|执行中的中间结果|放 state 里传给下一步|props / state|
|⚠️ 总要点|别把所有历史全塞上下文|按需检索 + 摘要压缩省成本|按需加载、别全量打包|

"多轮越聊越贵怎么办？" → "摘要压缩历史 + 只保留关键信息 + 长期记忆走检索——上下文里永远只放'这一步需要的'，不放'全部聊过的'。"



### 4.8 ⭐ Agent 的错误处理和兜底怎么做？

**Agent 必须假设每一步都可能失败**（工具调用失败、参数错、规划跑飞、死循环），所以要几招兜底：
	① **设最大步数/超时**——防死循环和无限烧钱；
	② **工具层重试**——超时、限流这类可重试错误自动重试、带退避（间隔逐次拉长）；
	③ **错误回灌**——把错误信息结构化喂回模型让它自我纠正，比如 SQL 字段写错就告诉它正确字段重新生成；
	④ **降级兜底**——多次失败就退回人工/给默认回复/老实说"没能完成"；
	⑤ **关键操作加校验和确认**。

"模型一直循环调同一个错误工具怎么办？" → "三件套：步数上限强制刹车 + 检测重复动作 + 把历史错误写进上下文告诉它'这条路试过了'，避免重蹈覆辙。"

关键词串【**限步数 · 重试 · 错误回灌 · 降级兜底 · 假设都会挂**】
    - **限步数/超时**：防死循环、防无限烧钱。
    - **工具层自动重试**：只重试超时/限流这类可重试错误，带退避。
    - **错误回灌**：报错结构化喂回模型让它自改（SQL 字段错 → 给正确字段重新生成）。
    - **降级兜底**：多次失败退人工/默认回复/老实说没完成；核心 = 假设每一步都可能失败。

### 4.9 ⭐ Agent 和 RAG 是什么关系？怎么结合？

结论先说——它俩不对立，**RAG 可以当成 Agent 的一个工具**：RAG 解决"知识从哪来"（检索增强），Agent 解决"任务怎么一步步完成"（规划+行动）。

结合方式是把"知识库检索"封装成 Agent 的一个工具，Agent 需要事实知识时**自己决定**去调 RAG 检索，再配合其他工具（算数、画图）完成复杂任务
	比如先 RAG 查公司制度、再调工具算数据、最后生成报告。
	这种 Agent 自主决定**要不要检索、检索几次、要不要重写查询**的玩法，叫 **Agentic RAG**。

|**谁**|**管哪一段**|**一句话身份**|
|---|---|---|
|RAG|知识从哪来（检索增强）|Agent 工具箱里的一件工具|
|Agent|任务怎么一步步完成（规划+行动）|调度所有工具的干活主体|
|Agentic RAG|Agent 自主决定要不要检索、检索几次、要不要重写查询|两者结合的玩法|

"什么时候只用 RAG 不上 Agent？" → "纯知识问答 RAG 就够；要多步操作、调工具才上 Agent"

**🎯 背诵要点（就背这几个）**：关键词串【**RAG是工具 · 各管一段 · 按需调用 · Agentic RAG**】

### 4.10 ⭐ Text2SQL 的原理和坑？（P2 核心）

Text2SQL 就是让模型**把自然语言问题翻译成 SQL**：把**数据库表结构（schema：表名、字段、注释）+ 用户问题**一起喂给模型生成 SQL，我的代码执行后拿结果。

坑主要四类：
	① 模型不知道你的表长啥样——**必须把 schema 喂给它**；
	② 字段/表名猜错——给**字段注释 + few-shot 示例**（给几个范例）锚定；
	③ 复杂 join/聚合容易错——限定查询范围、给示例；
	④ 最致命的是 **SQL 注入和越权风险**——用只读账号、表/字段白名单、SQL 校验，**绝不能让模型生成的 SQL 直接裸跑**。

"安全怎么保证？（这条几乎必问，背死）" → "四道锁：只**读**权限 + 表/字段**白名单** + **禁止** DROP/DELETE 等危险语句 + 参数校验——模型生成的 SQL 一律过校验层，绝不裸跑。"

关键词串【**喂schema · 字段注释/示例 · 安全校验 · 错误重试**】
    - 原理：schema（表名/字段/注释）+ 用户问题 → 模型生成 SQL → 代码执行拿结果。
    - 防猜错：字段注释 + few-shot 示例锚定；复杂 join/聚合限定范围、给示例。
    - 安全（必背）：只读账号 + 表/字段白名单 + 禁 DROP/DELETE + SQL 校验，绝不裸跑。
    - 出错：报错回灌让模型改写、限 N 次；仍失败就降级提示用户。

### 4.11 多 Agent 协作是什么？什么场景需要？

多 Agent 协作就是把一个复杂任务拆给多个各有分工的 Agent 协作完成。

常见三种模式：
	① **主从（Supervisor）**——一个主 Agent 调度多个专家子 Agent，比如规划 Agent + 取数 Agent + 画图 Agent；
	② **流水线**——按阶段串行接力；
	③ **辩论/反思**——多个 Agent 互相**审查**提升质量。

适用场景：单个 Agent 工具太多、职责太杂、上下文撑不下时，拆分能各管一摊、更可控。但代价是更复杂、更慢、更贵，**别为了用而用**。

"和单 Agent 多工具有啥区别？" → "单 Agent 适合工具不多的任务；多 Agent 适合职责差异大、需要专精和隔离上下文的复杂任务"

关键词串【**拆分工 · 主从/流水线/辩论 · 职责重才上 · 别滥用**】
    - 定义：把复杂任务拆给多个各有分工的 Agent 协作完成。
    - 三模式：主从（主调度多专家）/ 流水线（串行接力）/ 辩论（互相审查）。
    - 时机：单 Agent 工具太多、职责太杂、上下文塞不下才拆。
    - 代价：更复杂、更慢、更贵——别为了用而用。

### 4.12 ⭐ Agent 怎么评估？比 RAG 难在哪？
Agent 评估比 RAG 难，难在它是**多步过程**，要评的不只是最终答案。
维度有五个：
	① **任务完成率/成功率**（最终有没有正确完成）；
	② **工具调用准确率**（该不该调、选对没、参数对没）；
	③ **步骤效率**（用了几步、有没有绕路、有没有死循环）；
	④ **轨迹质量**（推理路径合不合理）；
	⑤ **成本和延迟**。
	方法：**建任务测试集跑端到端成功率** + 用 LLM-as-judge（模型当裁判）评轨迹 + 关键节点埋点观测。
		难点在于**中间步骤对、最终也可能错；最终对、过程也可能瞎蒙**——所以要看全过程。

"那 Agent 出问题怎么调试？" → "用类似 LangSmith（追踪平台）这类工具做全链路追踪；"

关键词串【**看全过程 · 成功率 · 工具准 · 步骤效率 · 轨迹质量 · 成本延迟**】
    - 难在多步：中间对最终可能错、最终对可能瞎蒙 → 必须看全过程。
    - 五维度：成功率、工具调用准确率、步骤效率、轨迹质量、成本延迟。
    - 方法：任务测试集端到端 + LLM-as-judge 评轨迹 + 关键节点埋点。

### 4.13 Agent 太慢/太贵怎么优化？

Agent 多步调用天然慢且贵，优化六招：
	① **减少步数**——能用固定 workflow（预设流程）就别全自主，简单任务不上 Agent；
	② **分层用模型**——规划用强模型，简单子任务用便宜小模型；
	③ **并行化**——无依赖的工具调用并发执行；
	④ **缓存**——重复的检索/工具结果缓存复用；
	⑤ **及早终止**——设步数上限、置信度（把握程度）够了就停；
	⑥ **精简工具数量和上下文**。
核心一句：**该确定的流程用代码固定，模型只用在真正需要判断的地方**。

"并行不会乱吗？" → "只并行**无依赖**的步骤，有依赖的必须串行"

关键词串【**减步数 · 分层模型 ·** **并行** **· 缓存 · 该固定就固定**】
    - 减步数：能固定 workflow 就别全自主，简单任务不上 Agent。
    - 分层用模型：规划用强模型，简单子任务用便宜小模型。
    - 并行无依赖调用 + 缓存重复结果 + 设步数上限及早终止。
    - 核心：确定的流程代码固定，模型只用在要判断的地方。
    - 加分项：⑤及早终止、⑥精简工具和上下文不强背——答出前四招即过关，想起故事里"到点先交活、收走没用的工具"就能带出来。

### 4.14 怎么防止 Agent 做出危险/越权操作？

核心原则先说：**永远不要完全信任模型的输出去执行有副作用的操作**——Agent 能调工具就有"行动力"，必须管控。
具体五招：
	① **最小权限**——工具只给必要权限，比如数据库只读；
	② **人工确认（Human-in-the-loop，人工把关）**——删数据、发邮件、下单这类高风险操作必须人工审批；
	③ **工具白名单 + 参数校验**——不让模型生成的裸命令/SQL 直接执行；
	④ **沙箱**（隔离环境）——代码执行类工具放沙箱里隔离跑；
	⑤ **审计日志**——所有动作可追溯。

"有人用 Prompt 注入（夹带恶意指令）诱导 Agent 干坏事呢？" → "防线放在工具层：**权限和校验兜底**、关键操作加**人工确认**——**不靠模型自觉**，就算注入成功了，它也没权限干成坏事。"

关键词串【**最小权限 · 人工确认 · 白名单校验 ·** **沙箱** **· 审计日志**】

### 4.15 ReAct 和 Plan-and-Execute 有什么区别？

都是 Agent 工作范式，区别一句话：**ReAct** **走一步看一步，Plan-and-Execute 先列完整计划再执行**。

展开说：
	ReAct 每次只想下一个动作，根据观察结果再决定下一步——灵活、能应对变化，但可能绕路、步数多；
	Plan-and-Execute 先一次性把整个计划（任务分解）列出来，再按计划逐步执行——更有全局观、步数更省、更可控，但计划赶不上变化时要 replan（重新规划）。

实践常结合：先 plan 出大步骤，每步内部用 ReAct 应对细节。

|**维度**|**ReAct（边想边做）**|**Plan-and-Execute（先列后干）**|
|---|---|---|
|干活方式|走一步看一步，每次只想下一个动作|先列完整计划，再逐步执行|
|优点|灵活、能应对变化|有全局观、步数省、更可控|
|缺点|可能绕路、步数多|计划赶不上变化，要 replan|
|适合|探索性强的任务|流程清晰的任务|

"生产环境用哪个？" → "流程清晰的任务用 Plan-and-Execute 更可控，探索性强的用 ReAct，看场景——P2 主干流程清晰所以偏 Plan，步内容错才用 ReAct。"

**🎯 背诵要点（就背这几个）**：关键词串【**ReAct** **走一步看一步 · Plan 先列全套 · 灵活 vs 省步 · 常结合**】

### 4.16 ⭐ Agent 的基本架构由哪些核心组件构成

**四大组件**协作构成、缺一不可——

- ① **LLM** **核心（大脑）**：负责理解任务与决策，由 System Prompt（系统提示词）定义角色；模型选型影响推理能力、工具调用稳定性和上下文窗口。
- ② **工具系统（执行者）**：Agent 与外界交互的**唯一入口**——搜索、数据库、代码执行、API 都算。
	- 核心原则是"**决策-执行分离**"：
		- 模型只输出工具名和参数、程序负责实际执行；
		- 工具描述质量直接影响表现；
		- MCP（Model Context Protocol，模型上下文协议）负责工具的标准化接入。
- ③ **记忆系统（档案室）**：
	- 短期存当前任务的中间状态，
	- 长期用向量库存语义、情节、程序性记忆，还要做重要性评估与衰减（旧记忆淡出）。

- ④ **规划模块（项目经理）**：把复杂目标拆成可执行步骤，方法含 **CoT/ToT、Plan-and-Execute/ReAct**。

- 收尾一句：四者形成"**规划→决策→执行→记忆**"的循环。

"为什么要强调'决策-执行分离'？" → "为了安全可控——模型可能幻觉，让它只输出工具名和参数，程序校验完再真正执行，避免直接放权造成误删数据这类风险。"

关键词串【**大脑决策 · 工具执行 · 记忆存取 · 规划拆解 · 决策执行分离**】
    - LLM 核心=大脑：理解+决策，System Prompt 定角色；选型看推理、工具调用稳定性、上下文窗口。
    - 工具系统=与外界交互唯一入口；模型只出工具名+参数、程序真执行；MCP 管工具标准化。
    - 记忆系统：短期存中间状态、长期向量库存三类记忆；规划模块把目标拆成可执行步骤。
    - 四者成"规划→决策→执行→记忆"循环。

### 4.17 ⭐ ReAct、Plan-and-Execute、Reflection 三种范式的区别与选型

三者解决的是**不同问题**，不是三选一
	ReAct 管"思考→行动→观察"的单步迭代，
	Plan-and-Execute 管"先列完整计划再分步执行"的复杂任务，
	而 **Reflection 不是独立范式**，是叠加在前两者上的"生成→评估→改进"质检闭环。

工程上常**混合使用**；成本上"**规划用强模型 + 执行用弱模型**"可降本 70~90%。



"ReAct 和 Plan-and-Execute 能结合吗？" → "能——主流程用 Plan 拆解保全局，单步执行用 ReAct 灵活处理，再配动态 Replan，兼顾全局视角和临场灵活。"

关键词串【**ReAct边干边看 · Plan先列计划 · Reflection质检buff · 强规划弱执行 · 常混合**】

### 4.18 ⭐ Agent 的长短期记忆系统设计与存储

Agent 记忆是**两层架构**。
	**短期记忆**是当前任务的工作台：维持完整的对话消息列表（user/assistant/tool），每次调 LLM 都传完整历史让模型理解进度，**任务结束即清空**。**
	长期记忆**是跨任务知识库：用"**向量库 + Embedding**"建语义索引，检索时把 query 转成向量、算相似度返回 Top-K（前K条），克服关键词不重叠的问题。
		长期记忆按内容分三类：
			**语义记忆**存事实知识（如用户偏好）、**情节记忆**存具体事件经历、**程序记忆**存处理流程和最佳实践。
			**存储粒度**取"一次完整交互"或"一个独立知识点"——太碎检索到的内容不完整、太粗会引入噪音。
			配合流程：**任务前**检索长期记忆注入 Prompt、**任务中**维持短期工作台、**任务后**沉淀重要结论。

"为什么用向量检索而不是关键词？" → "用户的问法和存储时的措辞常常字面不重叠，向量按语义相似度召回，能把'表意相关但用词不同'的记忆找出来——和 RAG 用向量库是同一个理由。"

关键词串【**短期工作台** **· 长期向量库 · 语义情节程序 · 粒度适中**】
    - 短期=当前任务工作台：完整消息列表，每次全量传给 LLM，任务结束清空。
    - 长期=跨任务知识库：向量库+Embedding，query 转向量算相似度返回 Top-K。
    - 三类长期记忆：语义（事实知识）、情节（事件经历）、程序（流程/最佳实践）。
    - 粒度取"一次完整交互 / 一个独立知识点"：太碎不完整、太粗有噪音。

### 4.19 Agent 记忆压缩有哪些方法

硬约束是上下文窗口有限，历史必须压。
	四类方法按"**历史怎么截→内容怎么挑→载体是否最优**"递进：**滑动窗口、摘要压缩、重要性过滤、结构化抽取**，工程最佳实践是**滑动窗口 + 摘要的组合**。
	另外要分清：**Prompt Caching**（前缀缓存）是**计算层**优化、不减少信息量，与压缩是**互补不是替代**。

|**方法**|**核心思路**|**要点/短板**|
|---|---|---|
|① 滑动窗口|只留最近 N 轮|极简；硬截断丢关键决策，适合短对话|
|② 摘要压缩|丢弃前先用 LLM 总结|保脉络；有额外调用与细节丢失；进阶=分层摘要（近 10 轮留原文/中期压缩/远期精炼）|
|③ 重要性过滤|按价值打分筛（规则关键词或 LLM 打分），不按时间|进阶=观察遮蔽（动态隐藏非删除、可重现）+ 主动压缩（工具返回立即压）|
|④ 结构化抽取|信息提炼成字段存（"预算5万""已确认方案B"）|密度最高；需预定义字段、通用性低|
|对照：Prompt Caching|缓存固定前缀，费用约降到 1/10|计算层优化、不减信息量，与压缩互补非替代|

"Prompt Caching 算记忆压缩吗？" → "不算——它在计算层不在信息层，不减少信息量、只省重复计算的成本，可以和压缩同时用。"

关键词串【**滑动窗口 · 摘要压缩 · 重要性过滤 · 结构化抽取 · Caching是互补**】

### 4.20 ⭐ 如何赋予 LLM 规划能力（CoT/ToT/GoT）

本质是"**把隐式推理显式化**"——LLM 默认一口气出答案，多步任务容易跳步，规划就是逼它把推理写出来。
三个方法**递进**：CoT 一条链、ToT 一棵树、GoT 成图；
工程上最常用 **Plan-and-Execute**：分离规划与执行、先产出完整计划再逐步执行并动态调整，比 ReAct 的即时决策**更有全局视角**。

|CoT 思维链|一条链，加一句"一步步思考"逼它写出来|无——单链走错就全错|零成本（加句提示词）|
|---|---|---|---|
|ToT 思维树|多路径：生成→评估→剪枝|有|调用增 3~5 倍|
|GoT 思维图|树升级为图，中间结论可合并复用|有|主要在学术阶段|
|Plan-and-Execute|先出完整计划，再逐步执行+动态调整|可动态调整|工程最常用，比 ReAct 即时决策更有全局视角|

"任务分解和 CoT/ToT 是什么关系？" → "任务分解是规划要达成的目标——把大目标拆成可执行子步骤；CoT/ToT/Plan-and-Execute 是实现分解与推理的具体方法。"

关键词串【**隐式变显式 ·** **CoT一条链 · ToT一棵树 · GoT成图 · 工程用Plan**】

### 4.21 ⭐ Agent 的反思机制、必要性及实现

反思是"**生成→评估→改进**"的结构化闭环，**不是随机重试**。
必要性：LLM 首次输出常有逻辑跳跃、细节遗漏、事实错误，给它一次回头检查的机会，它就能自己发现并修正。
核心实现是 **Self-Refine**（自评自改）：评估 Prompt 要给**明确检查维度**——事实、逻辑、完整性、表达——而不是让它自由发挥，并且要设 **"PASS"出口**防无限优化；改进 Prompt 必须同时传**三要素：原始任务 + 当前输出 + 评估意见**。
粒度两种：
	**步骤级**每步即查、发现早但调用翻倍；**任务级**整体评估、开销小但可能浪费前期工作。

进阶有 Reflexion（存失败经验）、LATS（结合蒙特卡洛树搜索，多路试错）、**多 Agent 互评**——独立 Critic（评审员）比自我反思好、能避免自洽偏见（自己骗自己）。工程关键：**硬性设最大 2~3 轮**防死循环，且每轮反思都是成本，**只用在质量要求高、错误代价大的关键节点**。

"为什么多 Agent 互评比自我反思好？" → "自我反思容易'自洽'地认可自己的错误；独立 Critic 视角不同，更容易发现盲区。"

关键词串【**生成→评估→改进 · 检查维度+PASS出口 · 改进传三要素 · 硬限2~3轮 · 关键节点才用**】
    - 追问备料：粒度两种——步骤级发现早但调用翻倍 / 任务级开销小但可能白干前期；进阶只记三个名字：Reflexion 存经验、LATS 多路试错、多 Agent 互评防自洽（细节📕范本里都有，不用重背一遍）。

### 4.22 ⭐ 多 Agent 的协作与动态切换机制

多 Agent 协作要解决两件事：**信息怎么传、活儿派给谁**。
协作架构三类：
	**流水线**（固定顺序）、**层级**（Orchestrator 分配收集）、**协商**（辩论达成一致）。
**通信两种**：
	消息传递——结果发到消息队列（异步信箱）、下游订阅，解耦但需要中间件（消息中转站）；
	共享状态——所有 Agent 读写同一个状态对象，LangGraph 就是这种，高效但需要写入规则防覆盖。
**状态管理**：核心是**只追加不覆盖、做增量合并**（必背）；全局 + 局部分层、把失败信息也写进状态供后续决策（加分项，晨测不考）。
**切换/路由三种**：
	静态路由规则写死，高效、可预测、易调试，但覆盖不了边缘情况；
	动态路由交给 LLM 判断，灵活但多一次调用、不可预测；
	Handoff（接力交棒）去中心化，当前 Agent 自己决定交给谁，没有中央瓶颈但容易成环、要防循环。
	**最佳实践是混合：主流程静态路由保底、边缘情况才动态兜底**。

| **机制**  | **是啥**                  | **优点**     | **缺点**     |
| ------- | ----------------------- | ---------- | ---------- |
| 消息传递    | 结果发消息队列、下游订阅            | 解耦         | 需要中间件      |
| 共享状态    | 都读写同一状态对象（LangGraph 即此） | 高效         | 需写入规则防覆盖   |
| 静态路由    | 规则写死谁接谁                 | 高效、可预测、易调试 | 盖不住边缘情况    |
| 动态路由    | 交 LLM 现场判断              | 灵活         | 多一次调用、不可预测 |
| Handoff | 当前 Agent 自己决定交给谁        | 无中央瓶颈      | 易成环、要防循环   |

"共享状态怎么防多 Agent 写冲突？" → "明确写入规则 + 只追加不覆盖、由框架做增量合并，每个 Agent 只写自己负责的字段。"

关键词串【**流水线/层级/协商 · 消息传递vs共享状态 · 静态vs动态vsHandoff · 只追加不覆盖 · 主静态边缘动态**】

### 4.23 ⭐ Single-Agent 和 Multi-Agent 的设计方案

我的原则是**渐进式演进：先用 Single-Agent 验证、发现真实瓶颈再拆 Multi**。
	Single-Agent = **LLM** **+ 工具集 + 决策循环**，单个 Agent 迭代调工具，架构简单、全程可控、排查快，适合流程清晰、不太长、信息量适中的任务。
	**三种情况它力不从心才上 Multi**：context 撑爆开始遗忘、需要完全不同的专业能力、有多个可并行的独立子任务。

Multi-Agent **推荐中心化方案 Orchestrator + Worker**：
	Orchestrator 拆解目标、动态分配、汇总结果，有静态路由 / 动态规划 / 自适应编排三种变体，可控、链路清晰、好调试。
	**去中心化方案**（Agent 自行协商、无中央调度）主要停留在学术阶段——任务重复分配、执行顺序无保证、失败无感知，几乎所有正经项目都选 Orchestrator 模式。

|Single-Agent|LLM + 工具集 + 决策循环|简单、可控、排查快|流程清晰、不太长、信息量适中；**先用它验证**|
|---|---|---|---|
|Multi 中心化（推荐）|Orchestrator + Worker（静态路由/动态规划/自适应编排）|可控、链路清晰、好调试|三信号出现才拆：context 爆 / 需完全不同专业 / 可并行|
|Multi 去中心化|Agent 自行协商、无中央调度|重复分配、顺序无保证、失败无感知|别用——主要停留学术，正经项目都选 Orchestrator|

"什么时候必须从 Single 拆成 Multi？" → "三种信号出现之一：context 撑爆开始遗忘、需要完全不同的专业能力、有可并行的独立子任务——没有这些信号就不拆。"

关键词串【**LLM+工具+循环 · 三信号才拆 · Orchestrator+Worker · 去中心化停学术 · 先单后多渐进**】

### 6.1 ⭐ 什么是 MCP（模型上下文协议）？解决什么问题？

MCP，Model Context Protocol、模型上下文协议，是一个**开放标准协议**，规范"大模型/Agent 怎么连接外部工具和数据源"。
做法是把每个工具/数据源做成标准化的 **MCP Server**（工具服务端），模型客户端按统一协议去**发现、调用**它们。

它解决的痛点：以前用 Function Calling，每接一个工具都要在应用代码里手写一套、各家不通用、没法复用；MCP 把"工具服务端"和"模型客户端"**解耦**——工具一次做成标准 Server，任何支持 MCP 的客户端都能用，相当于"**给 AI 工具定义了** **USB-C** **接口**"。
2025 年 12 月 MCP 被捐给 Linux 基金会成为开放标准，2026 已是**事实标准**。

"MCP 提供哪些能力？怎么通信？" → "三类能力：工具 Tools、资源 Resources、提示模板 Prompts，外加标准的工具发现机制；通信本地用 stdio（子进程管道），远程用 Streamable HTTP（早期 HTTP+SSE 双端点已弃用）。"

关键词串【**统一接口标准 · 工具做成 Server ·** **解耦可复用 · AI 界** **USB-C**】
    - 追问备料：能力 = Tools / Resources / Prompts + 工具发现机制；通信 = 本地 stdio、远程 Streamable HTTP。
    - 白话对照：stdio 就是本地俩程序用管道直接说话，Streamable HTTP 就是走网络的普通 HTTP 请求

### 6.2 ⭐ MCP 和 Function Calling 的本质区别？要接 10 个工具用哪个？

先说结论：**不是替代关系，是不同层次**。
**Function Calling 是模型层能力**——模型按 schema（参数格式）输出"要调哪个函数、传什么参"，但工具怎么实现、怎么对接**和应用代码强耦合**，换项目要重写。
**MCP 是协议/标准层**——把工具做成独立、可复用的 Server，与模型解耦，可独立部署、团队共享、跨应用复用。
所以怎么选：**单应用、几个工具 → Function Calling 直接写；要接很多工具、要团队/多应用复用、要标准化治理 → 用 MCP**。一句话：Function Calling 是"模型会调函数这件事"，MCP 是"工具怎么标准化对外提供"。

| **维度** | **Function Calling** | **MCP**                      |
| ------ | -------------------- | ---------------------------- |
| 层次     | **模型层**能力            | **协议/标准层**                   |
| 耦合     | 与应用代码焊死、换项目重写        | 与模型解耦、独立部署、团队共享、跨应用复用        |
| 适用     | 单应用、几个工具             | 工具多、要复用、要标准化治理               |
| 一句话    | "模型会调函数这件事"          | "工具怎么标准化对外提供"（底层仍靠模型的工具调用能力） |

"MCP 底层还是靠模型的工具调用能力吗？" → "是——MCP 规范工具的提供与发现，模型侧仍通过工具调用去用它们，两者是协作不是互斥。"

【**模型层 vs 协议层 · 焊死 vs 可复用 · 几个就 FC · 多且复用上 MCP**】
### 6.3 ⭐ Skills 是什么？和 System Prompt / Few-shot 有什么区别？

Skill 是把"某类任务的做法"封装成**可复用、按需加载**的能力包——里面有说明、步骤、示例，甚至配套脚本和资源，Agent 需要时才加载，而不是把所有本事堆进一个超长 system prompt。
三者区别：
	**System Prompt** 是全局常驻的人设规则，越长越稀释重点、还一直占上下文；
	**Few-shot** 是临时塞几个示例；
	**Skill** 是**模块化、按需加载**的技能单元——要做 A 任务就加载 A Skill，平时不占上下文，能力可组合、可单独维护。
	类比：system prompt 是"岗位职责"，few-shot 是"随手举例"，Skill 是"按需翻开的专项操作手册"。

|**机制**|**什么时候在场**|**特点**|
|---|---|---|
|System Prompt|全程常驻|人设 + 全局规则；越长越稀释重点、一直占上下文|
|Few-shot|临时塞进本次对话|几个示例引导格式/风格|
|Skill|**按需加载**、用完不常驻|能力包（说明+步骤+示例+脚本）；平时不占上下文、可组合、可单独维护|

"为什么不全塞 system prompt？" → "上下文有限、且越长越糊——按需加载更省、更准、更好维护。"

关键词串【**能力包 · 按需加载 · 不占上下文 · 可组合可维护**】

### 6.4 ⭐ Function Calling、MCP、Skills 三者区别与协作（一个比喻讲清）

三者各管一摊，分别解决"**怎么做（Skills）、接什么（MCP）、怎么调（Function Calling）**"。用"人做事"一比就清楚——**Function Calling 是手**，模型动手调工具的基本能力；**MCP 是标准插座/接口**，各种外部工具用统一标准接进来、即插即用、可复用；**Skills 是专项操作手册**，教模型某类任务怎么一步步做、按需翻阅。协作起来：Agent 靠 Skills 知道"这类活怎么干"，通过 MCP 把一堆工具标准接进来，再用 Function Calling 真正动手调用。

|**谁**|**管哪一摊**|**比喻**|**一句定位**|
|---|---|---|---|
|Function Calling|**怎么调**——模型动手调工具的基本能力|工人的手|"模型会调函数这件事"|
|MCP|**接什么**——工具按统一标准接入、即插即用、可复用|墙上标准插座|"工具怎么标准化对外提供"|
|Skills|**怎么做**——某类任务的步骤打包、用到才翻|施工手册|"按需加载的操作手册"|

"实际项目里三个都用上了吗？" → "不用都上——工具多、要跨项目复用才上 MCP，任务类型多、要可维护再上 Skills，按规模演进才是懂取舍。"

关键词串【**怎么做 Skills · 接什么** **MCP** **· 怎么调** **FC** **· 手册/插座/手**】

### 6.5 ⭐ A2A 协议是什么？和 MCP 什么关系？

A2A（Agent-to-Agent）是规范**多个 Agent 之间怎么互相通信、协作、分配任务**的协议。它和 MCP 是分工互补——**MCP 管"Agent 怎么连工具和数据"（Agent↔工具），A2A 管"Agent 怎么和别的 Agent 合作"（Agent↔Agent）**，一个是对工具的接口，一个是对同伴的接口，互补不冲突。
多 Agent 系统里常一起用：每个 Agent 用 MCP 接自己的工具，Agent 之间用 A2A 协作。

|**协议**|**连谁**|**一句定位**|**前端记忆钩**|
|---|---|---|---|
|MCP|Agent ↔ 工具/数据|对**工具**的统一接口|按规范调后端 API|
|A2A|Agent ↔ Agent|对**同伴**的沟通协议|微前端子应用间的通信约定|

"为什么 MCP 解决不了 A2A 的事？" → "MCP 是把对方当'工具'来调，缺少 Agent 之间的对等协作、任务协商和状态同步——所以要另立 A2A，两者各管一段。"

关键词串【**Agent 对 Agent ·** **MCP** **连工具 / A2A 连同伴 · 互补不冲突**】

### 6.6 ⭐ Agent 和 Workflow（工作流）有什么区别？怎么选？

一句话：**Workflow** **流程预先定死**——开发者把步骤、分支、顺序固定好，模型只在某些节点出力，可控、可预测、好调试、便宜；
**Agent 由模型自主决策**——自己决定下一步做什么、调什么工具、要不要循环，灵活、能应对开放任务，但不可控、难调试、更慢更贵。
怎么选：**流程清晰固定、步骤可枚举 → Workflow；任务开放、路径不确定、要随机应变 → Agent**。
生产里最常见的是"**Workflow 为骨架 + 局部 Agent 自主**"。

|**维度**|**Workflow**|**Agent**|
|---|---|---|
|流程谁定|开发者提前定死，模型只在节点出力|模型自主决定下一步/调什么工具/要不要循环|
|优点|可控、可预测、好调试、便宜|灵活、能应对开放任务|
|缺点|死板，接不住开放任务|不可控、难调试、更慢更贵|
|适用|流程清晰固定、步骤可枚举|任务开放、路径不确定|
|生产常态|当**骨架**|嵌在骨架里**局部自主**|

关键词串【**定死 vs 自主 · 可控便宜 vs 灵活贵 · 固定走** **Workflow** **/ 不确定上 Agent · 骨架+局部自主**】

### 6.7 ⭐ 什么时候"手搓 Agent"、什么时候用成熟框架？

核心一句：**别为了用框架而用框架，理解原理后按需选**。**框架**（LangChain / LangGraph / LlamaIndex）适合快速起步、标准场景、复杂编排——记忆、工具、编排、追踪都封装好了，省事；缺点是黑盒、定制难、版本变动大、有时偏重。

**手搓**——自己用模型 API 加几个函数写个循环——适合逻辑简单、要极致可控可调试、依赖要轻的场景；其实很多生产里的 Agent 就是"**一个清晰的循环 + 几个工具**"。判断标准：原型验证 / 复杂编排 → 框架；逻辑可控、要透明可维护、依赖要轻 → 手搓。

"那框架不就白学了？" → "不白学——框架体现的是 Agent 的标准模式（ReAct、记忆、工具），理解它之后再决定用不用；就算手搓，也是照这些模式写。"

关键词串【**框架省事但黑盒 · 手搓可控轻量 · 复杂上框架 / 简单手搓 · 别为框架而框架**】

- 判断一句：原型 / 复杂编排 → 框架；逻辑简单要透明 → 手搓。

### 6.8 ⭐ Agentic RAG 是什么？和传统 RAG 有什么区别？

传统 RAG 是"先检索后生成"的**固定流水线**——不管什么问题都"检索一次 → 拼接 → 生成"；**Agentic RAG 是把检索变成 Agent 手里的一个工具，让模型自己当"检索调度员"**——自主决定要不要检索、检索几次、检索什么、要不要改写查询、结果不好要不要重来、甚至换个知识库或上网搜。它能处理传统 RAG 搞不定的多跳（连查多步）/多实体/多轮问题，代价是更慢、更贵、更难控。

- **❓最可能追问 → 一句反杀**："那它和 Self-RAG / CRAG 什么关系？" → "可以看作 Agentic 思路的具体实现——Self-RAG 管'要不要搜'的自我反思，CRAG 管'搜错了先纠正'，需要的话我可以各展开一句。"

- **🎯 背诵要点（就背这几个）**：关键词串【**传统=定死流水线 · Agentic=检索变工具 · 模型自主决定检索几次 · 搞定多跳**】

- 代价一句：更慢、更贵、更难控——换来多跳 / 多实体 / 多轮问题能答。

### 6.9 GraphRAG / Self-RAG / Corrective RAG / CAG 都是什么？（了解级，能各说一句）

- **📕 面试范本（照这个节奏说）**：这四个都是 2024-2025 的 RAG 进阶范式，照下表每行各说一句就够：

- **GraphRAG / LightRAG**——用知识图谱（实体关系网）组织知识，检索时顺着实体关系找，擅长"多跳、多实体关联"问题，纯向量检索答不好的它行。

- **Self-RAG**——让模型自我反思：边生成边判断"要不要检索、搜到的相不相关、答案有没有依据"，按需检索。

- **Corrective RAG（CRAG）**——检索后先评估文档相关性，不相关就触发重检索或上网搜再生成，纠正"检索错了还硬答"。

- **CAG（Cache-Augmented Generation）**——知识库小、上下文够长时，把全部知识一次塞进上下文 + KV 缓存（推理缓存），省掉检索、图个低延迟；它和 RAG 的取舍是"知识量 vs 延迟/成本"。

|**流派**|**一句定位**|**记忆钩（前端味）**|
|---|---|---|
|GraphRAG / LightRAG|知识图谱组织知识、顺关系检索，擅长多跳/多实体关联|查关系图谱顺藤摸瓜|
|Self-RAG|模型自我反思：要不要搜、相不相关、有没有依据，按需检索|写代码自带 lint 边写边自查|
|CRAG|搜完先评文档相关性，不行就重搜/上网再生成|返回先校验，不合格重试换接口|
|CAG|知识小+上下文长：全塞上下文 + KV 缓存，省检索低延迟|数据小全量缓存进内存|

- **❓最可能追问 → 一句反杀**："你项目会用哪个？" → "P1 后续想上 Agentic RAG 做多跳；知识量小的子场景，比如单只基金的固定资料，可以用 CAG 降延迟——点到为止。"

- **🎯 背诵要点（就背这几个）**：关键词串【**Graph=关系图谱多跳 · Self=自我反思按需搜 · CRAG=搜完先验不行重搜 · CAG=小知识全塞缓存**】（上表**即**要点）

### 6.10 ⭐ RAG Triad（评估三元组）是什么？

- **📕 面试范本（照这个节奏说）**：RAG Triad 是**评估 RAG 质量的三个核心维度**，也是 RAGAS（RAG评估工具）这类工具的核心思想：① **Context Relevance 上下文相关性**——**检索到的资料**和问题相不相关（查检索质量）；② **Faithfulness 忠实度**——答案是否**忠于检索资料**、有没有脱离资料瞎编（查幻觉）；③ **Answer Relevance 答案相关性**——答案**切不切题**。三个一起看能定位问题出在"检索"还是"生成"：上下文不相关→检索的锅；上下文相关但忠实度低→生成的锅。三个分都可以用 LLM-as-judge（让模型当裁判）自动打。

- **❓最可能追问 → 一句反杀**："和召回率什么关系？" → "召回率只看'该找的找到没有'，Triad 更全面——检索准不准、生成忠不忠实、答得切不切题一起量。"

- **🎯 背诵要点（就背这几个）**：关键词串【**料相关 Context · 忠于料 Faithfulness · 答切题 Answer · 定位检索还是生成**】

    - Context Relevance = 检索的资料和问题相关（查检索质量）——先查这把尺。

    - Faithfulness 忠实度 = 答案忠于检索资料、不脱离资料瞎编（查幻觉）。

    - Answer Relevance = 答案切题。

    - 定位法：料不相关→检索的锅；料相关但不忠实→生成的锅。

    - 三个分可用 LLM-as-judge 自动打。

### 6.11 大模型网关（LLM Gateway）解决什么问题？

- **📕 面试范本（照这个节奏说）**：网关解决的是**多模型接入的治理问题**——它是放在应用和各家大模型 API 之间的**统一入口/中间层**：① **统一接口**——屏蔽各家差异，一套代码调多家；② **路由与降级**——按成本/能力路由，一家挂了切备用；③ **鉴权、限流、配额**——统一管 key、防超额；④ **可观测与计费**——集中记 token、延迟、日志；⑤ **缓存、内容审核**也统一做。本质是把"和大模型打交道的横切关注点（处处要的杂活）"收口到一层。

- **❓最可能追问 → 一句反杀**："和直接调 API 比，什么时候值得上？" → "多模型、要治理、要随时换厂商时网关省心；只用一个模型的小项目可以不上——我 P1/P2 单模型阶段就没上，这是取舍不是标配。"

- **🎯 背诵要点（就背这几个）**：关键词串【**统一入口 · 路由降级 · 限流计费 · 像统一 axios 封装**】

    - 位置：应用和各家大模型 API 之间的统一入口/中间层。

    - 五件事：统一接口、路由降级、鉴权限流配额、可观测计费、缓存与审核。

    - 本质：把和大模型打交道的横切关注点收口到一层。

### 6.12 SSE、WebSocket、WebRTC 有什么区别？实时语音 Agent 用哪个？

- **📕 面试范本（照这个节奏说）**：一句话先给结论——**纯文字流式 → SSE；要双向 → WebSocket；要实时语音/视频 → WebRTC**。展开说：**SSE** 是服务端单向推、基于 HTTP、轻量、自动重连，最适合大模型逐 token 流式输出文字；**WebSocket** 是全双工（同时收发）双向实时，适合双向频繁交互；**WebRTC** 为实时音视频设计、延迟超低，实时语音 Agent（边说边听边回）通常用它传音频。

|**方式**|**方向**|**特点**|**用在哪**|
|---|---|---|---|
|SSE|服务端→客户端单向|基于 HTTP、轻量、自动重连|文字流式（逐 token 推）|
|WebSocket|双向全双工|长连接、双向实时|双向频繁交互|
|WebRTC|双向音视频|为实时音视频设计、延迟超低|实时语音 Agent|

- **❓最可能追问 → 一句反杀**："你项目用哪个？" → "P0/P1/P2 文字流式用 SSE 就够；做语音 Agent 才上 WebRTC——按需选，不为新技术上重的。"

**🎯 背诵要点（就背这几个）**：关键词串【**SSE 单向推文字 · WebSocket 双向 · WebRTC 实时音视频 · 语音用 WebRTC**】

### 6.13 ⭐ 推理模型（o1 / DeepSeek-R1 / 长思维链）是什么？什么时候用？

- **📕 面试范本（照这个节奏说）**：推理模型是**专门强化长链条推理**的一类模型——回答前先生成一长段**内部思考（长思维链）**再给结论，在数学、代码、复杂逻辑、多步规划上明显更强，代价是**更慢、更贵、输出更长**，代表如 o1、DeepSeek-R1。用法：**复杂推理/规划/难题用推理模型，简单问答/抽取/闲聊用普通模型**——杀鸡不用牛刀，应用层常**按难度路由**。另外注意：有些推理模型对 Function Calling/MCP 的支持和普通模型不同，用前要看文档。

- **❓最可能追问 → 一句反杀**："和 CoT 什么区别？" → "CoT 是你用 Prompt 引导普通模型一步步想；推理模型把'长链思考'内化进了训练，不用引导、推理更强更稳。"

- **🎯 背诵要点（就背这几个）**：关键词串【**先想一大段再答 · 强在复杂推理 · 慢且贵 · 按难度路由 · 难才用**】

    - 回答前先生成长思维链再给结论，代表 o1 / DeepSeek-R1。

    - 强在数学、代码、复杂逻辑、多步规划；代价更慢更贵输出长。

    - 简单任务用普通模型，应用层按难度路由。

    - 对 FC/MCP 的支持可能与普通模型不同

### 6.14 ⭐ LLM 是怎么学会工具调用的？Function Call 能力训练过程

- **📕 面试范本（照这个节奏说）**：先给关键前提——**工具调用模式在预训练语料里不存在，参数再大也不会自动具备，必须专项训练**：预训练模型最多会说"我要调 API"，却输不出结构化 JSON。然后分三层说：

- ① **SFT（监督微调）教"怎么调"**——样本是完整调用链：System（工具定义+参数）→ User → Assistant（结构化 JSON 调用）→ Tool（结果）→ Assistant（自然语言答案），靠反向传播学会整条链；样本要覆盖单工具、**多工具并行**、工具失败重试、无需工具直接答等场景。

- ② **RLHF（人类反馈强化）教"该不该调"、建立边界感**——同一问题生成多种回答（调/不调/参数错）→ 人工排序 → 训奖励模型 → 用 PPO（一种较稳的强化算法）优化主模型；典型如"1+1 等于几"应直接答、不调计算器。

- ③ **运行时分工**——模型只理解意图、判断是否要工具、输出结构化 JSON；解析、执行真实函数、回传结果全是代码干的——**"模型只决策不执行"是安全与灵活的核心**。

- 加分点（能提更好，不强求）：SFT 数据来源是"人工标注做种子 + 模型自动生成扩量"，扩量要防**幻觉传递**（模型自动生成的样本可能带幻觉错误、被当真学进模型）；RLHF 进阶有 **RLAIF**（用 AI 评委替人工降本）。主干就是关键词串那四个，先把主干背死。
