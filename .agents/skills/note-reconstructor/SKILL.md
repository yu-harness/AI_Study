# note-reconstructor：将原始技术笔记重构为高质量学习笔记

## 设计理念

> **理解 > 记忆，可视化 > 文字，连接 > 孤立。**

原始技术笔记常见问题：文字密集、缺乏结构、知识点孤岛、难以速览。本 skill 将任意技术笔记重构为**结构化 + 可视化 + 有逻辑衔接**的高质量版本，让读者能快速建立全局认知、理解概念间的关系，并能在复习时快速定位关键结论。

本 skill 的可视化风格固定为：**类比表格 + `plaintext` 树形结构 + Markdown 表格 + 公式/代码块**。不使用 Mermaid，不生成 HTML 卡片，不为了画图而画图。

核心改造模式：

| 原始问题 | 改造方案 |
|---|---|
| 纯文字堆砌 | 拆分为短段落 + 结构化表格 + 关键术语加粗 |
| 缺少全局视角 | 开头增加类比表格，再用 `plaintext` 树形结构展示全局关系 |
| 概念孤立 | 用树形结构、箭头链路、前后状态对比表达关系 |
| 缺少衔接 | 节与节之间增加过渡文字，解释为什么需要下一步 |
| 笔记间断裂 | 每篇末尾增加「接下来看什么」+ 下篇开头「从哪里来」 |
| 难以回顾 | 每篇末尾增加「一句话总结」 |
| 概念难以记忆 | 补充口诀、类比、反例和记忆助手 |

## 重构流程

### 第零步：评估与确认

1. 读取目标笔记，判断当前状态：
   - 已经结构化：只做增量优化，不重复改写全部内容。
   - 仍是原始堆砌：执行完整重构。
2. 用户选中了某段内容时，优先处理选中片段，不擅自重写无关内容。
3. 用户提到「上下逻辑性」「增加过渡」时，重点处理节间和跨篇衔接。
4. 保留原文正确的技术信息、类比、公式和代码；只补充能帮助理解的内容。

### 第一步：建立全局架构

**类比开场**必须放在标题后、正文前。选择与主题高度相关的生活场景：

- 数据库 → 仓库、图书馆、出版社
- 持久化 → 拍照、日志、航行记录
- IO 模型 → 医院分诊台、餐厅点餐
- Agent → 员工、实习生、自动驾驶
- 注意力机制 → 传话游戏、全员群聊

格式：

```markdown
## 先做一个类比：XXX

在深入技术细节之前，先用生活场景建立直觉：

| 生活场景 | 技术概念 |
|---|---|
| ... | ... |
```

类比表格之后，紧跟一张**纯文本全景结构图**。使用 `plaintext` 代码块，表达“问题 → 旧方案 → 新方案”或“输入 → 处理 → 输出”的主线：

```plaintext
🚪 XXX 的整体脉络
│
├── 一、起点：输入/问题是什么？
│   └── 说明读者为什么需要理解这个主题
│
├── 二、旧方案：哪里出了问题？
│   ├── 问题 1：...
│   └── 问题 2：...
│
└── 三、核心方案：如何解决？
    ├── 机制：...
    └── 结果：...
```

结构图规则：

- 节点使用短句，不把完整段落塞进树节点。
- 只展示本篇主线，不罗列所有细节。
- 层级一般不超过 **5 层**，横向内容过长时拆成两张图。
- `├──` 表示同级分支，`└──` 表示最后一个分支，`│` 表示层级延续。
- 每张结构图下方写一行 `> 图释：...`，解释读者应该从图中看出什么。

### 第二步：结构重组

按**问题驱动**而不是功能清单组织内容：

```text
原始结构（差）：           重构结构（好）：
## 功能 A                  ## 一、核心问题是什么？
## 功能 B                  ## 二、为什么需要这个机制？
## 功能 C                  ## 三、旧方案为什么不够？
                           ## 四、核心方案怎么解决？
                           ## 五、有什么代价/风险？
```

每个 `##` 大节之间必须有过渡段落，说明上一节的结论为什么不足，以及下一节要补上什么。

### 第三步：内容改写规则

#### 1. 表格化并列信息

原文出现“A 是 X，B 是 Y，C 是 Z”的并列描述时，优先改为 Markdown 表格。对比类、参数类、选型类内容必须使用表格。

```markdown
| 维度 | 方案 A | 方案 B |
|---|---|---|
| 核心机制 | ... | ... |
| 优点 | ... | ... |
| 局限 | ... | ... |
```

#### 2. 使用纯文本树形结构表达关系

以下内容使用 `plaintext` 树形结构，不使用 Mermaid：

- 架构/组件关系
- 层级包含关系
- 方案演进
- 问题拆解
- 前后状态变化
- 知识点总览

示例：

```plaintext
⚙️ 传统方案：信息逐级传递
│
└── 词 1
    └── 词 2
        └── 词 3
            └── 词 N
                └── 信息需要经过 N 步
```
> 图释：传统方案必须沿着中间节点逐级传递信息，因此序列越长，信息距离越远。

#### 3. 使用箭头链路表达流程和时序

流程、执行步骤、请求链路不强行画成树，使用短句箭头链路：

```plaintext
📥 输入请求
    ↓
🔍 检查条件
    ↓
⚙️ 执行核心机制
    ↓
📤 输出结果
```
> 图释：一次请求从输入到输出经历的关键步骤。

步骤较多时改用编号列表；步骤存在分支时，再使用树形结构：

```plaintext
请求进入
│
├── 条件满足 → 走快速路径 → 返回结果
└── 条件不满足 → 走降级路径 → 记录原因
```

#### 4. 使用前后对比表达变化

```plaintext
📌 修改前
│
└── 第 1 页：A、B、C
    └── 第 2 页：D、E、F

⬇️ 插入 G 后

📌 修改后
│
└── 第 1 页：G、A、B
    └── 第 2 页：C、D、E
        └── F 被挤出当前分页范围
```
> 图释：插入操作改变了元素位置，导致后续分页结果发生漂移。

#### 5. 比例、计算和费用构成使用表格

不要用图形模拟数学计算，直接展示推导过程：

```markdown
### 最终账单

| 步骤 | 组件 | 数值 | 构成 |
|---|---|---:|---|
| ① | 组件 A | **XX B** | ... |
| ② | 组件 B | **XX B** | ... |
| ③ | 组件 C | **XX B** | ... |
| **=** | **合计** | **XX B** | 一句话概括 |
```

占比需要强调视觉差异时，可以补充纯文本条形：

```plaintext
A：████████████████ 80%
B：████                 20%
```

#### 6. 每个小节遵循推导链

每个 `###` 小节尽量遵循：**机制 → 现象 → 结构图/表格 → 根因 → 解法 → 结论**。

```markdown
### 小节标题（设问句，如「List 为什么翻车？」）

第 1 段：先讲清机制的正常逻辑。

第 2 段：说明触发条件，以及问题出现时的现象。

```plaintext
问题触发
│
└── 状态变化 → 结果异常
```
> 图释：一句话点出关键变化。

第 3 段：用一句话提炼根因。

第 4 段：自然引出解法，解释它为什么能解决根因。

| 方案 | 处理方式 | 结果 |
|---|---|---|
| 旧方案 | ... | ... |
| 新方案 | ... | ... |

结论：用一句话回答小节标题提出的问题。
```

这个模式的本质不是罗列知识点，而是推导答案。读者读完每个小节后，应该能回答：**为什么发生、如何诊断、怎样解决**。

#### 7. 可视化的使用边界

- 关系复杂但层级清楚：使用树形结构。
- 顺序明确且没有分支：使用箭头链路或编号步骤。
- 多方案对比：使用 Markdown 表格。
- 数值计算和累加：使用公式或累加表格。
- 比例对比：使用百分比表格，必要时增加文本条形。
- 简单内容：直接用短段落，不强行添加图表。

所有图表和结构块都必须服务于论证，不得为了满足数量而堆叠。

#### 8. 统一格式约束

- **禁止使用 Mermaid**，包括 `flowchart`、`graph`、`pie`、`sequenceDiagram` 等代码块。
- 不使用 HTML 卡片、内联 CSS 或依赖主题颜色的装饰性布局。
- 图形表达统一使用 `plaintext` 或 `text` 代码块。
- 关键术语、性能数字、复杂度、百分比、限制条件和核心结论必须加粗。
- 公式使用 LaTeX；代码使用对应语言的代码块；不要把代码伪装成树形图。
- 树形图中的箭头、缩进和节点文字要保持对齐，避免超过一屏宽度。

### 第四步：过渡衔接

这是 note-reconstructor 区别于普通笔记优化的核心能力。

**节间过渡**：每个 `##` 大节之间加入一段解释“为什么刚才讲的东西还不够”：

```markdown
---

**但光解决 X 还不够**——Y 的问题仍然存在。这就引出了下一节要讨论的 Z。

## 下一节标题
```

过渡段落至少回答一个问题：**为什么需要接下来这个概念？它解决上一节留下的哪个缺口？**

**跨篇衔接**（用户要求时）：

- 每篇开头增加 `> 💡 从哪里来？`，回顾上篇做了什么。
- 每篇末尾增加 `> 🧭 接下来看什么？`，预告下篇解决什么问题。
- 回顾必须说明“上篇建立了什么基础”和“本篇为什么是它的延续”。

格式：

```markdown
> 💡 **从哪里来？** 上一节讲了 A、B、C，建立了……的基础。本节在此基础上解决……的问题。
```

```markdown
> **🧭 接下来看什么？** 本节解决了 X，但 Y 的问题还没回答。下一节将……
```

### 第五步：收尾

**一句话总结**必须放在每篇末尾：

```markdown
## 一句话总结

> 核心概念 = 简洁解释 + 关键机制 + 核心结论。
```

不列点、不使用表格，用一段流畅的话浓缩全篇精华。

## 写作文法规范

### 标题层级

| 层级 | 用途 | 示例 |
|---|---|---|
| `#` | 文件主标题 | `# 1.1.1 前言` |
| `##` | 核心大节 | `## 一、AOF 是什么？——写后日志` |
| `###` | 子主题/具体问题 | `### 写后日志为什么会丢数据？` |
| `####` | 最小粒度 | `#### 工程亮点：原子写入` |

如果原笔记已经使用 `#` 作为文件标题，保留原有层级，不要为了套模板强行改标题。

### 开场结构

推荐顺序：

```text
# 标题

## 先做一个类比：...
类比表格

plaintext 全景结构图
图释

## 一、背景/问题是什么？
正文
```

### 表格使用标准

- 并列概念、参数、优缺点、方案选择必须优先考虑表格。
- 表格列数以易读为准，通常不超过 **5 列**。
- 单元格只放短句；复杂解释放在表格前后。
- 表格中的关键参数和结论加粗。

### 纯文本结构图标准

推荐使用以下符号：

```plaintext
│       层级延续
├──     非末尾分支
└──     末尾分支
↓       顺序流转
←→      双向关系
✅      正常/成功
⚠️      风险/限制
❌      失败/问题
```

质量要求：

- 一张图只讲一个主问题。
- 每层节点尽量不超过 **3 个**。
- 纵向一般不超过 **5 层**。
- 节点文字尽量控制在一行；详细解释放到正文。
- 结构图必须有图释，图释说明“这张图要读者记住什么”。

### 加粗规则

必须加粗：**核心术语**、**方法名**、**关键数据**、**复杂度**、**限制条件**、**核心结论**和**重要对比**。

## 特殊情况处理

### 仅追加内容（「追加进去」）

1. 先读取目标文件末尾，找到合适的插入位置。
2. 保持已有标题层级、表格风格和 `plaintext` 结构图风格。
3. 在新增内容开头增加过渡，说明它与前文的关系。
4. 更新「一句话总结」，确保覆盖新增内容。

### 仅增加过渡（「上下逻辑性」）

1. 识别每个 `##` 大节边界。
2. 在节与节之间插入过渡段落。
3. 用户要求跨篇衔接时，在首尾增加「从哪里来」和「接下来看什么」。
4. 不改变原有技术内容和结构图，除非发现明显逻辑错误。

### 修复结构图显示问题（「修复下」）

检查以下问题：

1. 是否误用了 Mermaid 代码块；全部改为 `plaintext` 或 `text`。
2. 是否把完整段落塞入树节点；拆回正文。
3. 是否层级过深或横向过宽；拆成两张图或改用表格。
4. 是否缺少图释；在结构图后补充一句说明。
5. 是否混淆顺序和层级；顺序使用 `↓`，层级使用 `├──`/`└──`。

## 输出质量检查清单

重构完成后自检：

- [ ] 开篇有与主题相关的类比表格。
- [ ] 类比表格后有一张简洁的 `plaintext` 全景结构图。
- [ ] 所有关系图、流程图和决策图都没有使用 Mermaid。
- [ ] 没有使用 HTML 卡片、内联 CSS 或装饰性布局。
- [ ] 每张结构图或流程图后都有一句图释。
- [ ] 每个 `###` 小节尽量遵循「机制→现象→结构图/表格→根因→解法→结论」。
- [ ] 计算/累加类内容使用公式或 Markdown 表格。
- [ ] 比例/占比类内容使用百分比表格，必要时补充文本条形。
- [ ] 原文核心技术内容完整保留，没有为了重排而丢失信息。
- [ ] 关键数据、术语、复杂度和结论已加粗。
- [ ] 每个 `##` 大节之间都有解释性过渡。
- [ ] 末尾有「一句话总结」。
- [ ] 用户要求跨篇衔接时，有「从哪里来」和「接下来看什么」。
- [ ] 表格列数适中，单元格没有塞入大段文字。
- [ ] 结构图层级一般不超过 5 层，节点文字简短且不横向溢出。
