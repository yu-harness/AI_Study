# note-reconstructor：任务导向的技术笔记重构

## 核心目标

本 skill 的目标不是把原文改得更长或更漂亮，而是把一份技术材料重组为一条可执行的学习路径：

```text
明确目标/任务
  -> 建立知识地图
  -> 识别模块依赖
  -> 区分主线必学与按需选学
  -> 从顶层逐步深入
  -> 给出解决方案
  -> 验证方案和学习结果
```

默认面向计算机专业学生、工程师和需要把技术知识用于解决问题的人。保持技术严谨，但不为了显得专业而堆砌公式、代码、部署细节或面试术语。

## 第一原则：先任务，后知识

每篇重构后的笔记都应回答：

1. 要完成什么目标，或解决什么问题？
2. 为完成这个目标，必须掌握哪些知识？
3. 这些知识为什么按当前顺序出现？
4. 如何把知识转化为具体设计、实现或判断？
5. 如何验证方案有效，或确认自己真正掌握？

不要从“这个概念是什么”开始无限扩展。概念必须服务于目标、任务或后续推理。

## 工作流程

### 第零步：确认处理范围

先读取原始笔记和相关上下文，判断用户要做哪种操作：

- 完整重构：重建知识路径和文章结构。
- 局部重构：只处理用户选中的片段。
- 逻辑补全：补充模块之间的前置关系、过渡和链接。
- 增量追加：把新内容放进既有知识地图，而不是简单贴到文末。
- 技术加深：只补充用户明确需要的推导、实现或工程细节。

用户选中了片段时，优先处理该片段，不擅自重写无关内容。

### 第一步：确定目标或任务

如果用户已经给出目标，直接以此为主线。

如果没有给出目标：

1. 从原文推断它可能要解决的问题。
2. 给出候选目标和推断依据。
3. 只有在目标基本明确时才开始重构。
4. 如果存在多个方向，例如面试复习、源码阅读和工程实战，先询问用户，不擅自选择。

如果用户没有提供任务，但明确要求继续处理，可以选择一个典型工程任务作为主线，并在笔记开头标明这是默认任务。

目标必须尽量写成可检查的结果，例如“构建一个能回答企业文档问题的 RAG 系统”，而不是“理解 RAG”。

### 第二步：建立顶层知识地图

正文开始前必须先给出总览，至少包含：

```markdown
## 学习目标

## 总体任务

## 知识地图

## 模块依赖关系

## 学习顺序
```

知识地图只展示当前任务需要的主线，不罗列所有相关知识。

模块依赖关系优先使用 Markdown 表格：

| 模块 | 类型 | 前置知识 | 本模块解决的问题 | 输出能力 | 后续连接 |
|---|---|---|---|---|---|
| 模块名称 | 主线必学/按需选学 | 必要前置 | 具体问题 | 能做什么 | 下一模块 |

学习顺序要解释“为什么先学这个、学完之后为什么能进入下一个模块”，而不只是列目录。

### 第三步：按四层递进组织内容

默认按以下四层从顶层走到底层，但只展开当前任务真正需要的层级：

1. **全局层**：这个技术解决什么问题，整体由哪些模块组成？
2. **机制层**：每个模块为什么存在，输入、处理过程和输出是什么？
3. **实现层**：算法、数据结构、代码和关键参数如何实现？
4. **工程层**：如何验证、部署、优化，以及如何处理边界条件和取舍？

某一层对任务无关时直接跳过，不为了凑齐四层而硬加内容。数学推导、代码、系统开销、部署和面试内容都遵循同一原则：只有它们支撑当前目标时才出现。

### 第四步：逐模块进行任务驱动讲解

每个主线模块按以下结构组织，必要栏目可以省略：

```markdown
## 模块 N：模块名称

### 模块目标
本模块要帮助读者完成什么具体任务？

### 前置知识
进入本模块前必须知道什么？

### 问题场景
如果没有这个机制，当前任务会遇到什么问题？

### 核心概念
只引入解决当前问题所需的概念。

### 工作机制
说明输入、处理过程、输出，以及它与其他模块的关系。

### 解决方案
针对问题应该如何设计和选择方案？

### 实现映射
只有确实需要时，给出代码、伪代码、数据结构、公式或配置。

### 验证方法
如何通过实验、测试、指标或现象确认方案有效？

### 工程取舍
只有存在真实取舍时，讨论性能、成本、复杂度、可靠性和适用边界。

### 与下一模块的关系
本模块产出的能力如何成为下一模块的输入？

### 掌握检查
完成本模块后，读者应该能够完成哪些判断或小任务？
```

“解决方案”必须具体到可执行动作。不要只写“使用缓存提高性能”，而要说明缓存什么、放在哪里、什么时候失效、如何验证命中率和一致性。

### 第五步：区分主线与按需深入

将知识分为两类：

- **主线必学**：完成当前任务必须掌握的知识，放在正文学习路径中。
- **按需选学**：当前任务不依赖，但对性能优化、异常处理、扩展场景或深入研究有价值的知识，放在相关模块末尾或附录。

知识点是否进入正文，由任务依赖决定，不由“这个主题通常应该讲什么”决定。

### 第六步：决定单篇还是拆分

小主题生成单篇完整笔记。满足以下任一条件时，拆成“总览笔记 + 模块笔记”：

- 存在三个以上相对独立的知识模块。
- 模块之间有清晰的前置依赖。
- 某个模块需要单独完成任务或实验。
- 同时包含概念、算法、代码和工程落地，且主线会被拉长。
- 读者需要分阶段学习或反复复习。

拆分不按固定字数切割，而按知识结构切割。默认命名如下，优先遵循用户知识库已有规范：

```text
主题-总览.md
主题-01-基础概念.md
主题-02-核心机制.md
主题-03-实现方案.md
主题-04-工程落地.md
```

总览笔记链接到所有模块；模块笔记链接回总览，并标明前置和后续模块。

## Obsidian 链接规则

使用 Obsidian wikilink，不使用普通 Markdown 文件链接替代知识库链接：

```markdown
[[主题-01-基础概念]]
[[主题-02-核心机制|核心机制]]
重构自：[[原始笔记]]
```

如果原笔记已被其他笔记引用：

- 默认不批量改写已有链接。
- 新笔记加入“重构自：[[原笔记]]”。
- 原笔记顶部加入“重构版：[[新笔记]]”。
- 只有用户明确要求时，才迁移旧链接。

## 内容处理规则

- 正确且服务于当前任务的内容：保留并重新组织。
- 重复、空泛或无法支撑任务的内容：压缩或删除。
- 当前不属于主线但可能有价值的内容：移动到“按需深入”。
- 不确定的内容：标记为“待验证”，不能直接写成结论。
- 不得因为追求简洁而静默丢失关键推导、代码、实验结果或技术限制。
- 原文正确的公式、类比和代码可以保留，但必须放到它们能解释主线的位置。
- 每节之间增加必要的过渡，解释为什么从当前问题进入下一步。
- 不要重复解释已经在前置模块建立的概念，除非为了当前推理必须回顾。

## 渐进式呈现

每个模块优先按“结论 -> 机制 -> 细节”呈现：

1. 先用一句话说明模块解决什么问题以及核心方法。
2. 再用简短流程、公式、伪代码或对比说明机制。
3. 最后按需展开推导、代码、工程细节、边界情况和验证方法。

读者应能快速抓住主线，也能在需要时深入。渐进式呈现不是删掉严谨内容，而是把严谨内容放在正确层级。

## 视觉和格式规则

视觉元素服务于知识关系，不服务于装饰：

- 知识地图和模块依赖表是强制的。
- 类比只在抽象概念难以建立直觉时使用。
- `plaintext` 树形图只在表达数据流、调用链、状态变化或层级关系时使用。
- Markdown 表格用于模块映射、方案对比、参数和取舍。
- Mermaid、HTML 卡片、复杂装饰图不是默认格式；只有用户明确需要或关系确实难以用 Markdown 表达时才使用。
- 不为了满足格式要求而强行添加公式、代码、表格、类比或图片。
- 公式必须说明变量、维度和成立条件；代码必须说明输入、输出和关键路径。

## 文件安全和版本规则

默认不覆盖原始笔记：

- 原始笔记保持不变。
- 生成带有清晰名称的重构版本。
- 在重构版本中记录来源。
- 用户明确要求“直接改原笔记”时，才允许原地修改。

如果重构过程中发现目标不明确、原文存在冲突或某项技术结论无法确认，应先停在确认点，不要继续大规模改写。

## 特殊请求

### 用户说“只加推导/只补代码/只增加过渡”

只修改指定范围，同时保持原有知识地图、链接和结构不被破坏。不要借机进行整篇重构。

### 用户追加新内容

先判断新内容属于哪个模块、是否是主线必学、依赖哪些已有内容，再插入对应位置。必要时更新总览、依赖表和模块链接，不要默认追加到文末。

### 用户要求修改原笔记

先确认目标文件、修改范围和是否保留备份。若用户确认覆盖，仍应保留来源信息或版本记录。

## 输出质量检查

完成前逐项检查：

- 是否明确了可检查的目标或任务？
- 是否先给出顶层知识地图？
- 是否说明模块之间的前置依赖、输入输出和学习顺序？
- 是否从全局层逐步进入机制、实现和工程层？
- 是否每个主线模块都回答了“为什么需要”和“如何解决”？
- 是否区分了主线必学和按需选学？
- 是否避免了与当前任务无关的知识扩展？
- 是否给出了必要的验证方法和模块掌握检查？
- 是否解释了模块与下一模块的连接？
- 拆分时是否建立了 Obsidian 双向链接？
- 是否保留了原笔记，并记录了重构来源？
- 是否没有把类比、图表、公式或代码变成强制装饰？
- 所有技术结论、公式、代码和配置是否可解释、可验证？
