# 项目面试弹药库

输入是一个项目目录（可选附带简历里该项目的原文），输出是一份能直接背、能防守的面试材料。

**这个 skill 的第一原则：每一句话都要能追到代码或文档的某一行。** 追不到的内容不写。面试官问「你说是这样，代码在哪」，你要能立刻翻出来。凭印象写的漂亮话，在追问第二层就会塌。

## 一、产物落在哪

默认落在项目目录下的 `面试弹药库/`：

```text
{项目目录}/面试弹药库/
├── 00-弹药库总览.md      ← 入口：这个项目一句话、三段式讲稿、数字总表、高危清单
├── 01-讲稿.md            ← 30 秒 / 2 分钟 / 5 分钟三个长度，逐字可念
├── 02-追问树.md          ← 面试官从哪问起、怎么往下追、每一层答什么
├── 03-数字防守表.md      ← 每个数字的出处、口径、被质疑时的回应
├── 04-简历对账.md        ← 简历每一句 ↔ 代码证据，标出对不上和说不圆的地方
└── 05-代码定位索引.md    ← 高频追问点 → 文件:行号，面试时现场翻
```

项目已有目录习惯时跟随项目。用户指定目录时用指定的。

## 二、执行流程

### Phase 0：摸底

按顺序做四件事，缺一件都会导致后面写飘：

1. **读强制规则文件**。项目根往上找 `AGENTS.md` 或 `CLAUDE.md`。这类文件规定了禁止使用的句式和用词，写弹药库时必须遵守。
2. **读项目自己的中文文档**。常见名字：`改造进度.md`、`README.md`、`docs/ARCHITECTURE.md`、`*复盘*.md`、`*实现*.md`。项目作者自己写的复盘含金量最高，里面往往已经写了踩坑和数字口径。
3. **找简历原文**。用户给了就用；没给就在工作区里找 `简历/` 目录下的 `resume.json` 或 `*.docx`，搜项目名。**简历口径是最终交付物**，弹药库必须和它对得上。
4. **跑一次目录清单**。列出源码目录结构、各文件行数、Git 提交历史。行数是后面写代码定位索引的原材料。

先把摸底结果跟用户对一遍，指出发现的矛盾（文档之间数字不一致、简历说法在代码里找不到支撑），再开写。

### Phase 1：挖弹药

按四个维度扫代码，每个维度都要落成「结论 + 文件:行号」：

**架构维度** —— 请求从入口到出口经过哪些层、每层做什么、层与层怎么传数据。找入口文件（`main.py` / `app.py` / 协调器），顺着调用链走一遍。

**决策维度** —— 系统在哪里做了判断，判断依据是什么，阈值多少。找 `if` 分支密集的地方、路由逻辑、配置常量。面试官最爱问的就是「为什么这里选 A 不选 B」。

**数字维度** —— 每个数字从哪来。找评测脚本、结果目录、数据卡片。**重点记下数字的样本量和时间**：`n=200` 和 `n=65` 的可信度差一个量级，面试官会抓这个。

**踩坑维度** —— 项目改过什么。翻 Git 日志和复盘文档，找「原来这样、后来改成那样」的提交。这类内容是面试中的加分项，因为它显示了调试能力。

扫描时用 Grep 找关键词，不要通读所有文件。常见锚点词：数字常量、`TODO`、`FIXME`、`bug`、`修复`、`坑`、`注意`。

### Phase 2：写四件产物

四件产物的写法见下面第三到第六节。

**先写 05 代码定位索引**，因为它强制你把每个论断钉到行号上。写完索引再写别的，天然不会飘。

### Phase 3：对账

最后检查三件事：

1. 讲稿里每个技术点，代码定位索引里有没有对应条目。没有就删掉那句话。
2. 数字防守表里每个数字，和简历原文是否一致。不一致要明确告诉用户，让他决定改哪边。
3. 通读一遍，把「我觉得」「应该」「大概」这类词全部替换成确定说法或明确标注为推测。

## 三、讲稿怎么写

三个长度，用途不同：

- **30 秒**：自我介绍里提到这个项目时用。两到三句，说清「做什么的、难在哪、我做了什么」。
- **2 分钟**：面试官说「讲讲你这个项目」。这是主战场，必须有结构。
- **5 分钟**：面试官明显感兴趣、让你细讲。加上踩坑和取舍。

2 分钟讲稿的骨架固定为四段：

```text
1. 一句话定位（这个系统是什么、给谁用、解决什么问题）
2. 架构主干（从请求进来到答案出去，经过哪几个环节，每环节一句话）
3. 我做的三件有难度的事（每件：问题 → 做法 → 结果数字）
4. 一个没做完的（显得诚实，也给面试官递话头）
```

逐字写，写成能念出来的口语。**不要写成书面语**——书面语一念就假。念一遍，念不顺的地方改掉。

## 四、追问树怎么写

追问树是弹药库的核心。面试官的提问是逐层深入的，你要为每一层准备。

树形结构，每层一行：

```text
Q1 你这个系统为什么要用多 Agent？
├─ 判断依据是什么？→ {答：代码位置}
│  ├─ 为什么阈值定在这里？→ {答}
│  └─ 如果全是复杂问题会怎样？→ {答}
├─ 多 Agent 的代价是什么？
│  ├─ 延迟增加多少？→ {答：数字，出处}
│  └─ 成本增加多少？→ {答：数字，出处}
└─ 为什么不用单个 Agent 换更强模型？
   └─ {答}
```

标记规则：

- `【硬】` 表示这个问题你答不上来会明显扣分，必须背
- `【险】` 表示问题本身有陷阱，答错方向比答不上来更糟
- `【送】` 表示这个问题是送分的，可以借它展开讲

**每层的答案要具体到能说出口的程度**，不能写「说明一下原理」。追问深度至少三层，热门问题追到四层。

追问树不是凭空想的。来源有三处，按含金量排序：

1. 项目复盘文档里作者自己记的坑 —— 这些是真被问过或真出过问题的
2. 代码里的设计取舍 —— 有取舍的地方就有「为什么不用另一种」
3. 简历措辞的模糊处 —— 简历写得含糊的地方，面试官一定会追问

## 五、数字防守表怎么写

简历上的每个数字都要能被质疑。表格字段：

- **数字**：原文照抄
- **口径**：这个数字是怎么算的（分母是什么、样本多少、谁判的）
- **出处**：文件路径与行号，或结果目录
- **薄弱点**：这个数字最容易被攻击的地方
- **回应**：被攻击时怎么答

**关键原则：主动暴露口径，比被追问出来强。**

写「准确率 91%」会被追问「谁判的、判了多少条」；写「91%，200 条自动评测集，由 LLM 裁判按要点清单判定，非医生盲审」，面试官反而会觉得你严谨。

如果某个数字的口径自己都不清楚，**标红并告诉用户**，不要替它编一个说法。

## 六、简历对账怎么写

逐句拆简历里这个项目的每条 bullet，做三列对照：

```text
简历原文 | 代码/文档证据 | 判定
```

判定分四档：

- **站得住**：代码里有，数字有出处，措辞准确
- **措辞过重**：事实有，但词用大了（例如把「检索增强」写成「知识图谱推理」）
- **属超报**：代码里找不到支撑，或者实现远比描述简单
- **说不圆**：和别的句子矛盾，或数字对不上

后两档要给出**改写建议**，直接给出可以替换的措辞。改写的原则是：把事实说全，不缩小也不放大。宁可说小一点，面试时超出预期是加分，低于预期是减分。

## 七、写作约束

### 必须遵守

- 读到的强制规则文件（`AGENTS.md` 等）里的句式与用词禁令，全部适用。
- 每一条技术论断标注来源，格式 `文件路径:行号` 或 `文档名 章节`。
- 找不到来源的论断不写。确实需要提但没证据的，写进「待确认」并告诉用户。
- 数字照抄原文，不四舍五入、不换算单位。写清样本量。

### 禁止

- 禁止用「我觉得」「应该」「大概是」描述系统行为。
- 禁止为了好听而用比代码更大范围的词。
- 禁止在讲稿里堆技术名词。每个名词都要能展开讲，展开不了就删。
- 禁止把「没做完」写成「后续规划中」这类含糊说法。直接说没做完。

## 八、验收用例

### 用例 1：标准调用

用户说「把 medical-agent 这个项目准备成面试能讲的」，并给了项目路径。

必须：先跑 Phase 0 摸底并汇报矛盾点；产出全部五份文件；每条论断带行号；数字与简历对照。

### 用例 2：简历里找不到证据

简历写着「实现多路召回融合，召回率提升 40%」，代码里只有单路向量检索。

必须：在对账里判为「属超报」，给出改写建议，并明确告诉用户这句要改，不能蒙混。

### 用例 3：用户只想知道会问什么

用户说「面试官会怎么问这个项目」。

必须：仍然先摸底再输出，只产 `02-追问树.md` 与 `05-代码定位索引.md`，并说明另外三份可以随时补。

### 用例 4：数字口径不明

用户说「把准确率写高点」，但找不到评测脚本。

必须：拒绝编造；告诉用户这个数字无法溯源；建议要么补评测要么从简历上撤下来。

## 九、输出口径

写完汇报：

```text
摸底发现：
- {矛盾点一}
- {矛盾点二}

已生成：
- 总览：{路径}
- 讲稿：{路径}
- 追问树：{路径}
- 数字防守表：{路径}
- 简历对账：{路径}
- 代码定位索引：{路径}

需要你决定的：
1. {简历里对不上的地方，改哪边}
2. {口径不明的数字，补评测还是撤掉}

下一步：先背 2 分钟讲稿，背完对着追问树【硬】标记的问题自问自答一遍。
```
