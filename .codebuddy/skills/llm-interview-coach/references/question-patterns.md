# 提问句式库

按场景分类。句式里的 `<主题>`、`<现象>`、`<指标>` 用具体内容替换，替换后必须带数字或具体约束，否则会退回八股腔。

## 一、开场破冰

用于面试前两分钟，降低紧张感，同时探出候选人的真实经历。

1. 你最近做的项目里，哪一块是你从头写到尾的？
2. 你简历上写做了 `<项目>`，先说说它解决的是谁的问题？
3. 这个系统上线之后，日活大概什么量级？
4. 你们团队几个人，你负责哪一部分？
5. 这套东西现在还在跑吗，最近一次改动是什么？
6. 你做的部分里，最难的一块是什么？

## 二、概念确认

用于确认基础是否扎实，只问一句，不给提示。

1. 你怎么理解 `<主题>`？
2. 如果只用一句话跟产品经理解释 `<主题>`，你会怎么说？
3. `<术语>` 这个说法你们内部具体指什么？
4. 你觉得 `<主题>` 解决的核心问题是什么？
5. 这个方案里，哪一步是必须的，哪一步可以省？
6. 你能举个场景说明它什么时候有用吗？

## 三、原理深挖

用于区分「看过文章」和「真懂机制」。

1. 它底层是怎么实现的？
2. 这一步具体在算什么，输入输出分别是什么？
3. 为什么设计成这个样子，换一种做法会怎样？
4. 你说的 `<机制>` 在代码里对应哪个环节？
5. 如果把这部分去掉，系统会退化成什么样？
6. 这个数值大概是什么量级，你能估一下吗？

## 四、方案对比

用于看是否具备取舍意识。

1. 那跟 `<方案 B>` 比，你会选哪个？为什么？
2. 这两个方案的差别在效果上还是在成本上？
3. 什么情况下 `<方案 A>` 会输给 `<方案 B>`？
4. 你们最后选了哪个，是效果决定的还是工期决定的？
5. 如果预算砍一半，你的选择会变吗？
6. 这两个方案能不能一起用，代价是什么？

## 五、场景设计

用于考开放设计和结构化表达。

1. 如果让你从零做一个 `<系统>`，你会怎么分成几块？
2. 这个系统的输入不稳定，你会怎么兜底？
3. 用户量涨十倍，哪一块会先出问题？
4. 你会先做哪一块，后做哪一块，判断依据是什么？
5. 这套设计里，哪个环节最容易成为瓶颈？
6. 上线前你会准备哪些监控指标？

## 六、故障排查

用于考定位顺序，重点看有没有先观测再动手。

1. 我们线上 `<现象>`，你会按什么顺序查？
2. 这个问题可能是哪几层引起的，你怎么一层层排除？
3. 你手上只有日志和监控，先看哪个指标？
4. 如果复现不了，你会怎么缩小范围？
5. 你会怎么验证它真的修好了，而非只看表面现象？
6. 这个问题你遇到过吗，当时怎么定位的？

## 七、压力测试

用于观察是否敢于纠正错误前提，以及是否被极端场景带歪。

1. `<错误结论>`，对吧？（错误前提，正确做法是先纠正）
2. 如果所有请求都超时，你还会按原来的顺序排查吗？
3. 这个方案在数据量翻一百倍时还成立吗？
4. 你说它更快，那为什么大厂没有全用这个？
5. 假设老板要求一周上线，你会砍掉哪部分？
6. 如果这个指标和另一个指标冲突，你保哪个？

## 八、开放探讨

用于收尾，看技术判断和视野。

1. 这个方向你觉得两年内会怎么变？
2. 你现在最想补的一块能力是什么？
3. 如果让你重做这个项目，哪一处会换方案？
4. 你怎么判断一个新框架值不值得投入时间？
5. 这套方案在你们行业之外还成立吗？
6. 你觉得这一块目前最大的未解问题是什么？

## 使用说明

- 每个场景挑一句即可，不要连续抛三句。
- 替换占位符时带上具体数字、现象或业务约束。
- 压力测试类句式每场面试用一到两次，过多会让候选人进入防守状态。
