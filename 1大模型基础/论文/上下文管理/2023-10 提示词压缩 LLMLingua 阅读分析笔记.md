# 2023-10 提示词压缩 LLMLingua 阅读分析笔记

> 原文：LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models，arXiv 2310.05736

## 元信息

## 一句话结论

用一个小模型的**困惑度**逐 token 判断哪些内容可以删，把长提示压到 1/20 还基本不掉性能；不需要改动目标大模型的参数，所以对只能走 API 调用的黑箱模型一样能用。

## 要解决的问题

- 思维链（CoT）、上下文学习（ICL）、检索历史记录这些做法让**提示**越来越长，动辄上万 token，推理成本和延迟跟着上涨
- **量化、剪枝、微调**这类省算力的做法都要改模型参数，API 调用的模型用不上
- 已有的 Selective-Context 按短语的自信息丢内容，留下两个缺口：忽略被删内容之间的**相互依赖**；忽略压缩用小模型与目标大模型之间的分布差异

## 方法：三个阶段，先粗后精

```text
原始提示（指令 + 示范 + 问题）
  → 一，预算控制器：给各部分分配不同压缩率
  → 示范层面筛选：按困惑度从高到低选示范，超出 k 倍目标长度就停
  → 二，迭代 token 级压缩：分段计算条件概率，只保留困惑度高于阈值的 token
  → 三，分布对齐：用目标大模型生成的数据对小模型做指令微调
  → 压缩后的提示，交给黑箱大模型推理
```

**一，预算控制器（Budget Controller）**

给提示的不同部分分配不同的压缩率。依据有两条：**指令和问题**直接决定生成结果，要少压；多个示范之间信息重复，可以多压。

具体做法是先按**公式算出示范部分**的压缩率，再让**小模型算每个示范的困惑度**，按困惑度从高到低挑选（困惑度高代表信息量大），选到累计长度超过 `k × τdems × Ldems` 为止；剩下的预算分给**指令和问题**。论文里超参数取 `k = 2`，指令压缩率 `τins = 0.85`、问题压缩率 `τque = 0.9`。

**二，迭代 token 级压缩（ITPC）**

把要压的提示切成段（段长 100），逐段**用条件概率**算困惑度，保留困惑度高于阈值 γ 的 token。关键在「迭代」：前一段压缩后的结果会拼进下一段一起算条件概率，这样能缓解「条件独立假设」带来的误差——这也是它和 Selective-Context 的主要区别，后者是单次推断、一次算完。

**三，分布对齐（Distribution Alignment）**

压缩用的小模型和目标大模型分布不一样，判断「哪些 token 不重要」的尺度就会有偏差。做法是用目**标大模型生成的数据**（Alpaca 数据集）对小**模型做指令微调**，让两者的分布更接近。

「判断尺度不一致」的问题。

**先说问题是什么**：删 token 的判断依据是困惑度，而困惑度是小模型算出来的。同一个词，小模型觉得「很常见、能猜到」，目标大模型可能觉得「很关键、猜不到」。用小模型的尺度去删，就容易把大模型真正需要的词删掉。

**再说什么是对齐**：既然两个模型对「难易」的看法不一致，就先把小模型的看法掰得跟大模型接近一点——具体做法是拿一批指令去问目标大模型，把大模型的回答收集起来，然后用这些回答去继续训练小模型（也就是指令微调），让小模型学会生成大模型那种风格与用词。训练完，它分配概率的方式就更像大模型，删内容时误删的概率就低了。

**数据从哪来**：指令来自 Alpaca 数据集，回答由目标大模型生成，成对使用。这份数据只用于对齐，不参与任何评测，避免污染结果。

**效果有多少**：消融实验里，去掉这一步，GSM8K 在 1-shot 约束下从 79.08 掉到 78.62。差距不大，说明它是个加分项；主要的分数还是来自迭代 token 级压缩和预算控制器。


**问题形式化**：压缩率 `τ = 压缩后长度 / 原长度`，目标是让压缩后提示的生成结果分布尽量贴近原提示的生成结果分布，也就是最小化两者的 KL 散度。

## 关键设计取舍

**一，删内容按信息量，不按位置**

依据是信息熵：困惑度低的 token 对整体熵贡献小，删掉它对模型理解上下文的影响也小。所以保留标准是「困惑度高」——模型越拿不准的地方越要留。位置截断只是一刀切掉尾部，不知道自己切掉的是什么；困惑度让删的人清楚自己删的是什么。

**二，在原提示上做减法，不让大模型重写**

论文给了三条理由：

- **控制不住**：改写的内容与长度都没法规定，要凑到指定压缩率就得反复重写、反复检查
- **贵而且效果更差**：重写要理解并重新组织推理步骤，小模型做不来，只能用大模型；而 GPT-4 生成的压缩提示在 BBH 上只有 27.13 EM，原始提示是 70.07；GSM8K 四分之一约束下是 56.33 对 77.33
- **压缩率上不去**：生成结果必须语法完整、前后连贯，能省掉的词有限；删 token 可以把功能词和重复表述拿掉

概括成一句：生成式压缩是「让模型用自己的话重讲一遍」，删 token 是「在原话上做减法」。重讲自由度大、控制力弱；减法不产生新句子，反而压得更狠。

顺带一条成本上的好处：删 token 只靠小模型算概率，不需要调用昂贵的大模型——5 倍压缩时，压缩这一步本身只花 0.3 秒。

**三，压缩率高的时候先删整句或整个示范，不同时逐 token 删**

压到很狠时，逐 token 删会让压缩后的提示支离破碎、丢掉关键信息。所以在高压缩率下先做示范层面或句子层面的粗粒度筛选，保住基本的语言完整性，剩下的预算再交给 token 级处理。

**三条取舍合起来就是一个顺序**：先决定哪些部分值得花预算（预算控制器），再决定每个部分里留哪些词（迭代 token 级压缩）。这也是论文标题里「先粗后精」的意思。

## 实验与结果

先记住这批实验想回答四件事：压完之后还能做对吗；换个任务或换个目标模型还成立吗；分数是哪个模块挣来的；到底省了多少。

### 问题一：压完之后还能做对吗

**数学题（GSM8K）**，分数是**完全匹配率**：

- 什么示范都不删：78.85 分，2366 token
- 压到 446 token（五分之一的长度）：79.08 分，居然比不压缩还**高**一点
- 压到 171 token（十四分之一）：77.41 分
- 压到 117 token（二十分之一）：77.33 分

也就是说长度**只剩二十分之**一，分数只掉 1.5 分。对比同一条线上的 Selective-Context：同样压到二十分之一，它只剩 44.20 分，差了 33 分——这就是这篇论文的主卖点。

**难题（BBH）** 掉得更多：全量 70.07，压到三分之一（288 token）还能保持 70.11；压到七分之一掉到 56.85。作者解释是里面有几道特别难的题（比如 shuffling 那一类）扛不住压缩。

**对话与摘要**：ShareGPT 压到三分之一语言还通顺，摘要类（Arxiv-March23）能压到九分之一。

一句话记法：数学题和对话类任务**压二十倍**几乎不掉分，难题掉得多一些。

### 问题二：换目标模型还成立吗

- **换成 Claude**：压到五分之一还能拿 83.51 分，比不压缩的简单提示高 0.8 分。说明这套做法不挑供应商，黑箱模型一样能用
- **换成更弱的小模型（GPT2-Alpaca）**：分数掉 1 到 2 分。原因是小模型和目标模型差得更远，判断「哪些词能删」的尺度更容易跑歪

后面这一条正好解释了论文为什么要加分布对齐那一步。

### 问题三：分数是哪个模块挣来的

消融的做法是每次拿掉一个模块，看分数掉多少（基准 79.08 分），按贡献从大到小排：

- 拿掉**迭代 token 级压缩**：72.93，掉 6 分多
- 预算控制器里改成随机挑示范：72.78，掉 6 分多
- 拿掉预算控制器：73.62，掉 5 分多
- 取消各部分不同的压缩率：77.26，掉不到 2 分
- 拿掉分布对齐：78.62，掉不到 1 分
- 换成最简单的去停用词：76.27，而且只能压到 1.3 倍

顺序记住就够：**迭代压缩**最要紧，挑示范的方式次之，动态压缩率与分布对齐是加分项；朴素的去停用词压不动。

### 问题四：省了多少

- **计算量**：小模型每 token 的开销大约只有大模型的 1/25，所以压五倍时，整体开销大约只有原来的四分之一
- **延迟**（V100 上跑 GSM8K）：不压缩 8.6 秒；压 2 倍 4.9 秒；压 5 倍 2.3 秒；压 10 倍 1.3 秒，加快 1.7 到 5.7 倍
- **压缩这一步本身很便宜**：只要 0.2 到 0.8 秒

### 两个附带发现

- 压缩之后模型吐出来的话也变短了，**说明省的不只是输入，输出那部分也省**
- 大模型能把压缩提示还原成原本的推理过程：用 Alpaca-7B 压的能还原完整 9 步，用 GPT2-Alpaca 压的只还原出 7 步还带着计算错误；GPT-3.5-Turbo 做不到还原，GPT-4 可以。作者猜这是模型规模变大之后才出现的能力
## 局限

- **压缩率有上限，超过 25 到 30 倍之后性能明显下降**：这条上限对所有方法都成立，本文的差别是把下降点往后推了——别的做法在十几倍就开始掉，它到二三十倍才掉
- **没有通用的安全压缩率，只能按任务实测**：同样的压缩率，提示越长、任务越简单、句子越多，就越扛得住。所以「压到几倍是安全的」没有统一答案，得拿自己的任务测拐点
- **分词器不一致会让长度估算出现偏差**：压缩用的小模型和目标大模型可能采用不同的分词方式，同一个字符串在两边切出的 token 数不一样。论文指的是压缩侧可能低估原始提示的 token 长度，进而让压缩率的计算对不上实际值

三条合起来给出一条使用上的提醒：别把**压缩率**当成一个可以随便调高的参数，先按任务测出掉分拐点，再留出余量。

## 与 Tether 现行做法的对照

> 对应笔记：[[06-上下文瘦身与输出管理设计]] —— 第一层（长输出在入口处收）、最后一层（段落预算控制）、目前没做的部分（缺的正是「按内容判断」）

- Tether 的第一层按字符截断，丢掉的是尾部；LLMLingua 按**信息量**删 token，判断依据是小模型的困惑度。差别在「知不知道自己在删什么」
- Tether 的第二层给每个记忆字段设上限，与预算控制器是同一个思路：给不同部分不同预算，重要的少压
- Tether 的第四层把旧历史折成一句摘要，接近论文里的「生成式压缩」；而这篇明确不走那条路，理由是长度不可控、成本高、压缩率上不去
- 两者产出的形态不同：Tether 的摘要要人能看懂、能解释来源；LLMLingua 的压缩提示人类读起来费劲，但只要目标模型能正确生成就算成功。评估口径因此也不同——它看下游任务指标，Tether 看机制是否可解释

## 可以带走的三个做法

- **按部分给预算**：不要对整段提示用同一个压缩率，指令与问题少压、**重复的示范多压**
- **删内容按信息量，而不是按位置**：位置截断会把关键内容一起切掉；用一个小模型算**困惑度**，就能近似判断哪些内容可以丢
- **压缩质量要跟下游任务绑在一起评估**：只看压掉了多少 token 会误导，要看压缩之后目标模型还能不能做对题
