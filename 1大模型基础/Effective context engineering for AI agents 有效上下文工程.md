# 为 AI 智能体做好上下文工程（Effective context engineering for AI agents）

对于 AI 智能体来说，**上下文**是一种关键但有限的资源。本文讨论如何有效地策展与管理驱动**智能体**的上下文。

提示工程（prompt engineering）作为应用 AI 的关注焦点持续了几年之后，一个新的说法开始凸显：上下文工程（context engineering）。用语言模型构建应用，重点正在从「为提示找到对的词句」转向回答一个更宽泛的问题：「什么样的**上下文配置**，最可能引出我们期望的模型行为？」

上下文指的是从大语言模型（LLM）采样时被纳入的那一组 token。要解决的工程问题是：在 LLM 自身的约束下优化这些 token 的作用，从而稳定取得期望的结果。要有效地驾驭 LLM，往往需要「在上下文中思考」——考虑模型在任一时点可用的整体状态，以及这个状态可能引出哪些行为。

本文讨论上下文工程这门刚成形的技艺，并给出一套更清晰的心智模型，用来构建可引导且有效的智能体。

## 上下文工程与提示工程

**两者的关系**：上下文工程是提示工程往下一步的延伸，目标相同（让模型做出期望的行为），范围更宽。

**提示工程管什么**：管你写给模型的那段指令——怎么写、怎么组织，重点是系统提示。

**上下文工程管什么**：管最终进入模型的那一整段 token 里放了什么、留了什么、删了什么，而且在推理过程中持续维护。

**范围差在哪里**：提示工程只看你写的那段提示；上下文工程还要管提示之外的其它内容——工具定义、MCP、外部数据、消息历史。

**为什么工作重点会转移**

早期任务多是单次的：做一次分类，或者生成一段文本。这类任务把提示写好就够了，所以提示工程占掉大部分工作量，上下文里基本也只有你写的那段提示。

现在智能体要跨多轮推理，覆盖几十分钟到几小时的时间跨度。每轮都会产生新内容——**工具返回的结果、模型的回答、用户的新输入**。这些内容不断堆进上下文，「把提示写好」这一件事不足以撑住。

**所谓「整个上下文状态」，指的是五样东西**：系统指令、工具、MCP、外部数据、消息历史。后四样都不是你手写的提示，但同样占用模型的注意力预算。

**循环式精炼**：智能体在循环里运行，每轮都会产生对下一轮可能相关的新数据。这些数据不会自动留下，而是每轮精炼一遍，再决定哪些继续留在上下文里。上下文工程既是艺术也是科学——在持续膨胀的可能信息里，挑出哪些进入有限的上下文窗口。

**一句话记法**：提示工程管「指令怎么写」，上下文工程管「整段上下文怎么摆」。

## 为什么上下文工程对构建有能力的智能体很重要

**模型也会「看不过来」**

LLM 跑得快、能吞下越来越大的数据量，但和人一样，超过某个点之后就会失焦、变糊涂。

大海捞针式的测试给出了一个说法——上下文腐化（context rot）：窗口里的 token 越多，模型从窗口里准确找出某一条信息的能力越差。这条结论来自 Chroma 的 context rot 研究（链接在文末），靠的是在不同长度上下文里查同一条信息的对照测试。

有些模型退化得缓一些，但这个毛病所有模型都有。所以**上下文是一种有限的资源**，而且越加越不划算：就像人的工作记忆有容量上限，模型也有一个「注意力预算」。每多塞一个 token，这个预算就少一点，它用在同一样东西上的注意力也被摊薄。

**为什么会这样**

原因在架构上。模型基于 transformer，每个 token 都要去看窗口里其它所有 token；n 个 token 就产生 n² 组两两关系。窗口一变长，这个数量涨得飞快，模型捕捉这些关系的能力被摊薄，于是出现了那个张力：**窗口越大，注意力越散**。

另一层原因是**训练数据的分布**：短文本远比长文本常见。所以模型对「隔着很长距离的两处内容互相呼应」见得少，专门为此训练的参数量也少。

**有办法缓解，但代价存在**

**位置编码插值（position encoding interpolation）** 这类技术，能让模型处理更长的输入：把长序列对齐回它原本训练过的较短范围。代价是它对 token 位置的判断变差。

所以这些因素带来的是一种渐变：模型在长上下文里依然很能干，只是信息检索和远程推理的精度，会比在短上下文里低一些。

**结论**：既然上下文越堆越不值钱，管好它就不是可选项。要做成有能力的智能体，每一轮放进去的东西都得用心策展。

**怎么验证自己有没有踩这个坑**：把同一条关键信息分别放进「两三千 token」和「十几万 token」的上下文里，各问同一个问题，比较答对的次数。差距明显，说明这条规律在你这套模型上同样成立。

**一句话记法**：上下文是消耗品——每塞一个 token 都在花注意力，注意力花得越散，找准信息的能力越差。

## 有效上下文的构成

**总原则**：模型的注意力有限，所以给它看的东西要少而准——用最少的高价值内容，让它做出你想要的结果。这话说起来容易，做起来全靠取舍，下面按组成部分讲怎么执行。

**系统提示的「正确高度」，就是在两种写法之间找位置**

一种**写得太具体**：把复杂的判断逻辑、各种 if-else 都塞进提示，试图逼模型一步步照做。结果提示本身变得脆弱，改一处牵动一片，越维护越乱。

另一种**写得太空**：只有「你要严谨、要专业」这类大话，模型拿不到具体的输出要求；还常常默认模型知道你的背景和意图，其实它并不知道。

合适的位置夹在两者中间：够具体，模型清楚你要什么、什么算做对；又留有余地，让它自己判断怎么做到。

打个比方：太具体像给下属一本三千条的操作手册，太笼统像只说一句「把事办好」。正确的高度像给一个有能力的同事交代任务——目标、约束、交付标准说清楚，具体怎么做交给他。

一端是脆弱的、用 if-else 写进提示的逻辑，另一端是过于笼统、或者错误假设了共享背景的提示。

**提示怎么排版**

建议把提示分成几块写，比如背景信息、指令、工具指引、输出说明，用 XML 标签或 Markdown 标题隔开。好处是模型找得到位置，你自己改动也清楚。等模型越来越强之后，具体用什么符号隔开大概会越来越不重要。

**目标是最小但完整**

写提示的目标是「不多不少」：能完整勾勒出你要的行为，又没有多余的话。最小和短是两件事——该给的背景、约束、例子一个都不能省。

**怎么找到这个「不多不少」**

先写一份只包含必要内容的最简提示，拿能拿到的最好的模型跑一遍，看它在你的任务上哪里出问题；再针对这些失败补指令、补例子。这样加进去的每一句都有理由，避免凭想象堆砌。

**工具**

工具是模型伸出去和环境打交道的手，也是它获取新内容的通道。所以有两条要求：

- 返回的信息要省 token，不能一调用就把一大坨内容倒进上下文
- 用起来要顺手，能引导模型做出高效率的动作

写工具参照写代码库里的好函数：自成一体、出错有容错、用途一眼明白、参数描述清楚没有歧义，并且贴合模型擅长的方向。

**工具集最常见的毛病是臃肿**

工具堆得太多、功能互相重叠，模型每次都得在一堆相似选项里猜该用哪个。判断标准很直白：如果连人类工程师都说不清某个场景该用哪个工具，就更不能指望模型说清。工具收得少一些，长对话里的上下文也更好维护。

**示例**

给例子（少样本提示，few-shot）依然是最有效的手段之一，强烈建议用。但别把一长串边缘情况全堆进去，试图把所有规则一次讲完，那样反而让模型抓不住重点。正确的做法是挑几个多样、典型的例子，把期望的行为展示清楚。对模型来说，例子就是「一图胜千言」。

**整体要求**

系统提示、工具、示例、消息历史，每一块都要审慎：内容要够有用，同时要紧凑。

**一句话记法**：提示写在「正确的高度」上，工具收在最小可用集，示例挑典型的几个，整段上下文保持信息丰富又紧凑。

## 上下文检索与智能体搜索

**先给智能体下个定义**

简单版：智能体就是「LLM 在循环里自己使用工具」。模型越强，能放手让它决定的事就越多——它能自己处理复杂情况，也能从错误里恢复。

**取数据有两种思路**

一种常见做法：在推理之前先把可能有用的资料检索出来塞进上下文，多用于基于嵌入的相似度检索。

另一种叫「即时（just in time）」：事先不搬数据，只记下轻量标识符——文件路径、存好的查询、网页链接。真正要用的时候，再用工具按需加载进来。

Claude Code 用的是后一种。面对一个很大的数据库，模型自己写查询、把结果存下来，再用 head、tail 这类命令翻看，全程不把整个数据对象搬进上下文。

这个思路和人一样：我们不会背下全部资料，靠的是文件系统、收件箱、书签这些外部索引，用到才取。

**标识符本身就带信息**

文件放在哪、叫什么名字，本身就提示了它的用途。tests 目录下的 test_utils.py 和 src/core_logic/ 下的同名文件，含义不同。目录层级、命名约定、时间戳，这些信号人和模型都读得懂。

**渐进式披露（progressive disclosure）**

让模型自己探索，可以一步步发现相关内容：文件大小提示复杂度，命名提示用途，时间戳可以当作相关程度的参考。模型逐层拼出理解，只在工作记忆里留住必要部分，其余用笔记另行保存。上下文窗口交给模型自己管之后，它盯住真正相关的那一小块，不会被一大堆可能无关的内容淹掉。

**代价**

自己探索比提前检索慢。而且对工程要求更高：工具要选对，判断方法要给对。引导不足时，模型会误用工具、走进无效路径、或者找不到关键信息，白白消耗上下文。

**混合策略**

有些场景的最优解是两者都用：为了速度先取一部分，剩下的交给模型自己决定要不要继续找。自主到多少合适，取决于任务。Claude Code 就是混合模式：CLAUDE.md 直接放进上下文，**glob、grep 这类基础命令**让它自己即时找文件，绕开索引过期和语法树复杂这两个麻烦。

**什么时候适合混合**

内容变化不快的场景更合适，比如**法律、金融**。往后模型越强，人工干预越少，越来越接近让模型自己判断。

**一句建议**

这个领域变化太快，「做最简单且可行的做法」仍然是给团队最好的建议。

**工程含义**：落到工具设计上，至少要有一条「能只取片段」的通道——按行段读文件、按关键词搜索、执行一条查询并只取结果，而不是把整份文件或整张表塞进上下文。

**一句话记法**：能提前取的先取一点保证速度，剩下的交给模型即时去查；取与查各占多少，由任务决定。

### 长时程任务的上下文工程

**问题**：任务一长，动作累加的信息量就装不下窗口。等窗口变大解决不了根本——塞的东西多了，真正相关的那几条会被稀释掉。

**三种办法，各自怎么用**

**压缩（compaction）**：快到上限时，把前面的对话交给模型总结，用这份摘要开一个新窗口继续。Claude Code 的做法是保住架构决策、没修完的缺陷、实现要点，丢掉冗余的工具输出，新窗口里再带上最近访问的五个文件。

难点在取舍：压得太狠，会把当时看着不重要、后来才发现关键的内容丢掉。做法是先保证不漏（把召回拉满），再去掉冗余。最容易去掉的是旧的工具调用结果——埋得那么深了，模型没必要再看原始输出。

**结构化笔记（structured note-taking，也叫智能体记忆）**：让模型把结论写到窗口外面存起来，要用的时候再读回来。开个待办清单、维护一个 NOTES.md 就属于这一类。

好处是用很小的代价换来跨轮记忆。Claude 玩宝可梦就是例子：它自己记着「在 1 号道路练了 1,234 步，皮卡丘升了 8 级，目标是 10 级」，还自己画地图、记成就、记打法。上下文重置之后，读自己的笔记接着往下干。

**子智能体架构（sub-agent architectures）**：主智能体只管高层计划，把深挖的活分给子智能体，各自用干净的窗口去查。子智能体可能查掉几万 token，但只交回一份浓缩摘要，通常一两千 token。具体过程留在子智能体内部，主智能体只看结论。研究表明，在复杂研究任务上比单智能体明显更好。

**怎么选**
- 需要大量来回对话 → 用压缩
- 里程碑清楚的迭代开发 → 用笔记
- 复杂研究、能并行探索 → 用子智能体

**一句话记法**：装不下的部分要么压成摘要、要么存到窗口外、要么交给子智能体查完只回摘要；三种做法按任务的形态挑。

## 结论

用 LLM 做应用的方式，已经发生了根本变化。模型越来越强之后，做事的难点不再只是写出完美的提示；还要在每一步都想清楚：**什么东西值得放进模型那点有限的注意力里**。不管你是在给长任务做压缩、设计省 token 的工具、还是让智能体自己临时去找数据，原则都一样：挑出最少但最有用的那点内容，让想要的结果最容易出现。

这篇文章里的这些方法，会随着模型变强继续演化。我们已经看到：模型越聪明，越不需要人规定它每一步怎么做，它能自己拿主意的地方就越多。但就算模型的能力再涨，把上下文当成一样宝贵而且有限的东西来用，这一条始终是做好智能体的关键。

现在就可以在 Claude 开发者平台上开始做上下文工程；另外那份「记忆与上下文管理」cookbook 里，有可以直接照着用的技巧和做法。

## 原文没交代、要自己定的三件事

文章给的是原则和做法，有三处它没有给，需要自己拍：

1. **压缩从什么时候开始**：原文只说「接近窗口上限」，没有给出触发比例。这个数值要按自己的模型与任务实测
2. **压缩与笔记的质量怎么验收**：原文给了 Claude Code 的取舍标准（保留架构决策、未解决的缺陷、实现要点），没有给评估指标。可以自己定两条：压完之后旧任务能不能接着做完、关键结论有没有丢
3. **即时检索用什么工具**：原文只给原则（记标识符、按需加载）和示例（head、tail、glob、grep），落到自己项目上要用哪几个工具，需要自己设计

## 对照到自己的项目（tether）

把文章里的四种做法对到 tether 上，位置立刻清楚：

- **压缩**：tether 的 history 每轮按预算裁剪，属于最轻的一档——旧的直接丢掉，不另写摘要。Claude Code 多一步：把要丢的内容先交给模型总结，再用摘要开新窗口
- **结构化笔记**：tether 的 memory（任务摘要、最近文件、文件摘要、跨轮笔记）就是这一类，存在会话里，下一轮再渲染回 prompt
- **子智能体**：tether 的 delegate 把子任务交给只读的子 agent 去查，最后只回一段结论文本，对应文章里的子智能体架构
- **即时检索**：tether 按行段读文件、按关键词搜索，对应文章的即时取数；文件摘要则相当于把取过的结果缓存一句，避免重复读

对照之后能看到一处差别：tether 的记忆由工具执行自动写入，写入的是结构化字段；Claude Code 的笔记更依赖模型自己写（待办清单、NOTES.md）。两边都算结构化笔记，写入的一方不同。
