##  DeepSpeed 与 ZeRO

**DeepSpeed 是什么**

DeepSpeed 是一个 PyTorch 优化库，让分布式训练省显存、跑得快。它的核心是**零冗余优化器**（Zero Redundancy Optimizer，ZeRO），正是它让大模型能在规模上训练起来。ZeRO 按阶段推进：

- **ZeRO-1**：**优化器**状态在各 GPU 之间切分
- **ZeRO-2**：**梯度**在各 GPU 之间切分
- **ZeRO-3**：**参数**在各 GPU 之间切分

它由微软开源，目标是让训练和推理超大规模模型变得**更简单、更高效、更经济**。横跨**模型训练、推理和模型压缩**三块，这里只看**训练相关的部分**。

它是目前大模型训练领域的核心工具之一：GPT-3、ChatGPT 的早期训练，以及 LLaMA 的一些微调版本、BLOOM 等开源模型，都用到了它。

### 5.1 冗余在哪

DP 与 DDP 里，每张卡**都存一份完整的参数、梯度和优化器状态**。这三份内容在所有卡上完全一样，属于纯冗余。

占比最大的是**优化器状态**。按 4.1 的字节数，16 字节里优化器状态占 12，接近四分之三。

**ZeRO（Zero Redundancy Optimizer）** 是 DeepSpeed 训练优化的核心，一套**减少分布式训练内存占用的技术**。它从消除这块冗余入手：把优化器状态按参数切分到不同显卡上，每张卡**只保留自己负责的那一片，不再整体复制**。需要用到别人的那部分时，再通过通信换回来。

### 5.2 基本思路

每张卡照常处理自己的 batch，但**只长期保存自己负责的那一片参数、梯度和优化器状态**。

- 计算需要别的参数时，临时从对应的卡上**取**回来，算完立即释放，不留在本地。
- 参数更新完成后，每张卡把自己那片新参数发给其他卡，替换掉对应位置的旧值。

显存占用因此按卡数均摊，代价是把「算的时候全都要」换成了「**用一块取一块**」的**通信**开销。

### 5.3 三级切分

ZeRO-DP 用来替代朴素的数据并行：DP 把模型**复制多份到各块卡上**，显存冗余很大；ZeRO-DP 把三样东西逐级切开，数字越大切得越多，省下的显存越多，付出的通信也越重。

![[zero-三级切分.svg|803]]

- **Stage 0**：不做任何切分，就是**普通的 DDP**。
- **Stage 1**：分割**优化器状态**（Partitioning optimizer state），内存占用降到原来的 **1/4** 左右。
- **Stage 2**：在上一级基础上再分割**梯度**（Partitioning gradients）。
- **Stage 3**：再把**模型参数**也分割（Partitioning model parameters）。理论上只要总显存够大，就能跑任意大的模型。

后三级是累加关系，Stage 3 三样全切。实际使用时在 `deepspeed.json` 的 `zero_optimization.stage` 里填 0 到 3。


7.5B 参数、64 张卡，四个阶段**每张卡**的显存依次是 **120 GB、31.4 GB、16.6 GB、1.9 GB**：

![[zero-四级显存.svg|709]]

柱子里三段的高度按各自的字节数折算。优化器状态占了 120 GB 里的 90，切到 Stage 3 的 1.9 GB 时，它仍然是最大的一段。这套四级在 DeepSpeed 文档里也写作 **Baseline、P_os、P_os+g、P_os+g+p**，与 Stage 0 到 3 一一对应。

这四个数字怎么来的，正是后面三节的内容。
### 5.4 Stage 0：普通数据并行

Stage 0 的含义是**什么都不切**。每张卡仍存整份参数、梯度、优化器状态，显存占用与 PyTorch 的 DDP 一样。这一节的重点是把 DeepSpeed 的封装跑通；省显存是后面三级的事。好处在下一节就显出来：把 stage 改成 1、2、3 时，训练代码一行都不用动，只有配置文件里的数字变。所以 Stage 0 既是起点，也是后面三级的对照。

用 DeepSpeed 做**数据并行**，不用像 PyTorch 的 DDP 那样手动 `init_process_group`、再把模型包进 `DistributedDataParallel`。调用 `deepspeed.initialize` 把模型包进 `DeepSpeedEngine`，进程组、梯度同步、优化器包装这些活都由它内部处理。

下面这段脚本做四件事，按顺序看：

1. 从环境变量里读出自己是第几张卡。
2. 按普通方式加载模型。
3. 写一份最小配置。
4. 交给 initialize 接管，并打印当前 stage 做确认。

```python
import os
import deepspeed
from transformers import BloomForCausalLM

# DeepSpeed 拉起进程时自动设置 LOCAL_RANK，指向当前进程绑定的那张卡
rank = int(os.getenv("LOCAL_RANK", "0"))

# 先按普通方式加载模型，随后交给 engine 接管
model = BloomForCausalLM.from_pretrained("bigscience/bloom-560m")

deepspeed_config = {
    # 每张卡每次前向喂多少条样本；总 batch 还要再乘卡数与梯度累积步数
    "train_micro_batch_size_per_gpu": 1
}

# initialize 负责建进程组、包优化器、按配置准备 ZeRO
# 返回四个值依次是 engine、优化器、训练 dataloader、学习率调度器
model_engine, _, _, _ = deepspeed.initialize(
    model=model,
    model_parameters=model.parameters(),
    config=deepspeed_config
)

# 配置里没写 zero_optimization，所以这里打印出来是默认的 Stage 0
print(f"Device {rank} - ZeRO Stage: {model_engine.zero_optimization_stage()}")
```

`deepspeed.initialize` 返回四个值，这里只用第一个：封装好的 engine，后面训练时的前向、反向、`step()` 都走它。最后那行 `print` 只是核对：`zero_optimization_stage()` 读的是生效的配置值，改 stage 只改配置，代码不动。

**怎么跑起来**

脚本自己不起多进程，交给随包安装的命令行工具：

```bash
deepspeed deepspeed_stage_0.py
```

这个工具会按可见的卡数拉起同样多的进程，每个进程跑一遍同一个脚本，各自从环境变量里拿到自己的 rank。所以下面有 8 行输出，顺序不定，那是 8 个进程并发打印的结果。

```text
Device 1 - ZeRO Stage: 0
Device 4 - ZeRO Stage: 0
Device 2 - ZeRO Stage: 0
Device 3 - ZeRO Stage: 0
Device 6 - ZeRO Stage: 0
Device 7 - ZeRO Stage: 0
Device 0 - ZeRO Stage: 0
Device 5 - ZeRO Stage: 0
```

`deepspeed` 在初始化过程中**拉起多个进程**，每个进程绑一张 GPU。配置里不显式写 `zero_optimization`，默认就是 Stage 0。

**训练循环**

训练代码与普通 PyTorch 几乎一样，差别只有三处替换。数据这边要注意一件事：每个进程必须读不同的切片，否则各卡算出来的是同一份梯度，求平均之后等于只用了一份数据。`DistributedSampler` 负责切分，它按进程序号把数据集分成 `world_size` 份。

```python
import os
import torch
from torch.utils.data import DataLoader
from torch.utils.data.distributed import DistributedSampler
from transformers import AutoTokenizer, DataCollatorForLanguageModeling

# DeepSpeed 会自动设置 WORLD_SIZE，表示参与训练的卡数
world_size = int(os.getenv("WORLD_SIZE", "1"))
tokenizer = AutoTokenizer.from_pretrained("bigscience/bloom-560m")
# mlm=False 表示按因果语言建模拼样本：输入是前文，标签是后移一位
collator = DataCollatorForLanguageModeling(tokenizer, mlm=False)

# 只取 64 条做个演示
train_dataset = load_wikitext(tokenizer, collator).select(range(64))
train_dataloader = DataLoader(
    train_dataset,
    batch_size=1,
    shuffle=False,
    # 每个进程分到不同切片，互相不重复
    sampler=DistributedSampler(train_dataset, num_replicas=world_size),
)

for batch in train_dataloader:
    device = torch.device("cuda", rank)
    input_ids = batch["input_ids"].to(device)
    labels = batch["labels"].to(device)

    # 前向：模型换成了 engine，其余用法不变
    outputs = model_engine(input_ids, labels=labels)
    # 反向：梯度归约由 DeepSpeed 内部完成
    model_engine.backward(outputs.loss)
    # 更新参数：内部会调用优化器和学习率调度器
    model_engine.step()
```

**和常规 PyTorch 训练的差别**
三处替换：`model(x)` 换成 `model_engine(x)`，`loss.backward()` 换成 `model_engine.backward(loss)`，`optimizer.step()` 换成 `model_engine.step()`。
梯度同步、混合精度、梯度累积都在 **engine 内部处理**，外面不用再写。

换句话说，分布式相关的活都从训练代码里挪进了 engine：梯度在哪一步同步、要不要混合精度、累积几步，统统由配置决定。

**实测显存**

`memory_status()` 可以直接打印当前卡上的显存占用：

```python
from deepspeed.runtime.utils import memory_status

for batch in train_dataloader:

    labels = batch["labels"].to(device)
    outputs = model_engine(input_ids, labels=labels)
    model_engine.backward(outputs.loss)
    model_engine.step()

if rank == 0:

```

### 5.5 Stage 1：只切优化器状态

每张卡仍保留完整的 fp16 参数和梯度，前向、反向各自独立完成，不需要向别的卡要东西。**被切开的是优化器状态：Adam 的动量、方差、fp32 主权重按参数分成 $M$ 份，每张卡只保存自己那一份**。

一次迭代这样走：
1. 每张卡独立做前向和反向，得到完整梯度。
2. 反向结束后做 reduce-scatter，每张卡只留下自己负责那一段的归约结果，其余段丢掉。
3. 每张卡用这一段梯度更新自己的优化器状态和 fp32 参数。
4. 做 all-gather，各卡把更新后的 fp16 参数广播出去，补齐成完整参数。

**和 DDP 的区别**

DDP 用 all-reduce，每张卡拿到完整梯度后自己更新全部参数。ZeRO-1 把「更新」这一步也切了，每张卡只更新 $\frac{1}{M}$，再把结果拼回来。

显存上省的是那 90 GB 的优化器状态：切成 64 份后每卡 **1.4 GB**，加上参数 15 GB、梯度 15 GB，合计 **31.4 GB**，对应图里 Stage 1 那根柱子。

### 5.6 Stage 2：再切梯度

在 Stage 1 的基础上多切一样东西：**梯度**。

**切分的变化**

参数仍然完整保存，优化器状态照旧切分，梯度也切成 $M$ 份。每张卡只保留与自己负责那段参数对应的梯度，其余段的梯度不再驻留显存。

**一次迭代的流程**

1. 各卡独立做前向和反向，算出完整梯度。
2. 反向过程中做 reduce-scatter，每张卡只留下自己负责那一段的归约结果，**其余段算完立即丢弃**。
3. 用这一段梯度更新自己的优化器状态和 fp32 参数。
4. all-gather 把更新后的 fp16 参数拼回完整。

**关键变化在哪**

Stage 1 要等完整梯度都算出来、reduce-scatter 做完才释放；Stage 2 是算一段归约一段，不用让整份梯度同时存在显存里，峰值因此下降。

显存上省的是那 15 GB 梯度：切成 64 份后每卡 0.23 GB，加上参数 15 GB、优化器 1.4 GB，合计 **16.6 GB**，对应图里 Stage 2 那根柱子。

### 5.7 Stage 3：连参数也切

三样东西全部切开：参数、梯度、优化器状态。每张卡只持有整个模型的 $\frac{1}{M}$。

**和前两级的区别**

Stage 1、2 里参数始终完整，每张卡都能独立跑完整的前向。Stage 3 把参数也切了，任何一张卡手上都只有一部分层的部分权重，单独一张卡算不动整个模型。

**计算时怎么拿到参数**

1. 算某一层之前，各卡把这一层的参数 all-gather 过来，临时拼成完整的一份。
2. 这一层前向算完，立刻释放刚拼起来的参数，只留自己负责的那片。
3. 反向也是用一次取一次，用完即放。
4. 梯度按 Stage 2 的方式 reduce-scatter，优化器状态按 Stage 1 的方式切分。

**代价**

通信量比前两级大得多：每一层的前向和反向都要 all-gather 一次参数。省显存最多，速度也最慢，实际使用时常配合 activation checkpointing 一起上。

**显存**

$(2 + 2 + 12) \times 7.5\text{B} \div 64 \approx 1.9$ GB，对应图里 Stage 3 那根柱子。切到这一步，单卡才装得下百亿参数级别的模型。

### 5.8 三级的取舍

级数往上走，省下的显存与付出的通信是同一个天平的两端。

- Stage 1 省的是最大的那块（优化器状态，90 GB 里的大头），通信只多一次 reduce-scatter 与 all-gather，实际使用最普遍。
- Stage 2 再省 15 GB，靠的是边算边丢，通信量与 Stage 1 基本相同。
- Stage 3 把参数也切了，显存能压到 $\frac{1}{M}$，代价是每一层都要额外 all-gather 一次参数，速度最慢。

模型能装下时，优先停在 Stage 1 或 2；装不下时再上 Stage 3，同时把 activation checkpointing 打开，用重算换显存。

### 5.9 速度不是一路变快

显存一路降，速度不是。判断快慢只看一件事：**通信量涨了多少**。

以 DDP 每步的**通信量**为基准（梯度做一次 all-reduce）：

- **Stage 1**：梯度做 reduce-scatter、参数做 all-gather，两段拼起来与一次 all-reduce 基本相当，通信量与 DDP 持平。
- **Stage 2**：同样是一次 reduce-scatter 加一次 all-gather，只是梯度边算边丢，通信量与 Stage 1 相同。
- **Stage 3**：参数被切开了，前向要按层 all-gather、反向再走一遍，总通信量约为 DDP 的 1.5 倍，而且是一层一层地取，延迟被切成许多小段。

所以速度上大致是：Stage 1 与 Stage 2 接近 **DDP**，Stage 3 慢一截，**带宽越紧张差得越多**。

**一个例外：能跑起来的那一档最快**

显存不够时，不开 ZeRO 会直接 OOM，或者只能把 batch 压到很小、频繁换出，实际吞吐更差。这时 Stage 3 虽然通信多，却是唯一能跑完的配置，速度上它反而赢。

**怎么选**

能用 1 或 2 就别上 3。非上 3 不可时，配 activation checkpointing、加大 micro-batch、用梯度累积补回总 batch，把通信摊薄一点。







# ZeRO-1 的本质：只切优化器状态，把“更新”也分给每张卡
![[Pasted image 20261105150442.png|467]]
## 一、图怎么读

```
████████  ████████  ████████  ████████  ████████  ████████    ← fp16 参数（完整）
████████  ████████  ████████  ████████  ████████  ████████     ← fp16 梯度（完整）
████      ← fp32 主权重 + 一阶动量 + 二阶动量（只留 1/M，又窄又厚）
```

- **上面两条保持满宽**：每张卡都持有**完整参数和完整梯度**
- **下面那块只占 1/M 宽**：优化器状态被切成 M 份，每卡一份

“窄但厚”是因为同样一段参数，fp32 状态要占 12 字节，是 fp16 参数（2 字节）的 6 倍。

## 二、优化器状态占比 75%

以 7.5B 模型、每卡一份完整状态为例：

| 组成 | 大小 | 占比 |
|---|---|---|
| fp16 参数 | 15 GB | 12.5% |
| fp16 梯度 | 15 GB | 12.5% |
| **优化器状态** | **90 GB** | **75%** |

**先切它，因为它的收益最大，而且不改前向计算**——参数完整，任何一张卡都能独立跑完整个模型，一行代码都不用改模型结构。

## 三、一次迭代四步（`[[DeepSpeed 与 ZeRO#5.5 Stage 1：只切优化器状态]]`）

```
① 各卡独立前向 + 反向         → 每卡都有完整梯度
② reduce-scatter            → 每卡只留自己负责那 1/M 段
③ 各自用这一段更新            → 优化器状态 + fp32 主权重（都只有 1/M）
④ all-gather                → 拼回完整的 fp16 参数，供下轮前向
```

**关键是第 ③ 步：更新被拆分了。**

以前是“每卡都拿完整梯度、都算一遍完整更新”；现在是“每卡只管 1/M 的参数，各算各的”。

## 四、通信量没有增加的原因

这是 ZeRO-1 最容易被误解的地方——**all-reduce 本来就是两段**：

$$
\text{AllReduce}=\underbrace{\text{reduce-scatter}}_{\text{各卡留一段}}+\underbrace{\text{all-gather}}_{\text{拼回完整}}
$$

DDP 把两段连在一起做，中间没有空隙。ZeRO-1 只是**在 reduce-scatter 和 all-gather 之间插入“本地更新”这一步**：

```
DDP:    梯度 ──all-reduce（两段合一）──▶ 完整梯度 → 各自更新全部参数
ZeRO-1: 梯度 ──reduce-scatter──▶ 1/M 梯度 → 更新 1/M 状态 ──all-gather──▶ 完整参数
```

**通信总量与 DDP 相同，但每张卡少存 87.5% 的优化器状态。**

## 五、省了多少

$$
\text{每卡显存}=4N+\frac{12N}{M}\ \text{字节}
$$

| 配置 | 每卡显存（7.5B 模型） |
|---|---|
| Stage 0（DDP） | 15 + 15 + 90 = **120 GB** |
| Stage 1，M=8 | 15 + 15 + 11.25 = **41.25 GB** |
| Stage 1，M=64 | 15 + 15 + 1.4 = **31.4 GB** |

M 越大越接近下限 `4N`（参数 + 梯度），**优化器状态这一块被彻底摊薄**。

## 六、它没解决的问题

| 仍然完整保存      | 后果              |
| ----------- | --------------- |
| **fp16 参数** | 模型本身多大，每卡就得放多大  |
| **fp16 梯度** | 反向时****仍要存在完整梯度 |

所以 Stage 1 只能把“16 字节/参数”压到“4 字节/参数”附近，**参数量超过单卡容量时依然放不下**——那要等 Stage 2 切梯度、Stage 3 切参数。

## 七、一句话

**ZeRO-1 只把优化器状态按卡切分，顺带把“参数更新”这一步也并行化；它复用了 all-reduce 本来就有的两段结构，在中间插入本地更新，所以通信量不增、显存降 75%，是三者中性价比最高的一刀。**


# ZeRO-2 的本质：梯度只需要保留自己负责的那一段，在反向传播时边算边归约

![[Pasted image 20261105150834.png]]

## 一、读图：从两条满宽变成一条满宽

```
████████ ████████ ████████ ████████ ████████ ████████ ████████  ← fp16 参数：仍完整
████                                                            ← fp16 梯度：只留 1/M
████                                                            ← 优化器状态：1/M
```

对比 ZeRO-1 的图：**参数那条没变，梯度和优化器状态一起变成窄条。**

## 二、核心洞察：需要全部梯度的理由是错的

Stage 1 里每张卡都要保存完整梯度，因为当时的顺序是：

```
算完整个反向 → 得到完整梯度 → reduce-scatter → 只留 1/M → 更新
                ↑
         这一步让完整梯度必须存在
```

但仔细想：**每张卡最终只用 1/M 的梯度去更新**。

那另外 (M−1)/M 的梯度保存着干什么？**只为了在 reduce-scatter 时贡献出去，然后丢掉。**

于是 Stage 2 把这两个动作合并：

```
算一段 → 立刻归约这一段 → 留下自己那份 → 其余丢弃 → 算下一段
```

**完整梯度从未同时存在过。**

## 三、反向传播的时序

反向是**从后往前**逐层算的，天然可以流式处理：

```
反向第 L 层  ──▶ 梯度块 L  ──reduce-scatter──▶ 是"我的"就留，不是就丢
反向第 L-1 层 ──▶ 梯度块 L-1 ──reduce-scatter──▶ 同上
   ...
反向第 1 层  ──▶ 梯度块 1  ──reduce-scatter──▶ 同上

此刻每卡手上只有自己的 1/M 梯度，参数完整，优化器状态 1/M
```

工程上按 **bucket（桶）** 做：把若干层梯度打包成固定大小的块，凑满一块就归约一次，让通信和后续层的反向计算重叠（`overlap_comm`）。

## 四、与 Stage 1 的关键差别：峰值，而不是最终占用

| | Stage 1 | Stage 2 |
|---|---|---|
| 完整梯度何时存在 | 整个反传过程都存在，直到 reduce-scatter 结束 | **任何时刻都只有部分** |
| 显存峰值 | 参数 + **完整梯度** + 1/M 状态 | 参数 + 1/M 梯度 + 1/M 状态 |
| 归约时机 | 反传结束后统一做 | **反传过程中流式做** |

**Stage 1 的“省”是稳态数值上的省，峰值仍在。Stage 2 才是真正把峰值压下来。**

这点在实际训练里很关键：OOM 通常发生在反向传播的峰值时刻，而不是稳态。

## 五、省了多少

$$
\text{每卡显存}=2N\ (\text{参数})+\frac{2N\ (\text{梯度})+12N\ (\text{状态})}{M}
$$

7.5B 模型、M=64：

| 配置 | 参数 | 梯度 | 优化器 | 合计 |
|---|---|---|---|---|
| Stage 0 | 15 | 15 | 90 | **120 GB** |
| Stage 1 | 15 | 15 | 1.4 | **31.4 GB** |
| **Stage 2** | 15 | **0.23** | 1.4 | **16.6 GB** |

**梯度从 15 GB 降到 0.23 GB**，剩下的大头就是参数本身。

## 六、代价

| 代价 | 说明 |
|---|---|
| **通信与计算必须重叠** | 否则归约会把反向拖成串行，速度掉得厉害 |
| **实现复杂度高** | 需要梯度分桶、异步通信、生命周期管理 |
| **对 bucket 大小敏感** | 太小通信频繁，太大又退化回 Stage 1 的峰值 |
| **跨节点时更依赖带宽** | reduce-scatter 走网络，NVLink 与 IB 差距明显 |

另外，Stage 2 只改“梯度怎么存”，**前向仍然每卡完整参数、不需要通信**——这仍是它最大的好处。

## 七、一句话

**ZeRO-2 发现“梯度只为更新服务，而更新只用 1/M”，于是把 reduce-scatter 拆进反向传播过程里逐层执行，让完整梯度根本没有机会同时存在；省的是峰值显存，代价是通信必须和计算重叠，否则会变慢。**



# 三行表示三块显存，箭头表示数据流向
![[Pasted image 20261105151357.png|418]]
这样理解基本正确，但准确来说：**每一行对应一种数据，而非一个阶段**。箭头才表示前向和反向传播。

| 行 | 内容 | 箭头 | 什么时候用 |
|---|---|---|---|
| 第一行 | **fp16 参数** W | → 左到右 | 前向要读，**反向也要读** |
| 第二行 | **fp16 梯度** ∂L/∂W | ← 右到左 | 反向逐层产生 |
| 第三块 | **fp32 优化器状态**（主权重 + 动量 + 方差） | 无 | 只在进行 `optimizer.step()` 时读写 |

## 一个需要纠正的地方

**第一行不只属于前向传播。**

参数在反向传播时也要用到，并且用得更多：
- 前向：`y = xW`
- 反向：算 `∂L/∂x` 和 `∂L/∂W` 都要 `W`

因此，**参数**贯穿前向和反向两个阶段。图中把箭头画在第一行，只是表示“前向的计算流从这里开始”。

**真正只在一个阶段出现的是梯度**——前向时还不存在，反向时才逐层算出来。

## 为什么梯度箭头朝左

反向传播从最后一层开始，向前推：

```
前向：  层1 → 层2 → 层3 → loss          （箭头 →）
反向：  loss → 层3 → 层2 → 层1          （箭头 ←）
```

第一个计算出梯度的是**最后一层**，所以箭头朝左，表示反向逐层推进。

## 第三块为什么没有箭头

优化器状态**不参与张量流**，它不在计算图中：

```
前向/反向：只在参数和梯度之间流动
step：    拿梯度 + 状态 → 算出新参数，然后结束
```

它更像“账本”，只在每步末尾被读一次、写一次，所以在图上没有方向。

## 顺带对上字节数

这三块正好对应笔记里的 `2 + 2 + 12`：

| 行 | 字节/参数 |
|---|---|
| 参数 | 2（fp16） |
| 梯度 | 2（fp16） |
| 优化器状态 | 12（fp32 主权重 4 + 动量 4 + 方差 4） |

**ZeRO 的三级切分，就是沿着这三行逐层处理的**：Stage 1 切第三块，Stage 2 再切第二行，Stage 3 连第一行也切。

## 一句话

**这三行是三块显存内容：参数、梯度、优化器状态。箭头才表示阶段——向右表示参数被前向读取，向左表示梯度沿反向产生，第三块没有箭头，因为优化器只在 step 时用到，不参与前向或反向的数据流。**


# 更新阶段各卡完全独立，但更新完必须“拼图”

> **你的问题（整理后）**：在 ZeRO-1/ZeRO-2 中，每张卡只保留自己负责的那一段优化器状态与梯度。那么本地更新完成后，是否需要把自己的结果发送给其他卡？另外，“第一次算的时候”各卡是否已经各自算好、彼此互不依赖？

这个问题可拆成两层：**更新时要不要等别人？不需要。更新完要不要交换？需要，但交换的是参数片段，不是梯度。**

## 一、更新阶段：各卡互不依赖

关键前提是**索引对齐**：

```
第 k 张卡负责的参数片段 [k]
  ├─ 它的梯度片段 [k]        ← reduce-scatter 后留下的
  ├─ 它的 fp32 主权重 [k]
  └─ 它的动量 m[k]、方差 v[k]
```

这四个东西**下标完全相同**，构成一套完整的“局部更新单元”：

$$
W_{[k]} \leftarrow W_{[k]} - \eta\cdot\frac{\hat m_{[k]}}{\sqrt{\hat v_{[k]}}+\epsilon}
$$

**公式里没有出现任何其他卡的数据**。因此，第 k 张卡算自己的那一段时，完全不需要等第 j 张卡。这也是它比 DP 快的原因：**更新本身被并行化了**。

## 二、但更新完必须交换：只有 1/M 是最新的

更新结束后，显存里是这样：

```
卡0:  [新][旧][旧][旧][旧][旧][旧][旧]
卡1:  [旧][新][旧][旧][旧][旧][旧][旧]
卡2:  [旧][旧][新][旧][旧][旧][旧][旧]
                ...
```

**每张卡只有自己那 1/M 是新的，其余仍是上一轮的旧参数。**

但下一轮前向需要**完整且一致的参数**，所以必须做一次 **all-gather**：

```
卡0 把自己那段发出去 → 各卡收齐 8 段 → 拼成完整的 8/8
```

结果是每张卡都重新拥有完整的新参数：

```
卡0:  [新][新][新][新][新][新][新][新]
卡1:  [新][新][新][新][新][新][新][新]
                ...
```

**注意交换粒度**：每张卡只发出自己的 1/M，但收到别人的 (M−1)/M，最终拼成全量。

## 三、完整时序（以 4 卡为例）

```
① 前向      各卡用完整参数，独立计算，无通信
② 反向      各卡算出完整梯度，无通信
③ reduce-scatter   交换梯度，各卡留下自己那 1/4
④ 本地更新   各卡只更新自己的 1/4 参数与状态    ← 不需要等任何人
⑤ all-gather       各卡发出自己的 1/4，收齐其余 3/4，拼成完整参数
⑥ 回到 ①
```

**第 ③ 步交换的是梯度，第 ⑤ 步交换的是更新后的参数片段。** 两者目的不同，不能混为一谈。

## 四、容易产生的两个误解

**误解 1：“算好了要传给别的卡去更新”**

不对。**每张卡更新的是自己的那一段，不需要别人代为更新。** 别人手里根本没有这段的优化器状态（已经被切走了），想代劳也做不到。

正确的说法是：**各人更新各自的一段，然后大家交换碎片、拼回完整。**

**误解 2：“第一次算的时候其他卡算好了”**

不存在“第一次”的特殊情况。每一轮的流程都相同：

- 各卡**同时**开始反向，速度可能有快有慢，但都要等 reduce-scatter 完成
- reduce-scatter 本身就是一个**同步点**：所有卡的梯度都到齐了，才能算出正确的平均值

所以不是“其他卡先算好了在等我”，而是**大家都得等到这一步同步完成**。

## 五、和 Stage 3 的差别（顺带厘清）

| | Stage 1 / 2 | Stage 3 |
|---|---|---|
| 参数 | **每卡完整**，前向无需通信 | 每卡只有 1/M，**前向要先 all-gather** |
| 通信时机 | 只在反向后（一遍） | 每层前向、反向都要 gather（多遍） |
| 单卡能否独立跑前向 | 能 | **不能** |

Stage 3 之所以慢，就是因为**每个算子都要现拼参数**；Stage 1/2 只在每步末尾拼一次。

## 一句话

**更新阶段各卡各管一摊、天然并行、互不等待；但更新完每张卡只在 1/M 的维度上是新的，必须通过 all-gather 互相交换片段，才能拼回完整参数供下一轮前向——所以是“各人更新各自的，再交换拼图”，不是“算好交给别人更新”。**


# 通信量相同，差别在于“何时传、传的时候有没有挡住计算”

> **你的问题（整理后）**：ZeRO-1 虽然完整保存了梯度，但依然要把梯度传播出去（reduce-scatter）。那么它的通信成本是否与 ZeRO-2 完全相同？

## 一、结论：通信量确实相同

| 阶段 | 每步每卡交换量 | 与 DDP 相比 |
|---|---|---|
| DDP / Stage 0 | reduce-scatter + all-gather ≈ **2N** | 1× |
| **Stage 1** | reduce-scatter N + all-gather N ≈ **2N** | 1× |
| **Stage 2** | 完全相同**2N** | 1× |
| Stage 3 | 每层 gather 参数 + 梯度归约 ≈ **3N** | 1.5× |

**Stage 1 与 Stage 2 的通信字节数完全一致。**

## 二、为什么“存不存”不影响“传多少”

**通信量由“必须交换什么”决定，与“本地保留什么”无关。**

需要交换的东西永远是两样：

```
① 各卡的梯度要合成平均梯度   → 这必须要传
② 更新后的参数要传遍所有卡   → 这也必须要传
```

两件事一件都不能少，**传的量就是 2N**。至于本地留不留那份完整梯度，只是“要不要在显存里多放一份副本”，与传输无关。

**“存了 → 所以要多传”是错觉：存与传是两个独立维度。**

## 三、真正的差别只有两点

**① 驻留时间：峰值显存**

```
Stage 1:  反向全程持有完整梯度 → 反传结束 → 一次性 reduce-scatter
          峰值 = 参数 + 完整梯度 + 1/M 状态

Stage 2:  反向逐层归约 → 算完一块丢一块
          峰值 = 参数 + 1/M 梯度 + 1/M 状态
```

**② 通信时机：能不能与计算重叠**

```
Stage 1:  [====== 反向计算 ======][== 通信 ==]     串行，通信裸露在外
Stage 2:  [计][通][计][通][计][通][计][通]          交错，通信被计算掩盖
```

**Stage 2 的收益主要来自“把通信藏进计算里”，而非“少传数据”。**

## 四、因此实际吞吐通常不同

| | Stage 1 | Stage 2 |
|---|---|---|
| 通信量 | 2N | 2N |
| 通信是否可重叠 | 难（要等梯度全部就绪） | 容易（bucket 流式） |
| 实测吞吐 | 较低 | 较高 |
| 实现复杂度 | 低 | 需要调 bucket 大小 |
| 显存峰值 | 高 | 低 |

**但需要说明一点**：Stage 2 的吞吐优势不是无条件的。如果 **bucket 设得太小**，归约会被切成很多碎片，启动开销和同步次数上升，**反而可能比 Stage 1 更慢**。工程上 `reduce_bucket_size` 的调参就是这个原因。

## 五、所以选择依据不是通信

既然通信一样，选择的判断标准就变成：

- **显存是否够用**：够 → Stage 1 更简单稳妥；不够 → Stage 2
- **是否卡在反向峰值**：OOM 常发生在反传结束那一刻，Stage 2 正是削这个峰
- **能否接受调参成本**：Stage 2 对 bucket、overlap 配置更敏感

## 一句话

**ZeRO-1 与 ZeRO-2 的通信量完全相同（都是 2N，与 DDP 一致），因为交换内容和交换次数都没变；Stage 2 省的是显存峰值、赚的是通信与计算的重叠，不是带宽。**


# ZeRO-3 采用“算一层拼一层”的方式，解决参数无法完整放在单张卡上的问题

![[Pasted image 20261105152439.png|428]]

> **你的问题（整理后）**：ZeRO-3 把参数也切分了，单张卡上只有模型的一部分权重，因此无法独立完成前向传播。这个问题是如何解决的？

## 一、问题本质：参数不完整，前向确实跑不动

Stage 1/2 的前提是“每卡都有完整参数”，所以前向可以独立执行。Stage 3 打破了这个前提：

```
Stage 2：卡0 = [全部参数]       → 前向随便跑
Stage 3：卡0 = [1/8 参数]       → 算第 1 层时缺 7/8，动不了
```

**“装得下”与“算得动”在 Stage 3 里变成了一对矛盾。**

## 二、解法：算到哪层，就把那层参数临时拼齐

核心思路一句话：**参数平时切成 8 份，用的时候临时拼成完整的一份，用完立刻拆掉。**

```
算第 1 层
├─ all-gather 第 1 层的参数（8 张卡各出 1/8 → 拼成一整层）
├─ 前向计算第 1 层
├─ 释放刚拼的完整参数，只留自己那 1/8
│
算第 2 层
├─ all-gather 第 2 层参数
├─ 前向计算
├─ 释放
│
...
```

**任何时刻，显存里最多只有“一层”的完整参数，而不是整个模型。**

这就是图里那些红色箭头的含义：**参数不是本地就有，要从别的卡“取”过来。**

## 三、反向传播怎么办

反向需要两层信息：**本层激活值和本层完整权重**。但前向拼好的参数早已释放，所以反向时要**再取一次**：

```
反向第 L 层
├─ 重新 all-gather 第 L 层参数
├─ 用激活值算梯度
├─ 梯度进入 reduce-scatter（每卡只留自己负责的 1/M）
├─ 释放该层完整参数
```

**所以每层的参数在一轮迭代中要被 gather 两次：前向一次、反向一次。**

如果同时开了 activation checkpointing，前向不保存激活值，反向时要**重算前向**，于是 gather 次数还要增加。

## 四、通信代价：约 1.5 倍

| 阶段 | 每步每卡通信量 |
|---|---|
| Stage 0/1/2 | ≈ **2N** |
| **Stage 3** | ≈ **3N**（1.5×） |

拆开算：

$$
\underbrace{N}_{\text{前向 gather}}+\underbrace{N}_{\text{反向 gather}}+\underbrace{N}_{\text{梯度 reduce-scatter}}\approx 3N
$$

省显存最多，代价也最直接：**通信涨 50%，并且每层都要经历一次同步。**

## 五、工程上如何把代价压住

| 手段 | 作用 |
|---|---|
| **参数预取（prefetch）** | 算第 k 层时，提前 gather 第 k+1 层，掩盖通信延迟 |
| **分桶（bucket）** | 把若干层打包一起 gather，减少同步次数 |
| **及时释放** | 用完立刻 free，否则峰值会退回 Stage 2 |
| **显存池复用** | 复用 gather buffer，避免反复 malloc |
| **与 checkpointing 配合** | 省下的激活显存可以用来放临时参数 |

**没有 prefetch 的 Stage 3 会非常慢**——通信完全暴露在关键路径上，每层都要停顿等待。

## 六、显存实际怎么算

$$
\text{每卡}=\underbrace{\frac{12N}{M}}_{\text{优化器}}+\underbrace{\frac{2N}{M}}_{\text{梯度}}+\underbrace{\frac{2N}{M}}_{\text{常驻参数}}+\underbrace{2N_{\text{layer}}}_{\text{临时完整层}}+\text{激活}
$$

**多出来的 `2N_layer` 是 Stage 3 的隐藏成本**：虽然参数切了，但任何时刻都要能放下一整层。层越大，这个临时峰值越高。

## 七、三级对比

| | 参数 | 前向通信 | 单卡可独立前向 | 适用场景 |
|---|---|---|---|---|
| Stage 1 | 完整 | 无 | ✅ | 优化器状态是瓶颈 |
| Stage 2 | 完整 | 无 | ✅ | 梯度峰值是瓶颈 |
| Stage 3 | 1/M | **每层 gather** | ❌ | 单卡装不下整个模型 |

**Stage 3 是唯一能突破“模型必须装进单卡”这一限制的方案**，也因此最慢。

## 一句话

**ZeRO-3 用“空间换通信”的极端版本：参数平时切碎，算到哪层就把哪层临时拼齐，算完立刻拆掉——单卡永远装不下完整模型，但也永远不需要装下，代价是每层两次 gather、通信涨到 1.5 倍，且必须靠预取把延迟藏起来。**


# ZeRO-3 只切分存储，不切分计算，属于“分片数据并行”

> **你的问题（整理后）**：ZeRO-3 把参数切分到各卡、单卡无法独立前向，这种思路是否可以理解为模型并行？

## 一、判断依据：看每张卡负责计算什么

**模型并行切的是计算图**：

```
TP（张量并行）：把某一层的矩阵按列/行切开
    卡0 算 W 的左半列 → 卡1 算右半列 → all-reduce 拼结果

PP（流水线并行）：把层分给不同卡
    卡0 跑第 1-10 层 → 卡1 跑第 11-20 层
```

每张卡只执行整体计算的一部分，需要和别人拼出完整结果。

**ZeRO-3 切的是存储**：

```
每张卡都算“完整的第 1 层”，只是参数平时不在本地
    卡0：取来整层参数 → 算自己那份 batch → 算完释放
    卡1：取来整层参数 → 算自己那份 batch → 算完释放
```

**每张卡执行的是同一层的完整算子**，区别只在处理不同的数据。

## 二、对比

| | 模型并行（TP / PP） | ZeRO-3 |
|---|---|---|
| 切什么 | **计算图**（算子/层） | **存储**（参数副本） |
| 每卡算的 | 不同的张量分片 / 不同的层 | 同一层的完整计算，不同 batch |
| 数据并行度 | 有（PP 内可再叠 DP） | **完全数据并行** |
| 通信对象 | 激活值（TP）/ 层间张量（PP） | **参数**（all-gather） |
| 单卡能否算完一层 | TP 不能 | **能**（拿到参数后即可） |
| 单卡能否算完整个模型 | 不能 | **能**（逐层取参数） |

**最后一行是关键**：ZeRO-3 下，单张卡理论上可以从头到尾跑完整个前向，只是慢，因为每层都要等参数。而 TP 下，单卡连一层都算不完整。

## 三、容易混淆的原因

两者有表面相似：

- 单卡都持有不完整的模型
- 都要靠通信临时凑齐数据

但**凑的东西不同**：

```
TP：     凑“计算结果”（部分和 → 全和），参数本来就在
ZeRO-3： 凑“参数本身”，计算一直是完整的
```

一个切结果，一个切原料。

## 四、实践中是组合关系

大模型训练常把三者叠加，叫 **3D 并行**：

```
节点内（NVLink，带宽高）  → Tensor Parallel
节点间（IB，带宽低）      → Pipeline Parallel
全局                      → ZeRO-3 做参数分片
```

Megatron-DeepSpeed 训练 530B 就是这么做的。

**分配原则**：越贵的通信（TP 的 all-reduce 每层都做）放在带宽最高的地方；ZeRO-3 的 gather 量大但可以预取，适合跨节点。

## 五、DeepSpeed 自己的归类

官方文档把 ZeRO 称为 **sharded data parallel（分片数据并行）**，与 Megatron 的 tensor/pipeline parallel 并列，不归入模型并行。这个命名本身就说明了立场。

## 一句话

**模型并行切“计算”，每卡只算一部分；ZeRO-3 切“存储”，每卡仍算完整的层、完整的数据并行流程，只是参数按需借来借还——它是数据并行的一种极致分片形式，不是模型并行，尽管两者在“单卡装不下”这一点上看起来很像。**

# ZeRO 用速度换显存：单步延迟变慢，可跑批大小变大

> **你的问题（整理后）**：从 DDP 依次升级到 ZeRO-1/2/3，训练速度是否逐级提升？能够开出的最大 batch size 是越来越大，还是越来越小？

## 一、结论

| 方案            | 单步速度（相对 DDP）            | 可开 batch    | 本质     |
| ------------- | ----------------------- | ----------- | ------ |
| DDP / Stage 0 | 100%                    | 基准（最小）      | 无冗余消除  |
| **Stage 1**   | ≈100%（常略快）              | **↑ 3~4×**  | 省优化器状态 |
| **Stage 2**   | ≈95%~100%               | **↑ 5~6×**  | 再省梯度   |
| **Stage 3**   | **60%~80%**（无预取可低至 40%） | **↑ 8× 以上** | 再省参数   |

**速度整体持平后下降，batch 持续变大。**

## 二、为什么速度不会递增

**Stage 1 为什么基本不掉速**

通信量与 DDP 相同（都是 2N），但**优化器更新被分摊了**——每卡只更新 1/M 参数，Adam 那部分计算量也降到 1/M。所以常出现“略快于 DDP”的情况。

**Stage 2 为什么持平**

通信量不变，只是把 reduce-scatter 拆进反向过程。**理想情况下通信被计算掩盖，实际收益取决于 bucket 调参**；调不好会因碎片化反而变慢。

**Stage 3 为什么明显变慢**

通信涨到 3N（1.5 倍），而且**同步粒度从“每步一次”变成“每层一次”**：

```
Stage 2：  [====== 反向 ======][通信]             每步 1 次同步
Stage 3：  [gather][算][gather][算][gather][算]   每层 2 次同步
```

同步次数暴涨，且每次都要等最慢的卡。**没有 prefetch 的 Stage 3 会慢得很难受。**

## 三、为什么 batch 会变大

显存省下来的部分，可以**转给激活值**：

```
每卡总量 = 参数 + 梯度 + 优化器状态 + 激活值
           └────── 前三项被 ZeRO 压缩 ──────┘
                              ↓
                    剩下的空间全给激活值 → batch 变大
```

7.5B 模型、64 卡的账：

| 方案 | 非激活占用 | 可用于激活的空间 |
|---|---|---|
| DDP | 120 GB | 极小 |
| Stage 1 | 31.4 GB | ≈ 4 倍 |
| Stage 2 | 16.6 GB | ≈ 7 倍 |
| Stage 3 | 2.2 GB + 层缓冲 | ≈ 10 倍+ |

**激活值近似线性于 batch，所以 batch 上限也近似按这个比例放大。**

## 四、一个必须分清的概念：延迟 vs 吞吐

**单步时间变长了，但每秒处理的 token 数可能反而更高。**

$$
\text{吞吐}=\frac{\text{每步样本数}}{\text{每步耗时}}
$$

```
DDP：     batch 8  / 1.0 s  = 8  samples/s
Stage 3： batch 64 / 3.0 s  = 21 samples/s     ← 单步更慢，吞吐更高
```

**所以“训练速度”要看你问的是哪个**：

| 指标 | 随 Stage 增加 |
|---|---|
| 单步延迟（step time） | ↑ 变慢 |
| 吞吐（tokens/s） | 先 ↑，超过 critical batch size 后转平 |
| 收敛所需步数 | ↓（batch 大，步数少），但总 token 数不变 |

## 五、Stage 3 的隐藏成本

$$
\text{峰值}= \underbrace{\frac{2N}{M}}_{\text{常驻参数}}+\underbrace{2N_{\text{layer}}}_{\text{临时完整层}}+\frac{14N}{M}+\text{激活}
$$

那个 **`2N_layer`** 是 Stage 3 特有的：虽然参数切了，但任何时刻都要能放下一整层。**层越大，这个临时峰值越高，能腾给 batch 的空间就被吃掉一部分。**

## 六、实践中的选择

```
显存放得下模型但 batch 太小  → Stage 1（几乎不掉速，性价比最高）
反向峰值 OOM               → Stage 2
单卡装不下整个模型          → Stage 3（别无选择，接受降速）
```

**Stage 1 是“免费”的，Stage 3 是“付费”的**——这是三者最本质的区别。

## 一句话

**从 DDP 到 ZeRO-3，速度不是越来越快：Stage 1/2 与 DDP 基本持平，Stage 3 明显变慢；而 batch 是一直变大，因为省下的显存全转成了激活空间。ZeRO 做的是“用时间换空间”，只是当 batch 增大带来的吞吐提升足够大时，账面上仍然划算。**
