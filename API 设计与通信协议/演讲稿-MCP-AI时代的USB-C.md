# 演讲稿：MCP —— AI 时代的 USB-C（8 分钟技术分享）

> 配套笔记：《1.8 MCP vs 传统集成方案对比》
> 用途：技术分享 / 面试项目讲解开头 / 组会汇报
> 时长：约 8 分钟（语速 ~180 字/分钟）
> 讲法建议：括号内是「动作提示」，加粗句是必须停顿强调的重点

---

## 开场（0:00–0:45）

大家有没有想过一个问题：为什么现在每个 AI 应用，都像是从零开始「重新发明轮子」？

我做一个 AI 助手要查天气，要写天气的 API 适配；做差旅助手要查机票，又要写一套携程的适配；换个模型，**还要再写一遍**。N 个模型 × M 个系统，就是 N×M 次重复劳动。

（停顿）

这个问题，Anthropic 在 2024 年 11 月给出的答案，叫做 **MCP** —— Model Context Protocol，模型上下文协议。到今天，OpenAI、Google、微软全部接入了它，GitHub 上相关项目加起来几十万 Star。

有人把它叫做 **「AI 世界的 USB-C」**。我今天就想花 8 分钟讲清楚三件事：**MCP 到底解决什么问题、它怎么工作的、以及它跟 REST、GraphQL、gRPC 到底什么关系。**

---

## 第一部分：MCP 解决什么问题（0:45–2:30）

先说一个反直觉的结论：**MCP 根本不是 REST / GraphQL / gRPC 的竞争对手。**

REST、GraphQL、gRPC 解决的是同一个问题——**「机器和机器怎么通信」**。它们的服务对象是代码，代码是确定性的，写死了就不会变。

但 AI 应用面对的是另一个问题——**「模型怎么知道有哪些工具、工具怎么用、结果怎么理解」**。

（停顿，敲黑板）

模型的调用是**概率性的**。它不像代码那样「编译过就一定能跑对」，它需要人把工具的用法讲清楚。

举三个传统方案的痛点：

- **REST**：接口是写死的，`/api/users` 在那儿，模型想查用户就只会这一个。新增一个接口？那得模型重新学。**契约靠人读文档，模型没法在运行时发现新接口。**
- **GraphQL**：查询要精确构造，但模型生成的复杂嵌套查询经常出错——**它要求调用方「聪明」，而模型恰恰不够聪明。**
- **gRPC**：性能无敌、类型精确，但**类型精确 ≠ 语义清晰**。模型需要的是「这个工具什么时候用」，不是「这个方法的 proto 定义」。

而 MCP 干的，是把这三件事标准化：

1. **工具的发现**——模型运行时问一句 `tools/list`，就能拿到所有能用的工具
2. **工具的描述**——每个工具自带 `description` + 参数 Schema，这就是给模型看的说明书
3. **上下文的供给**——除了动作，还能给模型喂「数据」（Resources）和「模板」（Prompts）

一句话总结：**REST 服务代码，MCP 服务模型。**

---

## 第二部分：MCP 怎么工作（2:30–5:00）

MCP 的架构是三层，记一个口诀：**宿主带客户，客户连服务。**

```
Host（AI 应用，比如 Claude）
  └─ Client（MCP 客户端，一个连接一个）
       └─ Server（暴露能力：工具/资源/提示词）
```

- **Host** 是装着大模型的应用，负责决定「模型该用什么工具」
- 每个 **Server** 对应一个 **Client**，负责协议的连接
- **Server** 暴露三类原语，我强调这个，面试必考：

| 原语 | 一句话 | 类比 |
| --- | --- | --- |
| **Tools 工具** | 模型能调用的函数，有副作用 | 双手 |
| **Resources 资源** | 模型能读的数据，只读 | 眼睛 |
| **Prompts 模板** | 可复用的提示词模板 | 剧本 |

（停顿）

底层协议是 JSON-RPC 2.0，但比普通 JSON-RPC 多了一个杀手锏：**能力协商**。

连接建立后，Client 和 Server 先互相发 `initialize`，声明「我支持什么」。这带来一个巨大好处——**协议可以向前兼容演进，不用版本化爆破**。REST 改个字段要开 `/v2`，MCP 改能力只需要协商。

传输层这块有个重要的演进，是我做对比时发现的：

（停顿）

**早期 MCP 用 SSE**——服务器向客户端单向推送。但它要两条连接，POST 发请求、GET 收事件，在网关、负载均衡、鉴权面前特别难搞。

**2025 年 6 月的稳定版换成了 Streamable HTTP**——一条标准 POST 连接，请求-响应和流式响应一起搞定，直接兼容现有基础设施。这一个改动，就是 MCP 从「能用」走向「能被企业采用」的关键。

最后说清楚一个容易混的概念——**MCP 和 Function Calling 什么关系？**

（停顿）

**Function Calling 是模型的一种能力**——让模型输出结构化的函数调用。**MCP 是一套生态协议**——让所有模型都能统一发现、调用所有工具。

打个比方：Function Calling 是「一个人会用筷子」，MCP 是「所有餐厅都用统一的菜谱格式」。前者解决单个模型，后者解决整个生态。

## 第三部分：和传统方案的关系、怎么选（5:00–6:45）

所以回到标题：MCP 跟 REST / GraphQL / gRPC 到底什么关系？

（停顿）

**我的结论：它们不是替代关系，是分层关系。**

- 你要给**模型**用 → 选 MCP
- 你要给**代码**用 → REST / GraphQL / gRPC 照旧
- 高性能微服务 → gRPC 依然不可替代

但更聪明的做法是**两层都要**：

**内部用 gRPC / REST 把核心能力暴露出来，外层套一层 MCP 门面，专门给模型用。** 这其实是现在大厂 Agent 平台的通行架构。

（停顿）

而且 MCP 有一个特别务实的优势：**它是「加一层门面」，不是「推倒重来」。** 你的老 API 继续给代码用，只需要写一个适配器，把传统 API 包装成 MCP 工具。我项目里就是这么做降本的——把原来手写的工具调用，统一收敛到 MCP 的 `tools/list` + `tools/call` 接口上。

选型上我给自己定的决策框架就三步：

1. **先问服务对象**：代码用传统协议，模型用 MCP
2. **再问数据形态**：要精确取数选 GraphQL，要高吞吐选 gRPC
3. **最后看生态**：MCP 生态已经覆盖了绝大多数常用工具

## 第四部分：风险与展望（6:45–7:40）

说点泼冷水的话，MCP 不是银弹，有三个真问题：

1. **安全**：工具返回的数据里可能夹带恶意指令，诱导模型去调不该调的工具——这叫**提示注入**。所以敏感工具要做人工确认，工具输出要做「数据 / 指令」隔离。
2. **成熟度**：规范还在快速演进，SDK 很多还在 pre-1.0。落地要锁版本、做回退。
3. **性能**：JSON-RPC 包装有开销，高频路径该走原生 API 还是走原生 API。

（停顿）

但我个人判断，**MCP 的方向是对的**——它把「AI 需要什么」变成了协议的第一公民。当一个协议同时被 Anthropic、OpenAI、Google、微软采纳，它就已经不只是技术选型，而是生态事实。

## 结尾（7:40–8:00）

最后收一下。

MCP 让我印象最深的一点，是它回答了一个时代问题：**当大模型成为新的「接口消费者」，我们的集成协议该为谁设计？**

过去 30 年，协议为人写、为代码写。现在，第一次有一个协议**专门为模型设计**。REST 是 HTTP 世界的 USB，而 MCP，正在成为 AI 世界的 USB-C。

（停顿，收尾）

## 附：可能的追问与应对

**Q：MCP 性能比 gRPC 差，为什么还用？**
> 性能不是 MCP 的卖点。对 AI 应用，模型一次调对工具、少一次失败重试，比省几毫秒有价值得多。高频路径保留原生调用即可。

**Q：MCP 和 Function Calling 到底怎么区分？**
> Function Calling 是模型能力，MCP 是生态协议。OpenAI 自己也接入了 MCP，两者是「能力」与「标准」的关系，不冲突。

**Q：MCP 服务器在哪跑？**
> 两种：stdio（本地进程，模型和工具在同一台机器）和 Streamable HTTP（远程部署，工具是独立服务）。本地安全、远程可扩展。
