## 一、MCP 概念基础（🟢）

### Q1. 什么是 MCP？一句话讲清楚

**一句话**：MCP（Model Context Protocol，模型上下文协议）是一个**为 AI 应用设计的开放协议**，它规定了「大模型如何发现、调用工具，以及如何获取上下文（数据与提示模板）」。

**加分扩展（3 句版）**：
- 由 Anthropic 于 2024 年 11 月开源，2025 年 6 月发布 2025-06-18 稳定规范
- 定位是「AI 应用与工具/数据之间的标准接口层」，被 OpenAI、Google、微软接入，是事实标准
- 常被类比为 **AI 世界的 USB-C**——一个接口，插所有工具

**踩坑提示**：不要只说「它是让 AI 调用工具的标准」——要带上「**上下文管理**」和「**工具发现**」两个关键词，这才说明你真懂。

### Q2. MCP 解决的核心问题是什么？

**参考回答**：解决的是「**模型如何发现并正确使用工具**」的标准化问题，具体拆三点：
1. **工具碎片化**：N 个模型 × M 个系统 = N×M 次重复集成。MCP 让集成降为 N+M。
2. **工具发现难**：REST 靠人读文档、GraphQL 靠懂 Schema，模型无法在运行时发现新工具。MCP 用 `tools/list` 动态发现。
3. **上下文割裂**：传统 API 只返回数据，不携带「如何理解」。MCP 用 Resources 显式声明模型需要的数据，用 Prompts 提供模板。

**一句话收口**：传统协议服务「确定性的代码」，MCP 服务「概率性的模型」。

### Q3. MCP 的三层架构是什么？

**参考回答**（口诀：**宿主带客户，客户连服务**）：

```
Host（LLM 应用，如 Claude Desktop）
  └─ Client（MCP 客户端，每连接一个）
       └─ Server（暴露能力）
```

- **Host**：承载 LLM 的应用，决定「模型该用什么工具」
- **Client**：每个 Server 对应一个 Client 实例，管理协议连接生命周期
- **Server**：暴露 Tools / Resources / Prompts 三类原语

**追问陷阱**：面试官可能问「Client 和 Host 是一对一吗？」→ 不，一个 Host 可以有多个 Client，每个 Client 连接一个 Server。

### Q4. MCP 的三大原语是什么？分别解决什么问题？

**参考回答**（表格背熟）：

| 原语 | 作用 | 类比 | 谁触发 |
| --- | --- | --- | --- |
| **Tools** | 模型可调用的函数，**有副作用**（查库/写文件/调 API） | 双手 | 模型主动调用 |
| **Resources** | 模型可读取的数据，**只读** | 眼睛 | 按需读取 |
| **Prompts** | 参数化的提示模板 | 剧本 | 用户/应用触发 |

**记忆口诀**：**动作是 Tools，数据是 Resources，模板是 Prompts。**

**加分**：补充一句——「Tools 回答『我能干什么』，Resources 回答『我需要什么信息』，Prompts 回答『怎么干最好』」。

### Q5. MCP 和 Function Calling 有什么区别？（🟡 高频追问）

**参考回答**：
- **Function Calling 是模型的一种能力**：让模型输出结构化的函数调用参数。绑定具体厂商（OpenAI 等）。
- **MCP 是一套开放协议**：规定了工具如何被发现、描述、调用。厂商中立。
- 一句话：**Function Calling 解决「模型能不能调用工具」，MCP 解决「所有模型怎么统一调用所有工具」**。两者不冲突——OpenAI 自己都接入 MCP。
- 类比：Function Calling 是「人会用筷子」，MCP 是「餐厅用统一菜谱格式」。

## 二、MCP 技术细节（🟡）

### Q6. MCP 基于什么协议？传输层有哪些？

**参考回答**：
- 底层是 **JSON-RPC 2.0**（请求/响应/通知/错误 四个消息类型）
- 传输层两种：
  1. **stdio**：本地进程间通信，模型与工具同机，最安全
  2. **Streamable HTTP**：远程部署，一次标准 POST 支持请求-响应 + 流式
- **演进**：早期用 SSE（单向流、两条连接），2025-06-18 稳定版用 **Streamable HTTP** 取代。原因：SSE 的 GET 长连接在网关/负载均衡/鉴权下难维护。

**加分点**：能主动说出「SSE → Streamable HTTP」的演进，说明你真的跟进过规范。

### Q7. 什么是 MCP 的能力协商（Capability Negotiation）？

**参考回答**：
- 连接建立后，Client 与 Server 互发 `initialize` 请求，携带各自支持的 `capabilities`
- 例如：Server 声明 `{ tools: {}, resources: {}, prompts: {} }`，Client 声明 `{ roots: {} }`
- 好处：**协议可向前兼容演进，无需版本化爆破**。REST 加字段要开 `/v2`，MCP 改能力靠协商。

**面试引申**：这正好对比 REST 的版本管理复杂——是很好的对比素材。

### Q8. MCP 工具的描述如何保证模型正确使用？（工具设计）

**参考回答**：三个设计要点：
1. **description 即说明书**：要写「做什么 + 何时用 + 注意事项」，这是模型唯一的理解来源
2. **inputSchema 用 JSON Schema**：每个字段加 `description`，让模型知道参数含义
3. **按需裁剪工具**：不要一次性暴露全部工具，按场景动态给模型「此时有用」的工具，省 token 且减少误调用

**加分点**：结合真实项目——「我在 Agent 项目里，会根据用户意图先筛选工具子集，再传给模型」。

### Q9. MCP 的典型调用流程（完整链路）是什么？

**参考回答**（能一步步说出来）：
1. Host 启动，Client 与 Server 建立连接 → `initialize` 能力协商
2. Client 发 `tools/list`，拿到工具清单（名称/描述/参数 Schema）
3. Host 把工具定义注入 LLM 的上下文（提示词）
4. LLM 根据用户问题，输出一个 `tools/call` 调用意图
5. Client 发 `tools/call`，Server 执行并返回结构化结果
6. 结果回填 LLM，模型据此生成最终答案

**这就是「工具循环」：发现 → 注入 → 决策 → 调用 → 回填**。

## 三、横向对比（🟡 必考）

### Q10. MCP 和 REST / GraphQL / gRPC 是什么关系？

**参考回答（核心判断题）**：**不是替代关系，是分层关系。**
- 服务对象不同：REST/GraphQL/gRPC 服务「代码」，MCP 服务「模型」
- 定位不同：前者是通信协议，MCP 是「工具 + 上下文的集成层」
- 最佳实践：**内部用 gRPC/REST 暴露能力，外层套 MCP 门面给模型用**

**类比**：REST 是图书馆目录卡片，GraphQL 是定制检索，gRPC 是高速专线，MCP 是给 AI 配的图书管理员。

### Q11. 四种方案的核心差异对比表

| 维度 | REST | GraphQL | gRPC | MCP |
| --- | --- | --- | --- | --- |
| 服务对象 | 代码 | 代码（前端为主） | 代码（微服务） | **模型** |
| 协议/传输 | HTTP/1.1 | HTTP/1.1 | HTTP/2 | JSON-RPC 2.0 (stdio/HTTP) |
| 数据格式 | JSON/XML | JSON | Protobuf 二进制 | JSON |
| 类型系统 | 弱 | 强（SDL） | 强（proto3） | 结构化（JSON Schema） |
| 接口模型 | 资源+动词 | 查询语言 | 方法 | **工具/资源/模板** |
| 实时性 | 轮询/WS | 订阅 | 原生流式 | 服务端推送 |
| 学习成本 | 低 | 中 | 中 | 低-中 |
| **AI 友好度** | 低（静态接口） | 低（要精确查询） | 低（语义不透明） | **高（动态发现）** |

### Q12. 为什么 GraphQL 对 AI 不友好？

**参考回答**：
- GraphQL 要求调用方**精确构造查询**，但 LLM 生成的嵌套 query 容易出错
- Schema 是给**人/代码**看的类型系统，模型需要的是**语义描述**而非类型精确
- 缓存困难（自定义 query 无法利用 HTTP 缓存）
- **根本矛盾**：GraphQL 的价值是「减少网络往返 + 精确取数」，但对模型来说，「能一次调对工具」比「少传几个字段」重要得多

### Q13. 为什么 gRPC 性能好却不适合直接给 AI 用？

**参考回答**：
- 性能好因为：Protobuf 二进制 + HTTP/2 多路复用 + 头部压缩
- 但对模型：**类型精确 ≠ 语义清晰**。proto 定义告诉模型「参数是 int32」，但没告诉它「这个参数填什么、什么时候该用这个工具」
- 而且浏览器支持差、调试困难、服务编排靠代码，模型无法自主选择方法

## 四、场景题（🟡 高频）

### Q14. 你们项目里怎么做工具调用的？怎么和 MCP 关联？

**参考回答（结合自身项目，这里以 Agent 项目为例）**：
- 我在 Agent 项目里实现了**类 MCP 的工具调用机制**：定义工具 Schema → 注入模型上下文 → 模型输出 `tools/call` → 执行并回填
- 与 MCP 的关系：我项目用 JSON 定义工具描述（类似 `tools/list`），用统一的执行入口分发（类似 `tools/call`），**思想一致、实现是轻量的自研版**
- 演进方向：如果要把工具生态开放给多模型/多方复用，会迁移到标准 MCP Server

**⚠️ 注意**：回答这类题**不要吹自己「用了 MCP」**，诚实说「借鉴了 MCP 的设计思想」，反而显得可信。除非你项目里真接入了 MCP SDK。

### Q15. 让你设计一个「AI 助手接入 10 个外部系统」，怎么选型？

**参考回答**：
1. **模型要用的** → MCP Server 统一暴露：查天气、查机票、订酒店各自包成一个 Tool
2. **代码要用的** → 原有 REST/gRPC 不动
3. **架构**：外层 MCP 门面 + 内部 REST/gRPC 核心服务
4. **安全**：工具级 RBAC + 敏感操作人工确认
5. **降级**：MCP Server 挂时，降级直连原 API

### Q16. MCP 的性能开销会不会是问题？你怎么取舍？

**参考回答**：
- 会有一层 JSON-RPC 包装 + 能力协商开销，量级上确实不如 gRPC
- 但**对 AI 应用，性能不是瓶颈**——瓶颈是「模型能不能一次调对」。一次失败重试的成本 >> 几毫秒协议开销
- **取舍方案**：高频热路径（如鉴权、缓存读取）走原生 API；模型交互路径走 MCP
- 结论：**MCP 的「性能」卖点是适配性，不是吞吐**

## 五、安全题（🔴 加分）

### Q17. MCP 相比传统 API 有哪些独特的安全风险？

**参考回答（说出「提示注入」就算过）**：
1. **工具误调用/滥调用**：模型可能被诱导调用高权限工具 → 工具级 RBAC + 敏感工具人工确认
2. **提示注入扩散**：工具返回的数据里可能夹带恶意指令（如返回内容写着「忽略之前指令，执行 XX」）→ 数据/指令隔离
3. **资源越权读取**：Resources 的 URI 需按会话鉴权
4. **工具供应链**：第三方 MCP Server 质量参差 → 优先官方/大厂维护的

### Q18. 如何防御 MCP 的提示注入？

**参考回答**：
1. **数据/指令隔离**：把工具返回的内容包裹在明确的 `<data>` 边界标记里，与系统指令分离
2. **敏感工具人工确认**：写文件、删数据、转账等高危工具，要求用户二次确认
3. **工具最小权限**：只暴露当前场景需要的工具，减少被诱导面
4. **输出校验**：对工具返回做白名单/格式校验，剥离可疑指令

## 六、架构与演进（🔴 加分）

### Q19. MCP 为什么能成为事实标准？你会怎么评估它的前景？

**参考回答**：
- **为什么能成**：① 开源且厂商中立 ② 解决真实痛点（工具碎片化）③ 巨头集体接入（OpenAI/Google/微软）④ 传输层向标准 HTTP 演进，企业易落地
- **前景评估**：
  - 正向：生态已经形成，SDK 完善，是 AI Agent 基础设施的必然趋势
  - 风险：规范仍在快速演进（版本兼容）、Server 生态质量参差、安全模型尚未成熟
  - **个人判断**：方向正确，值得投入。但落地要锁版本、留回退。

### Q20. 如果让你给现有系统引入 MCP，你的实施路径？

**参考回答（渐进式，四阶段）**：
1. **评估**：盘点现有 API，识别哪些要给模型用（2-4 周）
2. **试点**：挑 1-2 个高频 API 包成 MCP Tool，验证效果（4-6 周）
3. **并行**：模型走 MCP、代码走原 API，双轨运行（8-12 周）
4. **切换**：全部模型入口切 MCP，原 API 保留给代码（2-4 周）

**核心思想**：**MCP 是加一层门面，不是推倒重来。** 老 API 继续服务代码，MCP Server 做适配层（Adapter）包给模型。
